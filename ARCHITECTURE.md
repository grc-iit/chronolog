## 2. Glossary

- **Chronicle**: a namespace of stories. **Story**: one append-only log identified by `story_id`.
- **story_id**: uint64 assigned by Catalog. Never derived from names. Legacy derived it as CityHash64(chronicle+story), which collides on ("a","bc") versus ("ab","c") (`src/chrono-common/include/ArchiveManifest.h`, origin/archive-file-manifest). That derivation is forbidden.
- **writer_id**: uint64 assigned by Catalog at acquire. **incarnation**: uint64 persisted per writer identity, strictly increasing on every re-acquire. **sequence**: uint64 per (writer_id, incarnation), starts at 1, gapless.
- **EventId**: (story_id, writer_id, incarnation, sequence). The identity of an event. Equality of EventId is equality of events. `include/chronolog/types.h`.
- **HLC**: hybrid logical clock {int64 physical_ns; uint32 logical}. Keeper-assigned on accept.
- **causal_floor**: the maximum HLC a client has observed from any append result or read. Sent on every append item.
- **physical time**: the writer's CLOCK_REALTIME reading in ns, with an optional uncertainty bound and a clock status.
- **Durability**: ACCEPTED (Keeper RAM) or DURABLE (fsync'd Keeper WAL). Only DURABLE is an ack. UNSPECIFIED in a request means DURABLE and is never an achieved level.
- **Visor**: the process hosting Catalog and Cluster. **Keeper**: ingestion and WAL, hosts Journal. **Grapher**: tiering and archive, hosts TierStore publish. **Player**: hosts Replay.
- **Epoch**: per-story ownership version. A Route is valid for exactly one epoch.
- **Route**: {epoch, keepers, grapher, player} for a story. **KeeperRef**: {process_id, endpoint}, the one Keeper identity used by Route.keepers and Acquisition.assigned_keeper; internal subscriptions use process_id alone.
- **Pending-fsync HLC**: per writer, the HLCs assigned to DURABLE events whose fsync has not completed. Read only under that writer's lock.
- **Chunk**: a half-open HLC window [start, end) of one story's events, the unit of Keeper to Grapher transfer and of archive publication. Identified by a string `chunk_id` unique per Keeper.
- **Revision**: a monotonically increasing number on every AcquisitionUpdate, a persisted Catalog counter in SQLite that is never reused across Visor restarts. Keepers report `applied_revision` in Heartbeat. **fenced**: the per-item bool a Release returns, true iff the assigned Keeper applied the release revision within the fence timeout.
- **Receipt**: a Grapher-assigned number for one delivered chunk, scoped to a Grapher instance string. Delivery is not persistence.
- **W (persisted watermark)**: per-story end of the longest contiguous run of persisted windows from the story's earliest recorded window. Monotonic within a live story generation; a tombstone ends the generation.
- **E**: the Keeper's eviction boundary. Invariant E <= W.
- **Salvage chunk**: a chunk written outside the contiguous timeline. Watermark-exempt. Readable, never advances W.
- **Manifest**: the archive's append-only record of published files, one log and one snapshot per Grapher. `ManifestRecord.manifest_writer` names the Grapher instance that owns a log; it is distinct from the event `writer_id`.
- **Frontier (sealed, exclusive)**: for writer w assigned to Keeper k, an HLC F with the sealed-prefix property: every event of w with hlc < F is visible to reads and no event of w with hlc < F will ever be ingested. That property is the whole definition. With mixed durability a pending DURABLE event caps F below ACCEPTED events that are already visible. All writers on one Keeper share that Keeper's sealed frontier.
- **Completion**: the trailing message of a Replay.Read stream stating complete, frontier and laggards.
- **Gateway**: the out-of-core process that does authn, ACLs, redaction and audit. Not part of this repository's core.
- **Contract**: one of the six pure-virtual C++ interfaces in `include/chronolog/`.
- **Walking skeleton**: Visor Catalog plus Keeper Journal in RAM plus one client, composed end to end before any domain port.

## 3. Data model and the three time fields

Every event carries exactly three time-related fields. None substitutes for another.

| Field | Who assigns | Type | Use |
| --- | --- | --- | --- |
| physical | writer, at creation | TimeReading{physical_ns int64, uncertainty_ns optional uint64, status} | Range queries on wall time, auditing, OTel alignment |
| hlc | Keeper, on accept | Hlc{physical_ns int64, logical uint32} | Total order and causality |
| identity | Catalog (ids) and writer (sequence) | EventId | Deduplication, per-writer order, retry |

Every stored and streamed Event carries `durability`, the achieved level (ACCEPTED or DURABLE), so readers can apply I6.8. Envelope fields, all optional: `content_type` string; `payload` bytes, max size configurable, default 1 MiB, enforced at the Keeper; `trace_id` bytes(16) and `span_id` bytes(8) carrying W3C trace context; `attributes` map<string,string> for OTel GenAI keys (gen_ai.agent.id, gen_ai.conversation.id, gen_ai.tool.call.id, gen_ai.operation.name), MCP request ids, and A2A task_id, context_id, message_id. Key names follow the OTel GenAI semantic conventions (gen-ai-agent-spans), the A2A specification proto and the newest dated MCP schema, never the 2024-11-05 one.

Invariants:
- I3.1 An event MUST carry a complete EventId (all four fields non-zero) before the Keeper accepts it. story_id and epoch come from the request, writer_id, incarnation and sequence from the item (W10.13). Gate: `JournalContract.RejectsIncompleteEventId`.
- I3.2 A payload above the configured maximum MUST be rejected per item with INVALID_ARGUMENT in the item status, never truncated. A trace_id not exactly 16 bytes or a span_id not exactly 8 bytes, when present, MUST be rejected the same way. Gate: `JournalContract.PayloadAndTraceContextValidation`.
- I3.3 The Keeper MUST NOT modify physical time. It MUST assign hlc. Gate: `JournalContract.EnvelopeAndPhysicalReadingRoundTrip`.
- I3.4 Story and chronicle names map to ids in Catalog only. No component MAY compute an id from a name. Gate: `MetadataStoreContract.AssignedIdsDoNotAliasConcatenatedNames`.
- I3.5 Tombstones are identity tombstones: a destroyed story_id never returns and Catalog keeps its tombstone forever; the name may be reused by a new story with a new story_id. Gate: `MetadataStoreContract.StoryTombstonePermanence`.
- I3.6 Destroying a chronicle tombstones every story in it. Destroy of a story or chronicle MUST materialize its authority-selected due acquisitions before checking active rows and MUST refuse with FAILED_PRECONDITION while any acquisition remains active. In static mode it MUST additionally refuse while any EXPIRED or SUPERSEDED termination, including relevant historical incarnations, lacks applied_revision at least its original release revision from the owning process's currently registered instance. Registration alone is not fence proof; a replacement instance proves it after applying the WatchAcquisitions snapshot through that revision. Materialized expiry commits even if destroy is refused; no partial chronicle tombstone is allowed. Gates: MetadataStoreContract.ChronicleTombstonePermanence, DestroyRefusesActiveAcquisitions, DestroyMaterializesLeaderDueSet, DestroyRefusalCommitsMaterializedExpiry, StaticDestroyRequiresConfirmedExpiryFence and StaticDestroyRequiresConfirmedSupersessionFence.
- I3.7 Release fences the incarnation: once (writer_id, incarnation) is released, the Keeper MUST reject every later append carrying it with FAILED_PRECONDITION, and a release carrying an older incarnation MUST NOT release a newer one. Gate: `MetadataStoreContract.OldReleaseCannotReleaseNewIncarnation`, `JournalContract.ReleasedIncarnationCannotAppend`.
- I3.8 Every acquisition has a finite liveness-only lease. Omitted duration uses acquisition_lease_default_ns=300000000000; supplied positive duration clamps to the configured min/max. Invalid duration, empty preference, zero expected prior, invalid request id or checked arithmetic overflow MUST fail before mutation. Expiry apply checks the current unreleased tuple; terminal cause and original global release revision are idempotent and renewal MUST NOT revive a terminal acquisition. Acquire request ids have at least 128 random bits, are process-local retry ids of at most 128 UTF-8 bytes, and MUST NOT enter client checkpoints. Matching current-live retry preserves the grant and deadline; changed inputs refuse INVALID_ARGUMENT. Plain Acquire refuses HELD; conditional plain Acquire requires the exact terminal prior; takeover with expected prior is CAS, and a mismatch returns PRIOR_MISMATCH/current incarnation without mutation. Restart uses a fresh-id prior CAS. Same-id terminal retry identifies the matched incarnation and original cause, or PRIOR_MISMATCH/current when a successor exists. Same-term authority lapses and service gaps preserve remaining time rather than granting a fresh duration. Gates: `MetadataStoreContract.EveryAcquisitionHasAFiniteLease`, `LeaseRequestUsesDefaultAndClamps`, `RetriedAcquireAfterLostReplyReturnsTheSameGrant`, `SameIdTerminalRetryReportsCauseAndMatchedIncarnation`; enforcement gates land with RFC-G Visor 3b.

## 4. Ownership epochs

Every story has one owning Route per epoch. Every AppendItem carries (story_id via EventId, epoch).

- I4.1 `Membership::validateEpoch(story_id, epoch)` MUST reject a stale epoch. A stale epoch is never a gRPC error: Append returns gRPC OK, the affected items carry FAILED_PRECONDITION in their ItemStatus plus `current_route`, and because a batch is single-story (W10.13) a stale request-level epoch rejects every item and the AppendResponse also carries a top-level `current_route`. No trailing-metadata encoding. Gate: `MembershipContract.StaleEpochRejection`; `JournalContract.StaleEpochReturnsCurrentRoute`.
- I4.2 Epochs MUST strictly increase per story. `MetadataStore::compareAndSetEpoch` is the only mutator and MUST reject a desired epoch that is not greater than the current one. Gate: `MetadataStoreContract.EpochCompareAndSet`.
- I4.3 In static membership mode (`membership_mode: static`, the default) epochs are static: every story is epoch 1 and routes are fixed from configuration. Dynamic mode (M8) changes epochs only under I4.7 to I4.15. Implementations MUST still carry and validate the field so clients are correct from M1. Gate: `MembershipContract.StaticEpochIsOneAndValidated`.
- I4.4 A client receiving a FAILED_PRECONDITION item MUST adopt the returned Route and retry with the same EventIds. Retries are idempotent (section 5). Gate: `ClientContract.ClientRetriesOnStaleEpochWithSameEventIds` in `tests/contract/client/`.
- I4.5 Cluster.WatchRoutes MUST send a full snapshot on subscribe and on reconnect. A Keeper MUST NOT serve a story before it has a Route for it. Gate: `MembershipContract.UnknownStoryCannotValidate`.

- I4.6 A Route change MUST NOT invalidate an in-flight Keeper to Grapher chunk stream; the stream completes under the old epoch. Chunks are immutable once sealed and the receipt protocol tolerates resends. Gate: `ArchiveTransferTest.StreamCompletesAcrossEpochChange`.

Dynamic mode (M8, RFC-B). All of the following hold only when `membership_mode: dynamic`; static deployments are unchanged. Defaults: ceiling_ahead 5000 ms, physical_ahead 2000 ms, B_L 3 s, B_H 30 s.
- I4.7 Ceilings. Every Keeper instance holds a ceiling pair committed in the Catalog, C (an Hlc) and CP (physical ns). It MUST NOT assign an hlc >= C, report a sealed frontier above C, or report a physical frontier above CP - A (I8.9). Cluster.ExtendCeiling grants only to the current registered instance of a process, only when the request's applied_route_revision is at or above that process's fence revision (the revision of the latest route change of any story whose old or new Route lists it), and monotonically per process across instances: C = max(wanted_hlc + ceiling_ahead, previous C), CP = max(realtime + B_L + physical_ahead, previous CP). A refusal for the revision condition returns the RouteUpdates the Keeper is missing, read at the leader. An append that would reach C releases the story gate, its writer lock and the clock core, waits for an extension or a route application for at most append_ceiling_wait_ms, re-enters from validation, and fails UNAVAILABLE on timeout. Register by a new instance revokes every earlier instance of that process and returns the floor pair (max C, max CP); if the new instance did not recover the earlier instance's WAL, the same command commits an epoch change for every story the earlier instance served with it as a predecessor. Gates: `JournalContract.NoAssignmentAtOrAboveCeiling`, `JournalContract.CeilingWaitDoesNotBlockRouteApplication`.
- I4.8 Transition budget. No raise of a Keeper's acceptance clock L (I8.8) puts it more than B_L ahead of its CLOCK_REALTIME, and no observed floor puts its HLC more than B_H ahead of it. A transition that needs more installs the new Route but defers admission at the new epoch for that story until realtime catches up, answering UNAVAILABLE meanwhile. Gate: `JournalContract.TransitionsCannotRatchetTheAcceptanceClock`.
- I4.9 Epoch change and admission gate. Route changes caused by one trigger (heartbeat silence for keeper_failure_timeout_ms, which affects availability only; or the operator's DrainKeeper, JoinKeeper, AbandonKeeper) are one CatalogCommand under one revision. For each story X it carries epoch e + 1 (compareAndSetEpoch stays the only epoch mutator, I4.2), the new Route, the ordering cut H_X = max over every instance of every old-Route Keeper of the C ever granted to it, each predecessor's own cut, and the story's physical floor PF_X(e + 1) = max(PF_X(e), min over every old-Route process of the latest CP granted to its latest registered instance); it sets the fence revision of every Keeper listed in the old or new Route. Each Keeper keeps a writer-preferring per-story gate held shared by every append from epoch and assignment validation through hlc assignment and pending or visible registration; lock order is gate, membership, shard, writer, clock core, and FetchHot, Heartbeat, the sealer and the WAL committer never take it. Applying a route update takes the gate exclusive, installs the Route and cuts, schedules observeFloor(H_X) when RouteUpdate.observe_floor is set for this Keeper (it is new to the Route or inherits remapped writers), schedules the raise of L to PF_X when it is new to the Route, releases the gate, and reports the revision applied only after every story in the command passed its exclusive section; admission at e + 1 opens when the scheduled steps are done under I4.8 and the ceiling exceeds H_X. Survivors never raise L. Gates: `JournalContract.ReassignedWriterObservesOldFrontier`, `JournalContract.RouteChangeWaitsOutValidatedAdmissions (TSAN)`, `JournalContract.NewMemberAcceptanceClockCoversTheStoryPhysicalFloor`.
- I4.10 Unlisted Keeper. A Keeper MUST reject per item with FAILED_PRECONDITION and current_route every append for a story whose applied Route does not list its process_id, checked under the gate with validateEpoch. Gate: `JournalContract.UnlistedKeeperRejectsAppend`.
- I4.11 Ordering and reassignment. Every hlc an old-Route instance can still assign for X is below its committed C, hence below H_X; every new-epoch assignment of a remapped writer is above H_X. Only writers of removed Keepers are remapped, by writer_id over the new Route's Keepers, stable per (writer_id, epoch) (I7.5); a remapped writer re-acquires (incarnation + 1), and unacked DURABLE items of the old incarnation are reported as outcome unknown, never acked and never silently resent.
- I4.12 Retired seals. A Keeper answering FetchHot for a story at an epoch it no longer owns reports sealed frontier min(F, own cut) and physical frontier min(P, own CP - A); a current owner's trailer carries its applied epoch. Gate: `ArchiveTransferTest.RetiredOwnerSealIsCutAtTheHandoff`.
- I4.13 Predecessors. RouteState for a story carries predecessors {KeeperRef, instance, owned epoch, own cut C_k, own CP_k} for every removed Keeper instance and every revoked instance whose WAL was not recovered. FetchHotRequest carries expect_instance and expect_epoch; a Keeper answers a predecessor request only when both match, and the trailer echoes its instance. A Read whose range starts below a predecessor's own cut includes it as a source on [start, min(end, own cut)); its physical span is (-inf, max(C_k.physical, CP_k) + S). A predecessor that does not answer, or whose seal is below that bound, makes the Read SOURCE_FAILED or LAGGING_WRITERS. Gates: `ReplayContract.UndrainedPredecessorIsASource`, `ReplayContract.DeadPredecessorIsSourceFailed`, `ReplayContract.ReplacementInstanceCannotAnswerForItsPredecessor`.
- I4.14 Drain. Once its sealed frontier reaches its own cut, a retired instance ships an Empty chunk for any eventless part of [chain_end, own cut), and an instance that never held an event for the story is drained at once. It reports drained for exactly (story, instance, owned epoch) when its eviction floor reaches its own cut (I13.8); the leader removes only that entry and in the same command raises RouteState.archived_below to the cut, and the Player reads the archive over [start, max(B, archived_below)). Gates: `ReplayContract.DrainedPredecessorHistoryComesFromTheArchive`, `MembershipContract.StaleDrainReportDoesNotRemoveANewerPredecessor`, `JournalContract.RetiredKeeperDrainsWithAnAlreadyEvictedFinalChunk`, `JournalContract.WriterlessRetiredStoryDrainsAtItsOwnCut`.
- I4.15 Abandonment. Heartbeat carries per (instance, story) settlement proofs (coverage_start, settled_through), committed in batches and never above the truth. AbandonKeeper first removes the process from every Route, then replaces each predecessor entry of each of its instances with the abandoned range [settled_through of that same instance's proof, own cut) when the proof covers the instance's first event, else [Hlc{0,0}, own cut). A Keeper that was never granted a ceiling (a cluster switched from static mode) can only be abandoned as total loss: [Hlc{0,0}, +inf) on both axes, with no ordering claim for its writers. Every Read intersecting an abandoned range is complete=false with SOURCE_FAILED. The Catalog refuses any other epoch change for a story while a Keeper of its current Route has never been granted a ceiling. Gate: `MembershipContract.AbandonedRangeUsesOnlyTheSameInstanceProof`. A Tail delivers no event across an abandoned range: I6.13 caps its frontier at the range start and terminates SOURCE_FAILED when the frontier reaches that range, with complete=false. Gate: `ReplayContract.TailStopsAtAnAbandonedRange`.

## 5. Ack semantics

`enum Durability { DURABILITY_UNSPECIFIED = 0; ACCEPTED = 1; DURABLE = 2; }` in `proto/chronolog/v1/chronolog.proto`. UNSPECIFIED means DURABLE in a request and MUST never appear as an achieved success level. Default DURABLE.

- ACCEPTED: the event is in Keeper RAM and ordered. It is lost on Keeper crash.
- DURABLE: the event is fsync'd in the Keeper WAL with group commit. It survives Keeper crash.
- Only DURABLE is called an ack in any documentation, log line, metric or SDK name.

Invariants:
- I5.1 A server that cannot provide the requested level MUST reject that item with UNIMPLEMENTED (level not built) or UNAVAILABLE (level built but failing) in the ItemStatus and `achieved_durability = DURABILITY_UNSPECIFIED`. It MUST NOT return ACCEPTED when DURABLE was requested. Status codes are fixed by this file and asserted exactly by headers and contract tests: unbuilt durability UNIMPLEMENTED, built but failing UNAVAILABLE, sequence gap FAILED_PRECONDITION with the expected sequence, payload or trace-context violation INVALID_ARGUMENT, stale epoch or released incarnation FAILED_PRECONDITION, physical reading outside the acceptance window OUT_OF_RANGE (I8.9; the rejection consumes the sequence), capacity refusal RESOURCE_EXHAUSTED with rejection CAPACITY (I13.16; decided once per request after the dedupe lookup, applied only to items that would create a new event, the sequence not consumed; amended 2026-10-03, PI A16.3 sign-off). Gate: `JournalContract.NoSilentDurabilityDowngrade`.
- I5.2 Before the WAL lands (M5), every DURABLE append MUST fail per I5.1 with UNIMPLEMENTED. The walking skeleton MUST request ACCEPTED explicitly. Gate: `JournalContract.AcceptedIsExplicitRamReceipt` instantiated for the RAM Journal.
- I5.3 AppendResult per item MUST carry status, achieved durability, assigned hlc, EventId. Gate: `JournalContract.AppendResultCarriesAllFourFields`.
- I5.4 A duplicate EventId MUST return the original result (same hlc, achieved durability equal or higher) and MUST NOT store a second copy. Gate: `JournalContract.IdempotentRetryReturnsOriginalResult`.
- I5.5 A gap in sequence for (writer_id, incarnation) MUST be rejected per item with FAILED_PRECONDITION and the expected next sequence in the item message. Later items of the same writer in that batch MUST also be rejected. Gate: `JournalContract.GaplessSequenceRejection`.
- I5.6 DURABLE MUST mean fsync returned success, not write() returned. An fsync failure MUST fail every item in the group with UNAVAILABLE and MUST NOT report DURABLE for any of them. Gate: `JournalContract.FsyncFailureFailsTheGroup` (fault-injected file sink). Crash gate: `tests/integration/keeper_wal_restart_test.sh` (ctest `keeper.wal_restart`).
- I5.7 Legacy RAM retention (KeeperChunkRetentionStore) cannot implement DURABLE and MUST NOT be labelled as such.
- I5.8 AppendStream cancellation MUST NOT roll back accepted items. Gate: `JournalAdapterTest.CancelledStreamKeepsAcceptedItems`.
- I5.9 A batch MUST be processed in item order per writer; an item's result position equals its request position. Gate: `JournalContract.PerItemFailureDoesNotEraseSuccessfulBatchItems`.

- I5.10 The WAL commits groups adaptively: as soon as the previous fsync returns, the committer writes and fsyncs every record queued at that moment, up to group_commit_max_bytes. The knob group_commit_window_us (default 0, at most 10000) holds a group open until the window has passed since its first record or the byte bound is reached; 0 is adaptive commit. I5.6 holds in both modes. Measured with tools/bench/run.sh custom at 6bbe4575 on dragon (two NVMe disks, dev build): a nonzero window cost 10 to 46% of throughput for one writer at batch 1 and gained at most 2.6% at 64 writers with batch 64, so the default stays 0. Gates: `JournalContract.FsyncFailureFailsTheGroup` instantiated for window 0 and 1000 us, `WalJournal.WindowedGroupReportsDurableOnlyAfterSyncReturns`. Amended 2026-10-03 with the PI's QA sign-off; the text it replaces described a fixed 1 ms timer the code never had.

## 6. Completeness semantics

`Replay.Read(story, [start, end))` on hlc or physical time returns EventBatch messages and ends with exactly one Completion: `complete bool`, `frontier hlc`, `repeated laggards {writer_id, incarnation, frontier}`. Then EOF.

Completion also carries `IncompleteReason reason` with values LAGGING_WRITERS, PHYSICAL_AXIS_UNBOUNDED, SOURCE_FAILED, TRUNCATED. It is set whenever `complete=false`.

Definition: the read is complete iff every Keeper in the story's Route answered and its sealed frontier F_k >= end, on the HLC axis. Equality is sufficient because the frontier is exclusive. The registered-writer view from WatchAcquisitions is used only to name laggards (writers assigned to a Keeper that failed or lags); a stale acquisition view therefore cannot produce a false complete. The Keeper obtains F by ticking its HLC (future assignments are > F) under the rules in I6.11; for DURABLE data F is capped at the minimum pending-fsync HLC. Idle registered writers share their Keeper's frontier and do not block completeness. A writer is registered from acquire until release or incarnation supersession. Completeness in v1 is defined on the HLC axis only. An HLC frontier does not bound a writer's future backdated CLOCK_REALTIME stamps, so a physical-axis Read MUST return `complete=false` with reason PHYSICAL_AXIS_UNBOUNDED until M6 lands an acceptance policy that bounds backdating.

Invariants:
- I6.1 An HLC Read with some registered writer's sealed frontier below end MUST set `complete=false`, reason LAGGING_WRITERS, and list that writer in laggards. A frontier equal to end is sufficient. Laggards are the writers whose Keeper did not answer or whose sealed frontier is below end. Gate: `ReplayContract.CompletionNamesLaggardsAndEqualityIsSufficient`, `ReplayContract.CompleteWhenEveryKeeperSealReachesEnd`, `ReplayContract.IdleRegisteredWriterDoesNotBlockCompleteness`, `ReplayContract.UnknownWriterCoveredByItsKeeperSeal`.
- I6.2 A Read MUST NOT drop events that are below the archive boundary but not yet confirmed persisted. Re-homed legacy guard: `ColdReplay.UnacknowledgedEventsBelowTheBoundaryAreKept`. Contract gate: `ReplayContract.UnconfirmedHotEventsBelowBoundarySurvive`.
- I6.3 A Keeper that fails to answer MUST make the reply incomplete with reason SOURCE_FAILED; a truncated answer MUST make it incomplete with reason TRUNCATED. Re-homed legacy guards: `ColdReplay.AKeeperThatDidNotAnswerWidensTheArchiveReadAndMarksTheReplyIncomplete`, `ColdReplay.ATruncatedAnswerMarksTheReplyIncompleteWithoutWideningTheRead`. Contract gate: `ReplayContract.FailedSourcePreventsCompleteness`, `ReplayContract.TruncatedSourcePreventsCompleteness`.
- I6.4 Events MUST be deduplicated by EventId across hot and archive sources. Re-homed legacy guards: `ReplayMerge.EventFromTheArchiveAndAKeeperIsReturnedOnce`, `ReplayMerge.EventsDifferingOnlyInWriterIdAreDifferentEvents`, `ReplayMerge.EventsDifferingOnlyInIncarnationAreDifferentEvents`. Contract gate: `ReplayContract.TotalOrderAndEventIdentityDeduplication`.
- I6.5 `Replay.Tail` MUST NOT claim completeness. Its Completion on orderly termination MUST have `complete=false`. Gate: `ReplayContract.TailNeverClaimsCompleteness`.
- I6.6 `Journal::frontier(story)` MUST return the Keeper's sealed frontier for every writer registered on that Keeper, including writers with zero events, and that value MUST satisfy the sealed-prefix property and nothing more; in particular it MUST NOT exceed the minimum pending-fsync HLC. When nothing is pending it exceeds every assignment. Gate: `JournalContract.HalfOpenRangeAndFrontierIncludesRegisteredWriter`, `JournalContract.SealedFrontierExceedsEveryAssignmentWhenNothingPending`, `JournalContract.DurableInvisibleUntilFsyncAndSealDoesNotPassPendingHlc (M5)`, `JournalContract.IdleRegisteredWriterDoesNotBlockCompleteness`.
- I6.7 A Read on a tombstoned story MUST fail whole-request with FAILED_PRECONDITION. A Read admitted before the tombstone that reaches an archive file removed by I13.11 MUST end complete=false with SOURCE_FAILED, never a partial result presented as complete. Gate: `ReplayContract.ReadOnTombstonedStoryFails`.
- I6.8 `complete=true` MUST imply that every event in the range that any writer will ever produce is in the stream. A later Read of the same range MUST return the same event set for DURABLE events; ACCEPTED events may vanish on Keeper crash and the invariant says so. On the physical axis, completeness is relative to the writers' reported intervals (I8.9). Visibility: an ACCEPTED event is visible once accepted, a DURABLE event only after its fsync. Gate: `ReplayContract.CompleteReadIsStableForDurableEvents`.
- I6.9 Tail resumes exclusively after `position` (hlc, EventId); the event at `position` MUST NOT be re-sent. Gate: `ReplayContract.TailResumesExclusivelyAfterPosition`.
- I6.10 Physical-axis Read (M6, RFC-A). Selection: every event whose interval [lo, hi] (I8.9) intersects [s, e): lo < e and hi >= s (an unbounded event: s <= p < e). For a story whose physical_policy flag is true (I8.12) the sources are read on the HLC window [s - S - D, e + A + D) (saturating) and filtered by interval; for a story whose flag is false the sources' whole HLC domain is scanned and the Read is never complete. The interval test runs at the source (Keeper FetchHot with the physical range; the archive reader after decoding), and read_max_events counts only matches. A Read whose matches exceed the bound returns TRUNCATED with no claim; the SDKs split the physical range in halves recursively, read each half as an independent Read, deduplicate by EventId and report the aggregate complete iff every leaf is complete. A Read is complete iff the story's flag is true, every Route Keeper answered with the Route epoch and reported a physical frontier P_k >= e, no source failed or was truncated, no LOST window lies in the archive range, no selected event is unbounded, and no abandoned range or undrained predecessor span (I4.13) intersects [s, e) unless every such predecessor answered with its own P >= e. A selected unbounded event gives PHYSICAL_AXIS_UNBOUNDED (meaning: an event in range has no finite clock bound); P_k < e gives LAGGING_WRITERS. Gates: `ReplayContract.PhysicalReadCompleteWhenEveryPhysicalFrontierPassesEnd`, `ReplayContract.PhysicalRangeHonorsUncertainty`, `ReplayContract.UnboundedEventMakesPhysicalReadIncomplete`, `ReplayContract.StoryWithoutPolicyIsNeverPhysicallyComplete`, `replay_adapter.PhysicalReadAboveTheLimitIsTruncatedWithoutClaim` (`src/chrono-player/tests/`). `ReplayContract.PhysicalAxisAlwaysIncomplete` is retired.
- I6.11 Frontier ordering rules, all MUST. (a) Archive.FetchHot ticks F before it scans events, never after, so every event with hlc < F accepted during the scan is in the reply. (b) HLC assignment and insertion are atomic under the writer's lock, and the frontier tick happens before any per-writer lock is taken for the scan. (c) Completeness is decided over every Keeper in the Route; the Player maps registered writers to `assigned_keeper` from WatchAcquisitions only to name laggards, and a Keeper that did not answer makes the read SOURCE_FAILED with its writers listed. (d) In dynamic mode an epoch change carries the ordering cut H_X of I4.9 (the maximum ceiling ever granted to the previous epoch's Keepers, which bounds every hlc they can assign); every Keeper that is new to the Route or inherits remapped writers MUST observeFloor(H_X) before admitting at the new epoch, and survivors that inherit no writer need not. A writer's new incarnation is never admitted on a different Keeper until its old incarnation is fenced on the old Keeper. Under static epochs the persisted Catalog assigned_keeper is shared across incarnations, so both incarnations land on one Keeper and I7.4 rejects late old-incarnation appends. (e) Pending-fsync state is tracked per writer and registered in the same writer-lock critical section as HLC assignment. The scan ticks h_t first, then for each writer takes that writer's lock, scans its visible events and reads that writer's minimum pending-fsync HLC while still holding the lock. F = min(h_t, min over writers of those per-writer minima). Two conditions make this sound and are part of the rule: fsync completion makes an event visible and clears its pending entry under the same writer lock, so a scan never observes an event that is neither visible nor pending; and writer state is created under the story lock before the writer's first HLC assignment, and the scan iterates the writer set as it is after the tick, so every writer assigned before the tick is scanned. A global pending set sampled outside the writer locks is unsound whether sampled before the scan (an event assigned before the tick but registered after the sample) or after it (an fsync completing after the scan drops an unreturned event from the cap). (f) FetchHotTrailer carries the Keeper's current epoch; the Player MUST treat a trailer epoch different from its Route epoch as SOURCE_FAILED. Gates: `ArchiveTransferTest.FetchHotTicksFrontierBeforeScan`, `ArchiveTransferTest.FrontierTickOrderedBeforeInsert (TSAN)`, `ReplayContract.UnknownWriterCoveredByItsKeeperSeal`, `JournalContract.PendingFsyncRegisteredWithAssignment (TSAN)`, `JournalContract.FsyncCompletionFlipsVisibilityUnderWriterLock (TSAN)`, `JournalContract.WriterCreatedBeforeFirstAssignmentIsScanned`, `JournalContract.ReassignedWriterObservesOldFrontier`, `ReplayContract.TrailerEpochMismatchIsSourceFailed`, `AcquisitionWatcherTest.NewOwnerAdmittedOnlyAfterOldOwnerFenced`.
- I6.12 Truncated HLC Reads. A TRUNCATED HLC Read's frontier c MUST be at or below: every Route Keeper's reported sealed frontier; for every applicable predecessor whose seal is below its own cut, that seal; the end of what the Player returned; and for every source whose answer was truncated, the hlc of the last event that source returned. No LOST window may lie below c, and the Player then cuts c down to an archive record start. Every source's contribution is exclusive at c, so [start, c) is complete on its own and a continuation from c inclusive has no gap or duplicate. Gate: `ReplayContract.TruncatedReadFrontierIsACompletePrefix`.
- I6.13 Tail delivery frontier (RFC-D). Let position be the exclusive resume position and initialize `T0 = position.hlc`. T never decreases. Every required source contributes only coverage proved under its expected epoch and instance, following I6.11 and I6.12. Retained coverage is final within its instance. An instance change discards that source's buffered state and makes the current round non-advancing; refetch from T. Compute T_min as the minimum covered bound of every Route Keeper and every still-constraining predecessor. Cap it at the start of each abandoned range above T that it would cross (I4.15). If a required source has neither an eligible answer nor retained coverage, this round moves nothing. A round with no source proves no advancement. Deliver every merged hot-buffer and archive event with `T <= hlc < T_min` and `ReplayLess(position, event)`, exactly once per Tail RPC in ReplayLess order; then set `T := max(T, T_min)`. Events sharing an HLC below T_min are ordered by `(writer_id, incarnation, sequence)`; all events at `hlc == T_min` wait. Archive events obey the same bound regardless of eviction floors. Across reconnects I6.9 governs exclusive resumption from the client's last received event. If T lies in or reaches an abandoned range, end with complete=false, frontier T and reason SOURCE_FAILED after delivering any eligible prefix already queued. Any Keeper FAILED_PRECONDITION, without message matching, or a recorded archive tombstone is evidence for Catalog confirmation. Only a Catalog FAILED_PRECONDITION ends the Tail with FAILED_PRECONDITION, taking precedence over archive-tombstone SOURCE_FAILED termination, including a tombstone first discovered by the archive refresh. Previously queued eligible events may be returned before confirmation. Without confirmation, a refusing or down Keeper stalls delivery; an archive tombstone, LOST window or archive-read failure retains the existing SOURCE_FAILED behavior. A failure of the Route source for the round ends the Tail with that status; the client resumes under I6.9. A Tail never claims completeness (I6.5). Gap-free continuation across Keeper instances requires that no source's F fall below T, as provided by M5 WAL frontier reservation. I6.8 permits ACCEPTED events to vanish on crash. A Keeper without a WAL does not satisfy section 12's restart rule; for it the gap-free promise holds only above T. This rule does not promise recovery of ACCEPTED data or delivery of new events assigned below T after a RAM-only restart. Gates: all TAIL-1 entries in the section 15 ReplayContract, Component suites and adapter (RealKeeperTail) inventory.
- I6.14 Unreadable archive files (RFC-I 3.10; PI sign-off 2026-10-03). A Read whose range overlaps an effective Published archive record, as resolved from the manifest when the Read planned it and after the re-resolution of I13.12 and I13.14, whose file cannot be read at its effective location (tier unavailable, file missing, undecodable, checksum mismatch, object-store error, or no answer within tier_io_timeout_ms) MUST end complete=false with reason SOURCE_FAILED, never TRUNCATED (I6.12), and MUST NOT return events of that range while claiming completeness. A file that a Deleted record retires, or whose compaction successor reads, is not a failure. A Tail delivers no event at or above the start of such a file and ends SOURCE_FAILED as I6.13 states. Gate: `ReplayContract.UnreadableArchiveFileIsSourceFailed`, with cases missing, undecodable, checksum mismatch, unavailable tier, hang, physical axis and Tail.

## 7. Ordering

Total order for replay: (hlc, writer_id, incarnation, sequence), lexicographic. Implemented once as `ReplayLess` in `include/chronolog/types.h`. Per-writer order is sequence order and is never violated.

- I7.1 Replay output MUST be sorted by the total order within one stream. Gate: `ReplayContract.TotalOrderAndEventIdentityDeduplication`.
- I7.2 For a fixed (writer_id, incarnation), hlc MUST be non-decreasing in sequence. The Keeper enforces this at accept because it assigns hlc in arrival order and rejects gaps. Gate: `JournalContract.PerWriterOrderSurvivesBackwardPhysicalStep`.
- I7.3 Read-then-write causality: if client A observes event X (hlc h) and then appends Y with causal_floor >= h, then hlc(Y) > h. Gate: `JournalContract.KeeperAssignsHlcAboveCausalFloor`.
- I7.4 A new incarnation of a writer MUST sort after every event of its previous incarnation. The Keeper MUST reject an append whose incarnation is below the highest it has seen for that writer. The only exception is a writer of a story abandoned as total loss under I4.15. Gate: `JournalContract.OlderIncarnationIsRejected`.
- I7.5 Two Keepers serving one story (a Route lists several keepers for partitioning) MUST NOT both assign hlc for the same writer. Writer to Keeper affinity is `Acquisition.assigned_keeper`, stable per (writer_id, epoch); a Keeper MUST reject an append from a writer not assigned to it with FAILED_PRECONDITION and current_route. Gate: `MetadataStoreContract.AssignedKeeperStableWithinWriterEpoch`, `JournalContract.UnassignedKeeperRejectsWriter`. Preferred Keeper is a first-assignment hint resolved against the committed Route. HONORED uses an eligible initial hint, NOT_IN_ROUTE discloses a stale hint, and RETAINED discloses existing affinity precedence. Release, expiry and takeover MUST NOT move a surviving assignment; absent hints have absent results. Removed owners retain I4.11's floor-qualified modulo remap. A6 re-homing is a separate dynamic-only follow-up requiring a confirmed terminal fence and destination observeFloor of the old owner's committed ceiling; static mode lacks that ceiling and cannot offer this migration. Expiry is not owner-fence proof.
- I7.6 Legacy timestamp ordering guard retained for the Clock port: `ClientClock.StrictlyIncreasesEvenWhenRawStepsBackward` in `client/cpp/tests/clock_test.cpp` (origin/visor-clock-exchange).

## 8. Clock contract

`Clock::now() -> TimeReading{physical_ns, uncertainty_ns optional, status}` with status Synced, Unsynced or Unavailable (`include/chronolog/clock.h`).

- v1 bound (M6): read with ntp_adjtime(2) in read-only mode (modes = 0, unprivileged). maxerror is in microseconds; bound_ns = maxerror x 1000, which already includes the kernel's drift growth between disciplining updates. Synced iff the call succeeds, STA_UNSYNC is clear and bound_ns <= cap (default 1 s); then uncertainty_ns = bound_ns; otherwise Unsynced with no bound; a failing call is Unavailable. Services use `src/chrono-common/clock/KernelClock`; client/cpp carries its own twin (section 11).
- Unsynced and Unavailable MUST carry no finite bound: `uncertainty_ns` is absent. An absent bound means unknown, never zero.
- `Clock::tick() -> Hlc` for a local event, `Clock::observe(Hlc) -> Hlc` merges a remote HLC with the standard HLC rule, `Clock::uncertainty()` returns the last bound.
- No ML in v1. A learned predictor MUST NOT shrink the bound until residual coverage is validated.
- `chronolog.internal.v1` Cluster.ReadClock returns the Visor's monotonic authority tick for a Cristian round-trip estimate (offset = authority_tick_ns + RTT/2 - t1). That tick is kept separate from CLOCK_REALTIME and from the chrony bound. RTT uncertainty MUST NEVER replace physical uncertainty, and ReadClock MUST NOT be used by the Keeper to assign hlc. It is not in `chronolog.v1`; it can be promoted later additively. Writers without chrony report Unsynced physical time.
- Legacy Cristian exchange with the Visor (`client/cpp/include/ChronoClock.h`, origin/visor-clock-exchange) reported uncertainty = RTT/2. That exchange is replaced by the chrony-backed Clock; the monotonic clamp and the injected TimeSource test seam are kept.

Invariants:
- I8.1 HLC MUST strictly increase per Keeper even when physical time steps backward or the source becomes Unavailable. Gate: `ClockContract.HlcMonotonicUnderBackwardPhysicalStep`, `ClockContract.UnavailableSourceKeepsHlcAdvancing`.
- I8.2 `observe(h)` MUST return an Hlc > h and > the last tick. Gate: `ClockContract.ObservePreservesReadThenWriteCausality`.
- I8.3 A Synced reading MUST have a finite bound; an Unsynced or Unavailable reading MUST NOT. Gate: `ClockContract.UnsyncedAndUnavailableHaveNoFiniteBound`.
- I8.4 The HLC logical counter MUST reset to 0 when physical advances and MUST increment otherwise. Gate: `ClockContract.StandardHlcLogicalTick`.
- I8.5 The Keeper MUST assign hlc = max(local physical, last assigned, client causal_floor) with tick. Gate: `JournalContract.KeeperAssignsHlcAboveCausalFloor`.
- I8.6 A causal_floor far in the future MUST NOT be accepted blindly. The Keeper MUST reject an item whose causal_floor.physical_ns exceeds local physical by more than a configured skew limit (default TBD) with INVALID_ARGUMENT. Gate: `JournalContract.AbsurdCausalFloorIsRejected`.
- End-to-end gate kept after the port: `tests/end-to-end/clock-skew/clock_skew_harness.sh` (origin/visor-clock-exchange), asserting that the absolute error of the measured offset is at most the reported uncertainty plus 2 ms slack (`kSlackNs = 2'000'000` in `tests/integration/visor/clock_skew_probe.cpp:31`; the harness runs as ctest `visor.clock_skew`).

- I8.7 `Hlc.physical_ns` is CLOCK_REALTIME on the Keeper. HLC tolerates steps by construction (I8.1) and this keeps hlc comparable to the writer's physical field. Gate: `ClockContract.HlcMonotonicUnderBackwardPhysicalStep`.

Physical acceptance policy (M6, RFC-A). The policy constants A (acceptance window, default 15 s), S (the causal floor skew limit of I8.6, default 60 s), D = S + reserve_ahead (default 61 s), the uncertainty cap (default 1 s) and a policy version are fixed when the Catalog is created; Register returns them and a process configured differently refuses to start (`MembershipContract.MismatchedPolicyRefusesRegistration`). Per event: p = physical_ns; u = uncertainty_ns when Synced and u <= cap, else the event is unbounded and u = 0; lo = p - u; hi = p + u, computed with overflow checks (an unrepresentable interval is INVALID_ARGUMENT, `JournalContract.UnrepresentableIntervalIsInvalidArgument`).
- I8.8 Acceptance clock. L lives inside the Keeper's HLC core: L = max(CLOCK_REALTIME, previous L), raised only by I4.8. `Clock::assignChecked(floor, interval)` runs in one critical section of the core: compute the candidate hlc from max(L, floor, last), including any logical overflow carry; if candidate.physical - L > D raise L to candidate.physical - D; test I8.9 against that final L; commit the candidate only if the item passes; return the hlc with that L. The Keeper calls it under the writer lock and holds the lock until the event is registered pending or visible. Hence L <= hlc.physical <= L + D for every accepted event. On restart L = max(CLOCK_REALTIME, restart hlc.physical - reserve_ahead, R + A), R the highest physical frontier ever reported (persisted beside the HLC reservation). Gates: `ClockContract.AssignCheckedIsAtomicWithTheFinalAcceptanceClock (TSAN)`, `JournalContract.PhysicalCheckOrderedBeforeInsert (TSAN)`, `JournalContract.HlcLeadOverAcceptanceClockIsBounded`.
- I8.9 Acceptance rules. The Keeper MUST reject an item with lo < L - A or hi > L + S with per-item OUT_OF_RANGE, achieved UNSPECIFIED. The rejection consumes the sequence: nothing is stored, the rejection is recorded in the dedupe window and in the persisted writer checkpoint, next_sequence advances, and a retry of that EventId returns the same OUT_OF_RANGE before and after a restart. Gates: `JournalContract.BackdatedReadingIsOutOfRange`, `JournalContract.FutureReadingIsOutOfRange`, `JournalContract.OutOfRangeConsumesSequenceAndRetriesIdempotently`.
- I8.10 Physical frontier. `Journal::physicalFrontier(story)` reads L first, then takes each writer lock over the writer set as it is after that read: P = min(L - A, min lo over pending events that are not yet visible); an ACCEPTED event being upgraded to DURABLE stays visible and does not cap P. The Keeper reports max(last reported P, computed P), persists it beside the HLC reservation, never reports it above that reservation or above CP - A (I4.7), and carries it in FetchHotTrailer.physical_frontier_ns, computed before the event scan. Gates: `JournalContract.PhysicalFrontierBoundsLaterAcceptance`, `JournalContract.PhysicalFrontierSurvivesRestart`, `JournalContract.DurabilityUpgradeDoesNotLowerPhysicalFrontier`.
- I8.11 Every physical completeness claim on a story is protected across Keeper changes: survivors' own P bounds earlier claims, and a Keeper new to the Route raises L to the story's physical floor PF_X (I4.9) before admitting.
- I8.12 Policy coverage per story. The Catalog keeps a per-story physical_policy flag, true at creation iff every Keeper of the story's first Route registered with the current policy version, and cleared permanently when a Keeper without it serves the story or an archive chunk without the policy marker (ChunkIdentity.physical_policy) touches it. A Keeper's new WAL writes the policy record first; a WAL without it registers its Keeper as without policy.

## 9. The six interfaces

All live in `include/chronolog/`, are pure virtual, return `absl::Status` or `absl::StatusOr<T>`, and contain no gRPC or protobuf types. Shared value types live in `types.h`: EventId, Hlc, TimeReading, Durability, Route, Epoch, Envelope, Event, AppendItem, AppendResult, Range, Frontier, Completion, Chunk, ManifestRecord, ChunkReceipt, WatermarkReport, ReplayBatch. Thread-safety stated here and in the header comments is normative.

**Clock** (`clock.h`): now() -> StatusOr<TimeReading>, tick() -> Hlc, observe(Hlc) -> Hlc, uncertainty(), assignChecked(floor, interval) -> {hlc, L} or OUT_OF_RANGE or WOULD_EXCEED_CEILING (I8.8, I4.7), observeFloor(Hlc), which raises the HLC without assigning an event and is never ceiling-gated (I4.9). tick() and observe() are infallible: loss of the physical source sets status Unavailable on now() and HLC continues from last assigned plus logical ticks. All methods MUST be safe to call concurrently from any thread; tick and observe serialize on one atomic or mutex; now() MUST NOT block on I/O, so the chrony refresh runs on a background thread owned by the implementation. Invariants I8.1 through I8.4. Suite: `ClockContract`.

**MetadataStore** (`metadata_store.h`): createChronicle, getChronicle, listChronicles, destroyChronicle, createStory, getStory, listStories, destroyStory, acquire(story, writer_identity) -> Acquisition{story_id, writer_id, incarnation, route, assigned_keeper}, release, compareAndSetEpoch. `assigned_keeper` is a KeeperRef{process_id, endpoint}, the single Keeper for this writer in the current epoch, stable per (writer_id, epoch); AcquireResponse carries no epoch field of its own, route.epoch is the only epoch in that response; it enforces I7.5 while Route still lists every keeper. All methods thread-safe and linearizable per key. Persistence for M2 is SQLite (vcpkg port sqlite3) in WAL journal mode with synchronous=FULL; acquire and incarnation bumps MUST commit before the RPC returns. M8 replicates the same operations through NuRaft behind the same contract (RFC-B): the SQLite database is the state machine, each mutation is one CatalogCommand applied as one transaction with every id and revision assigned inside apply, snapshots are SQLite online backups, the leader serves mutations and linearizable reads only under a valid NuRaft leadership lease, followers forward unary calls, and any replica serves the watch streams from its applied state; subscribers reject a snapshot or delta whose revision or per-story epoch regresses. I9.1: the Raft log store MUST fsync before append returns. Gate: `MetadataStoreContract.RevisionSurvivesLeaderChange` (with a kill of a majority). Invariants I3.4 through I3.6, I4.2, plus `MetadataStoreContract.PersistedIncarnationStrictlyIncreases`, `MetadataStoreContract.StoryTombstonePermanence`, `MetadataStoreContract.AssignedKeeperStableWithinWriterEpoch`. Suite: `MetadataStoreContract`.

Finite acquisition grants, process-local request-id dedupe, explicit takeover/CAS and typed native AcquireRefusal details follow RFC-G (PI sign-off 2026-10-02 21:25). New grants/incarnations and terminal transitions are durable; ordered per-entry RenewAcquisitions updates only qualified-authority memory and writes no SQLite row, Raft entry, revision or feed delta. SQLite remains Raft's applied state machine. CLOCK_MONOTONIC deadlines use a separate map mutex, never held across store I/O, fsync, proposal/network waits or acquisition of the store mutex. Post-commit applied-transition observation installs live deadlines and removes terminal entries even after a lost RPC reply. A new term/fresh step-up or static restart rebuilds now+T; same-term qualification lapses and service-tick gaps pause remaining time, charging overlap once before due checks. Every sweep performs bounded progressing missing-row reconciliation; current unreleased missing tuples initialize now+T on Renew/retry/evidence, while existing due/pending entries never reset. Authority qualification is an atomic timestamped state with the applied index published at apply and peer ages sampled without the store mutex; stale samples cannot end a newer lapse. Step-up captures the applied index under the store mutex while the observer buffers transitions. Reconciliation drops durable terminal tuples; ExpireAcquisitions apply returns per-tuple outcomes, including no-ops, to clear pending marks. A partial index on acquisitions WHERE released=0 bounds scans. The completed service tick shares map serialization with Renew, evidence and sweep; a separate monitor cannot report progress for a stalled worker. Configuration MUST require 0 < acquisition_lease_min_ns <= acquisition_lease_default_ns <= acquisition_lease_max_ns and acquisition_lease_min_ns > ns(max(raft.election_upper_ms, heartbeat_timeout_ms) + release_fence_timeout_ms + lease_safety_margin_ms), with checked conversion and a service-tick gap allowance below lease_min. SDK CLOCK_BOOTTIME horizons are scheduling advice only. Client acquire is single-flight per process-owned request id: concurrent use waits or refuses, delivered ids refuse FAILED_PRECONDITION, and an identical logical acquire reuses its own unresolved id only after the prior call returned without a grant. At most one Writer per tuple exists per Client. New interface methods and factories land with G2; G1 introduces value types only.

**Membership** (`membership.h`): route(story_id) -> Route, routeState(story_id) -> RouteState {Route, ordering cut, physical floor, predecessors, archived_below, abandoned ranges} (I4.9 to I4.15), validateEpoch(story_id, epoch), registerProcess(Process{id, instance, endpoint, role}), heartbeat(id, instance). route() returns a snapshot copy taken under a bounded shared-lock section; validateEpoch() takes at most a shared lock; registration may take an exclusive lock. Invariants I4.1, I4.3, I4.5, I7.5, plus `MembershipContract.RegisterHeartbeatAndRestartFencing`. Suite: `MembershipContract`.

**Journal** (`journal.h`): append(AppendBatch{story_id, epoch, items}, durability) -> vector<AppendResult> (single-story batches, W10.13); read(story, range) -> vector<Event>; frontier(story) -> vector<Frontier>; keeperFrontier(story) -> Hlc, the Keeper-level seal even when no writer is registered, which FetchHotTrailer carries as `sealed_frontier`; physicalFrontier(story) -> int64 (I8.10). append() MUST be callable concurrently for different stories; for one writer, acceptance and hlc assignment MUST be atomic. read() holds each writer lock only for that writer's scan slice and never across the whole story. Invariants I3.1 through I3.3, I5.1 through I5.9, I6.6, I7.2 through I7.4, I8.5, I8.6, I13.8. Suite: `JournalContract`.

**TierStore** (`tier_store.h`): publish(Chunk) -> ManifestRecord; read(story, range); manifest(story) -> vector<ManifestRecord>; contiguousWatermark(story) -> Hlc. publish() MUST be thread-safe across stories and across concurrent streams of one story (legacy `ArchiveManifest::append` is mutex-serialized for this reason). Visibility is API visibility: a reader sees a chunk only through its manifest record, never by scanning files; publish() is atomic to readers in that sense. read() MUST be safe concurrently with publish(). Invariants I13.1 through I13.7, I12.2 through I12.4. Suite: `TierStoreContract`.

**Replay** (`replay.h`): read(story, range) and tail(story, position) each return a `ReplayStream` with next() -> optional<ReplayBatch> (nullopt is EOF) and cancel(). A stream has exactly one consumer; distinct streams are independent; cancel() is thread-safe, idempotent and unblocks a pending next(); destroying a stream cancels and joins owned work. The implementation MUST NOT invoke the consumer under any internal lock. Invariants I6.1 through I6.5, I6.7 through I6.9, I6.13, I7.1, I12.6. Suite: `ReplayContract`.

A Tail (I6.13) maintains a buffer and covered bound for each Route Keeper and applicable predecessor, keyed by process id and predecessor owned epoch, with the Keeper instance attached. Fetch from max(T, covered); a new source starts at T. A source's covered bound is its sealed frontier, capped at its own cut for a predecessor and the last returned event HLC when truncated (I6.12). An empty truncated answer adds no coverage. A predecessor is unconstraining only when its covered bound reaches its own cut. Buffer limits cut coverage at the first omitted event, keeping only the prefix strictly below that HLC, except that an empty source buffer always admits its first event and the archive always admits its first equal-HLC group, so the payload budget (tail_max_bytes, section 13) is soft by one payload or one tie group per share, with one warning per source per Tail. Full buffers suspend replacement calls until delivery frees room; retained coverage is reused only in the matching epoch and required predecessor instance. Any share shrink, including a joining predecessor or a newly configured archive, may discard buffered payload and reset the fetch start to T without decreasing T. At most one Catalog confirmation occurs per round, and an unchanged refusal set after a live Catalog answer needs no new confirmation; identity and instance changes supply new evidence.

Every suite MUST be declared with `GTEST_ALLOW_UNINSTANTIATED_PARAMETERIZED_TEST` so M1 is green with no implementations. Every component port MUST instantiate the suite for its implementation. A suite instantiation is a `INSTANTIATE_TEST_SUITE_P` in the component's own test directory, never inside `tests/contract/`.

## 10. Wire API rules

Public package `chronolog.v1`, file `proto/chronolog/v1/chronolog.proto`, services Catalog, Journal (Append unary, AppendStream bidi), Replay (Read, Tail server streams). Internal package `chronolog.internal.v1`, file `proto/chronolog/internal/v1/internal.proto`, services Archive (TransferChunk client stream, WatchWatermarks server stream) and Cluster (Register, Heartbeat, WatchRoutes, WatchAcquisitions, ReadClock for skew observability among cluster processes). Every frame repeats identity, total_bytes, checksum and checksum_algorithm (CRC32C default via absl/crc/crc32c.h, SHA256 optional); offsets are gapless; the checksum is over the whole concatenated data; `final` MUST coincide with byte count reached and stream EOF. The response is one ChunkReceipt{status, chunk_id, bytes, grapher_instance, receipt}. A partial stream, offset gap, byte mismatch or checksum mismatch MUST produce a receipt with a non-OK status and MUST NOT be treated as delivered. Legacy shape: `src/chrono-common/include/ChunkReceipt.h` (origin/700-watermark-feedback). Gate: `ArchiveTransferTest.PartialStreamYieldsNoReceipt`, `ArchiveTransferTest.ChecksumMismatchYieldsNoReceipt`.
- W10.5 WatermarkReport{story_id, watermark, grapher_instance, highest_receipt, pending_receipts sorted, dropped}. Every receipt from grapher_instance up to highest_receipt is written except those in pending_receipts. `dropped=true` replaces the legacy `kStoryDroppedWatermark = UINT64_MAX` sentinel and means the story is gone and every chunk for it MUST be freed. Legacy semantics: `StoryWatermarkReport` in ChunkReceipt.h. Gate: `JournalContract.DroppedStoryReportFreesRetainedChunks`.
- W10.6 Cluster.WatchRoutes sends full snapshots on subscribe and reconnect (I4.5). Heartbeat carries (process_id, instance, applied_revision, repeated per-story frontiers); a new instance replaces the old registration. A Keeper MUST send a Heartbeat immediately after applying a RELEASED update so Release latency is not bounded below by the heartbeat interval. HeartbeatRequest.admission_evidence=8 carries a bounded coalesced set of OK new-sequence admission tuples, drained per attempt without indefinite failed-delivery replay. Duplicate/pending retry, upgrade, rejection, WAL replay, archive work and empty heartbeats supply no evidence. Static and dynamic authorities validate current registered instance, assigned owner and current unreleased tuple; consume locally before heartbeat early return and strip evidence before any proposal. Evidence adds no durable renewal command.
- W10.7 Contract headers MUST NOT include generated protobuf or gRPC headers. Conversion lives in `src/chrono-<service>/adapter/`. Gate: ctest `ContractHeaders.NoGeneratedIncludes` (`tests/contract/include_guard_test.sh`) greps `include/chronolog/` for `.pb.h` and `grpcpp`.
- W10.8 Every AppendRequest MUST carry `story_id` and `epoch`; a zero epoch is whole-request INVALID_ARGUMENT. Read and Tail do not carry an epoch because Players serve any epoch's data. Gate: `JournalAdapterTest.MissingEpochIsInvalidArgument`.
- W10.9 All timestamps on the wire are int64 nanoseconds, authority_tick_ns included. No Duration or Timestamp well-known types in `chronolog.v1`, so SDKs in every language compare plain integers.
- W10.10 A oneof that is unset MUST fail whole-request with INVALID_ARGUMENT. Gate: `ReplayAdapterTest.UnsetRangeIsInvalidArgument` at the adapter level.
- W10.11 Responses echo `batch_id`. SDKs correlate on it, never on arrival order, for AppendStream.
- W10.12 Release returns ReleaseResponse{status, fenced}. Catalog commits the release, then waits up to `release_fence_timeout_ms` for the assigned Keeper's Heartbeat `applied_revision` to reach the release's revision. fenced=false means the release is committed but the Keeper had not confirmed; appends that Keeper accepted before fencing stay valid and sort before any newer incarnation. No claim of linearizable release is made. Release is idempotent by (story_id, writer_id, incarnation): a retry after a lost response returns the committed revision and the current fenced state, which is also how a client polls fence state. Gate: `MetadataStoreContract.ReleaseReportsFenceState`, `CatalogAdapterTest.DroppedReleaseRetryReturnsCommittedState`, adapter `CatalogAdapterTest.ReleaseWaitsForAppliedRevision`. Polling an EXPIRED or SUPERSEDED tuple returns its original revision/current fence state without overwriting its cause. Sweeper commits and returns without this bounded fence wait. Neither a persisted confirmation command nor a metric proves fencing.
- W10.13 Append batches are single-story. AppendRequest carries story_id, epoch, durability, batch_id and items; an item carries writer_id, incarnation, sequence, physical, causal_floor and envelope; a result carries the full EventId. A batch mixing stories is impossible by construction and the top-level current_route is unambiguous. Gate: `JournalContract.PerItemFailureDoesNotEraseSuccessfulBatchItems` on the new shape.
- W10.14 AcquisitionUpdate and ReleaseResponse carry `revision`, a persisted Catalog counter never reused across Visor restarts, and the proto comments say so; HeartbeatRequest carries `applied_revision`. There is one global Catalog revision counter. A Keeper's applied_revision is the highest R such that every update relevant to that Keeper with revision <= R is applied; irrelevant revisions are skipped implicitly, and applied_revision is scoped to the reporting process instance. WatchAcquisitions on subscribe or reconnect sends a full snapshot of the acquisitions assigned to that Keeper as of revision R, then deltas above R; a (re)started Keeper applies the snapshot, restoring every fence, before admitting any append. Gates (acquisition adapters): `AcquisitionWatcherTest.RevisionGapsAreSkipped`, `AcquisitionWatcherTest.RestartRestoresFencesBeforeAdmission`, `AcquisitionWatcherTest.AppliedRevisionIsMonotonic`. AcquisitionUpdate.termination_cause=8 preserves the original cause. A replacement instance proves a fence only after applying the snapshot through its revision; obsolete-instance reports cannot prove it. Snapshot absence need not restore a precise diagnostic cause; Catalog Renew classifies it.
- W10.15 CLOCK_STATUS_UNSPECIFIED on the wire maps to Unavailable in every adapter, never to Synced; the proto comment states it. Gate: `JournalAdapterTest.UnspecifiedClockStatusIsUnavailable`.
- W10.16 `chronolog.v1.Story` carries `Route route = 6`, filled by GetStory and ListStories with the story's current Route (none for a tombstoned story); Story.route.epoch equals Story.epoch in the same response. It is a snapshot: a client MUST still adopt current_route from any FAILED_PRECONDITION item (I4.4). Gate: `catalog_adapter.GetStoryCarriesCurrentRoute` (`src/chrono-visor/tests/`).
- W10.17 Story destroy propagation (RFC-C). `RouteUpdate` and `WatchRoutesResponse` carry `bool tombstoned = 11`: the story was destroyed at this revision and no route follows. The destroyStory or destroyChronicle transaction takes one fresh acquisition revision and inserts, per destroyed story, a tombstoned RouteUpdate into membership_history, in static and dynamic mode alike; WatchRoutes delivers history rows in both modes. Full snapshots never carry tombstones (I3.5 keeps them forever). Membership commands skip tombstoned stories: no epoch change, predecessor, drained or abandonment entry is written for one, a DrainKeeper or AbandonKeeper still commits for the Keeper's live stories, and a destroy and a route change for one story are separate commands. Subscribers apply the epoch-regression rule only to updates with tombstoned=false; a tombstoned update is applied whatever its revision, before the epoch and revision guards, never lowers the applied revision, and after it every later RouteUpdate for that story_id is ignored. `WatchRoutesResponse` carries `bool snapshot_end = 12`: exactly one message with it set follows the snapshot entries and precedes every delta, with revision R, story_id 0 and no route. A Keeper, Grapher or Player reconciles only at that marker. A story it holds data for, learned from a route at a revision at or below R and absent from the snapshot, is treated as a received tombstone with no lookup: every story live at R is in the snapshot and story ids are never reused (I3.5). A story known only above R, or only from an acquisition, an append or a FetchHot, keeps the bounded Catalog.GetStory lookup, resolved on a worker before any story gate (A4-K v2). A snapshot whose R is below the subscriber's applied revision concludes nothing, and a stream that ends before its marker reconciles nothing. Reconciliation never gates serving. A Keeper acknowledges R at the marker and each later revision after applying it, and reports it as Heartbeat applied_route_revision (amended 2026-10-03, SNAPEND, PI QA sign-off). Gates: `MembershipContract.DestroyEmitsTombstoneDelta`, `MembershipContract.NoRouteChangeAfterTombstone`, `RouteWatcherTest.TombstoneUpdateIsAppliedWithoutARoute`, `cluster_adapter.WatchRoutesEmptySnapshotHasOnlyTheMarker`, `DynamicClusterBeforeFirstStoryTest.WatchRoutesEmptySnapshotEndsBeforeFirstDelta`, `RouteWatcherTest.SlowSnapshotNeverLooksUpOrReconcilesBeforeItsMarker`, `RouteWatcherTest.StoryCreatedAfterTheSnapshotKeepsItsAppendsAtTheMarker`, `RouteWatcherTest.AcknowledgesTheSnapshotAtItsMarkerAndEachDeltaAfterIt`.
- W10.18 AcquireRequest adds optional lease_duration_ns=3, optional preferred_keeper_process_id=4, takeover=5, optional expected_prior_incarnation=6 and acquire_request_id=7. AcquireResponse keeps field 6 unused and adds AcquisitionLease lease=8, optional keeper_preference=9, refusal_reason=10, HELD remaining_ns=11, optional current_incarnation=12 and optional termination_cause=13; existing fields 2/3/4 identify a matched terminal tuple. AcquireRefusalReason is UNSPECIFIED=0, HELD=1, PRIOR_MISMATCH=2. AcquisitionTerminationCause is UNSPECIFIED=0, EXPIRED=1, RELEASED=2, SUPERSEDED=3, OWNER_REMOVED=4. KeeperPreferenceResult is UNSPECIFIED=0, HONORED=1, NOT_IN_ROUTE=2, RETAINED=3 and is absent without a hint. AcquisitionLease exports positive finite duration_ns and nonnegative remaining_ns, never an absolute host expiry. Catalog.RenewAcquisitions has bounded tuple inputs and ordered independent ItemStatus/lease/termination-cause results (W10.3); transport success is not entry success and successful renewal is not durable. Terminal tuples preserve cause; unknown tuples are NOT_FOUND, missing current-live deadlines initialize locally. AppendResult uses only RFC-F's shared field 6, with no second cause field or Journal renewal piggyback. Internal CatalogCommand preserves members 1..8 and adds ExpireAcquisitions=9, AcquireCommand=10, DestroyStoryCommand=11 and DestroyChronicleCommand=12. Authority-selected predecessor presence, resolved duration, Route/assignment, complete due sets and owner-instance/revision fence observations are revalidated at apply; ids and revisions are allocated only at deterministic apply, which samples no replica clock. Gates: unchanged `ProtoContract.AdditiveCompatibility` and `ProtoContract.NamingLint`.
- W10.19 Event stream message size (PI sign-off 2026-10-03, RECV-1, RECV-2). Every event-carrying stream message (ReadResponse, TailResponse, FetchHotResponse) holds at most 2 MiB of encoded events, counted as encoded Event bytes, except that it always holds its first event. Gates: `replay_adapter_recv.ReadDeliversEightMaximalPayloads`, `replay_adapter_recv.TailDeliversEightMaximalPayloads`, `replay_adapter_recv.HotReadDeliversFiveMiBAttributes`, `ArchiveTransferTest.FetchHotBoundsEncodedAttributesAndAdmitsOversizedFirstEvent`, `ClientChannelPolicy.DefaultReceivesAnAdmittedLargeEventAndExplicitLimitOverrides`, and the eight 1 MiB default-option Read and Tail cases in `sdk.acceptance`, `python.acceptance` and `typescript.acceptance`.

## 12. Failure model

Each failure names the behaviour and the gate. "Lost" below means lost from the system; ACCEPTED data is by definition lost on Keeper crash.

**Keeper crash.** ACCEPTED events are lost. DURABLE events are recovered from the WAL on restart and resent to the Grapher. Retained chunks whose receipt was not settled are resent. Gate: `tests/integration/keeper_wal_restart_test.sh` (ctest `keeper.wal_restart`); `JournalContract.DurableAckSurvivesCrash` (I12.1). A restarted Keeper MUST resume HLC assignment above every frontier it has ever reported: M5 persists a reserved HLC high watermark in the WAL and never reports a frontier beyond the persisted reservation (gate: `JournalContract.RestartResumesAboveReportedFrontier`). Before M5 a Keeper restart is a new Keeper instance and all its ACCEPTED data is gone by definition. A Read spanning the crash reports laggards until writers resume. Writers MUST re-acquire; the new incarnation sorts after the old one (I7.4). A Tail spanning a crash retains its frontier and discards the restarted source's buffer. Gap-free continuation under I6.13 requires WAL reservation preventing frontier regression; a Keeper without a WAL does not meet this restart rule, and I6.8 separately permits ACCEPTED loss. Writers that must re-acquire after the crash use `takeover=true, expected_prior_incarnation=their own prior incarnation`, with one logical request id reused through retries. A matching current live row can be atomically superseded; an intervening holder refuses PRIOR_MISMATCH. This explicit self-recovery avoids HELD for a full lease without weakening I7.4, WAL reservation or assignment/fence/floor rules. A restart with no prior-incarnation checkpoint follows the Writer crash policy. A generic not-registered rejection alone is not proof of Keeper crash or EXPIRED; classify through Catalog as section 6 specifies. The successor accepts future operations, with prior uncertain operations requiring explicit reconciliation. Re-homed smoke/WAL gates preserve exact ids/HLCs, actual fsync receipts and post-restart frontier ordering.

**Grapher crash.** Receipts are scoped to a Grapher instance; a new instance has a new `grapher_instance` and new numbering. A Keeper MUST NOT settle a pending receipt with a report from another instance (I12.2). Re-homed legacy guards: `JournalContract.ReceiptFromAnotherGrapherInstanceIsNotSettled`, `KeeperRetention.RestartedGrapherSettlesAResentChunkBelowTheKnownWatermark`, `KeeperRetention.DelayedReportFromTheSameGrapherDoesNotUndoANewerOne`. W is recovered from the per-Grapher manifest (`ArchiveManifest::deriveWatermarks`, origin/archive-file-manifest). Contract gates: `TierStoreContract.ManifestRestoresContiguousWatermark`, `JournalContract.ReceiptFromAnotherGrapherInstanceIsNotSettled`.

**Interrupted chunk stream.** A stream that ends without an OK ChunkReceipt MUST be treated as not delivered; the Keeper MUST mark the chunk send-failed and keep it readable and resendable (I12.3). Re-homed legacy guard: `KeeperRetention.MarkSendFailedKeepsChunkReadableAndResendable`. Contract gate: `ArchiveTransferTest.PartialStreamYieldsNoReceipt`. A receipt whose byte count differs from what was sent MUST be treated as a failed send.

**Receipt without persistence.** A covering W alone MUST NOT settle a pending receipt (I12.4). Re-homed legacy guards: `KeeperRetention.ChunkAckedUnderACoveringWatermarkWaitsForItsReceipt`, `ArchiveWatermarkTest.ReceiptStaysPendingUntilTheChunkIsWritten`, `ArchiveWatermarkTest.WatchReflectsPublishAndDroppedStory`, `ArchiveTransferTest.AFailedPublishReturnsNoReceiptHoldsTheWatermarkAndNeverReusesTheNumber`. Contract gate: `JournalContract.CoveringWatermarkAloneDoesNotSettleReceipt`.

**Keeper shutdown.** The Keeper MUST hand unshipped chunks to extraction while it still runs, resend chunks with no receipt, and wait up to `shutdown_confirm_timeout_secs` (legacy default 150, `conf/default_conf.json.in` on origin/700-watermark-feedback) for the Grapher to confirm (I12.5). Re-homed legacy guards: `KeeperRetention.ShutdownWaitEndsWhenTheGrapherConfirmsEveryChunk`, `KeeperRetention.ShutdownWaitSendsAgainAChunkTheGrapherNeverWrote`, `KeeperRetention.ShutdownWaitGivesUpAtTheTimeout`, `KeeperRetention.ShutdownSendsAgainAChunkWhoseSendFails`.

**NFS and shared file systems.** Measured by Kun Feng on ares-comp-[03-08], NFSv3, `acregmax=120` (commits 152dd5a8, 56571da5 on origin/archive-file-manifest):

| Assumption | Result | Measurement |
| --- | --- | --- |
| concurrent O_APPEND from several clients is atomic | FAIL | 66.1% record loss, 6 nodes synthetic; 3.2% in a live 2-Grapher run; 0% with 6 processes on 1 node |
| stat() reflects recent writes promptly | FAIL | 120.14 s detection lag against a 1 s poll |
| compaction is detectable | PASS | via mtime, late never lost |
| link() fails rather than clobbers | PASS | EEXIST |
| readdir sees new files | PASS | no persistent UNRECORDED |

Consequences, all normative: no two processes MAY ever append to one file on a shared file system (per-Grapher manifests, section 13). A poller MUST open() a file before deciding whether it changed; stat() on the path is not a change detector. After the fix the publish-to-visible latency measured median 0.19 s, max 1.00 s at a 1000 ms poll (commit 56571da5). Gates: `ManifestLog.EachWriterAppendsToItsOwnLog`, `TierStoreContract.IndependentWriterLogsMergeWithoutSharedAppend`, `FileTierStore.ReadersMergeNewWriterLogsAndDeduplicateInReplayOrder`, `ManifestLog.CompactionLeavesOtherWritersLogsAlone`, `ManifestLog.ATornFinalLineIsDiscardedAndEarlierRecordsSurvive`; `tests/integration/manifest_restart_test.sh` (ctest `grapher.manifest_restart`). A Player that starts before any manifest exists MUST adopt one that appears later without restart (third bug in commit 56571da5; gate: `ColdReplay.ReadOnlyViewMergesEveryWriterAndNeverScansDataFiles`, which re-homed the legacy cases for a manifest log created after startup). The archive scanner MUST exclude manifest artifacts (`ArchiveManifest::isManifestArtifact`, commit e02ef673).

**Clock loss.** When the Clock source becomes Unavailable the Keeper MUST keep assigning HLC from last-assigned plus logical ticks. Writer physical readings pass through unchanged. Physical-axis reads follow I6.10: an event's interval uses its bound when Synced, and a selected event without a finite bound makes the Read incomplete with PHYSICAL_AXIS_UNBOUNDED (I12.6, replaced by I6.10). Gates: `ReplayContract.PhysicalRangeHonorsUncertainty`, `ClockContract.UnavailableSourceKeepsHlcAdvancing`.

**Visor crash.** Catalog state is in SQLite with WAL journal mode and synchronous=FULL, so every acknowledged acquire and incarnation bump survives (section 9). Routes are static until M8 so Keepers continue serving. Acquire and release are unavailable until restart; appends under a valid epoch continue. In dynamic mode (M8) the same operations replicate through NuRaft and a Visor crash fails over to a new leader; a new leader waits a full keeper_failure_timeout_ms before declaring any Keeper failed. Gate: `tests/integration/visor_restart_test.sh` (ctest `visor.restart`).

**Keeper failover (dynamic mode).** A Keeper that stops renewing its ceiling stops admitting within ceiling_ahead_ms (I4.7). When the leader removes it from its stories' Routes (I4.9), the successor admits only above the ordering cut, Reads below the removed Keeper's own cut need it as a predecessor source until it returns and drains (I4.13, I4.14), and an operator who declares it lost uses AbandonKeeper, whose ranges stay SOURCE_FAILED forever (I4.15). Gates: the dynamic-mode integration test, ctest `dynamic_failover_integration` (`tests/integration/dynamic/`, listed in section 15).

**Player crash.** Stateless. A client's ReplayStream ends with a non-OK status; the client re-issues Read or Tail from its last position (I6.9). Gate: `ClientContract.ClientResumesTailAfterStreamError` in `tests/contract/client/`.

**Writer crash.** A restarted writer without a prior incarnation waits for committed expiry before ordinary Acquire, or uses a deliberate unconditional takeover. An RFC-F launcher holding its host-local slot lock and checkpointed prior incarnation may use `takeover=true, expected_prior_incarnation=N`; only the current row N, live or terminal, can advance. Mismatch returns PRIOR_MISMATCH/current incarnation and cannot fence a newer holder. Within one process each logical Acquire retains its at-least-128-bit random request id across a lost reply; a checkpoint or restart never restores it and always creates a fresh id for prior CAS. An unknown newer PRIOR_MISMATCH requires explicit takeover; retry of the current live grant returns the same incarnation rather than HELD. A new successful grant strictly increases incarnation, while an idempotent retry does not. I3.7/I7.4 still reject late old-incarnation appends after the Keeper has seen the release/new incarnation; before the fence they remain valid and sort before the successor. Unacked DURABLE requests remain UNKNOWN and never become fabricated acknowledgments or silent resends. Gates retain ReleasedIncarnationCannotAppend/OlderIncarnationIsRejected and add request-id/CAS recovery cases.

**Release fencing lag.** Between Catalog's commit of a release and the Keeper applying that revision, the old incarnation can still append at its Keeper. Those events are valid and sort before the next incarnation because the next incarnation is assigned the same Keeper in the same epoch (I7.5). Release reports `fenced=false` when the Keeper did not confirm within the timeout (W10.12). A Visor restart MUST NOT reuse a revision; the counter is a persisted SQLite row. The Keeper heartbeats immediately after applying the fence (W10.6). Gate: `MetadataStoreContract.ReleaseReportsFenceState`, `MetadataStoreContract.RevisionSurvivesRestart`.

**Partial manifest line.** A torn final line MUST be discarded and earlier records kept (`parseManifestLine` returns false, `ArchiveManifest.h`). Gate: `ManifestLog.ATornFinalLineIsDiscardedAndEarlierRecordsSurvive`, `TierStoreContract.TornManifestRecordIsIgnored`.

| Failure | Behavior and residual |
| --- | --- |
| Writer dies without Release | No new admission or explicit renewal; a continuously qualified Catalog eventually commits EXPIRED. New term/restart can add T; same-term lapses preserve remaining time with downtime excluded. Static destroy waits for fence proof. |
| Writer cannot reach Catalog, reaches Keeper | Keeper-carried new admission renews if Keeper reaches Catalog. RPC failure/local horizon never stops SDK dispatch. |
| Busy Writer reaches Catalog; Keeper cannot | All-Writer scheduler explicitly renews on lead schedule even during continuous append. Keeper evidence is supplementary; its failed delivery cannot alone expire this Writer. |
| Catalog unavailable/no qualified leader | No new expiry/destroy proposals; current acquisitions remain retained. Static Keeper can continue; dynamic I4.7 ceilings can exhaust. Already-enqueued durable transitions may resolve. Restart/new-term initializes fresh T; same-term requalification applies only lapse offset. |
| Authority suspend/pause/freeze/stall | CLOCK_MONOTONIC system suspend is downtime; service-tick gaps detect SIGSTOP/freezer/stalled-fsync intervals even with a valid single-replica leaderLease. Pause/qualification overlap shifts deadlines once before post-thaw due checks. Static restart installs fresh T; no downtime-only expiry. |
| EXPIRED or SUPERSEDED commits while Keeper/holder isolated | Fence propagation remains the residual window. A static holder can still obtain DURABLE acks until its Keeper applies the fence, so static destroy requires current-instance proof for both causes, including history. Dynamic destroy retains the existing new-admission island bound from ceiling_ahead_ms plus append_ceiling_wait_ms. Earlier admitted pending fsync may finish later. |
| Static owning Keeper is permanently lost | Destroy remains refused without proof. Operator restores the configured owning process_id with a fresh instance, applies WatchAcquisitions snapshot before admission, sends applied_revision >= each required release revision, then retries destroy. New registration alone, unrelated process id and timeout cannot prove a fence. |
| Keeper restart lacks a terminal diagnostic slot | Snapshot restores fences; not-registered does not identify EXPIRED. SDK uses its existing retry budget, then one authoritative tuple Renew. |
| Sleeping client resumes after another launcher | CLOCK_BOOTTIME schedules immediate renewal; local time is no admission authority. Confirmed EXPIRED allows plain conditional recovery; prior mismatch/HELD never escalates to unconditional takeover. Dispatched unreceipted operations remain UNKNOWN. |
| Hung app/leaked renewing session | SDK-object liveness can retain the lease indefinitely. RFC-F session end/idle timeout closes its Writers; no application-progress guarantee is claimed. |

Dynamic residual bounds concern new admission under existing ceilings, not fsync latency or lease safety. Static fence proof can delay destroy indefinitely until the owning process is restored. Timeout never supplies that proof.

## 13. Tiering

Tiers are ordered per deployment and get slower (RFC-I 3.1): Keeper RAM (hot, serves Tail and recent Read, bounded by retention_cap_mb); the Keeper WAL (DURABLE); `local`, the Grapher's archive_root wherever it lives, where every chunk is published; then zero or more slow tiers of kind `posix` (NFS, PFS, a second disk; `s3` is deferred). Manifest logs, snapshots and validated marks stay with `local` (I13.7); a manifest never lives on a migration target. Every Grapher and every Player that reads an archive has a tier table in its own config: an ordered list of {name, kind, root, rank} with `local` at rank 0, where a root is a path on that host. Manifest lines name a tier, its rank and its uuid, never a host path. A posix slow tier MUST honor fsync and make link and unlink durable on reply, which on NFS means a `sync` export. The Grapher is the only writer to the archive; Players are readers. Chunk windows are half-open on the HLC axis (`Chunk{start, end}` in `types.h`), replacing the legacy steady_clock windows.

- I13.1 Files MUST be published (written to a temporary name, fsync'd, renamed, then the containing directory fsync'd) before their manifest record is appended or durability is confirmed, so the manifest never names a partial or unlinked file. A crash between the two loses the trailing record, which only under-reports W. Source: `ArchiveManifest.h` ordering rule. Gate: `TierStoreContract.PublishRecordNamesVisibleCompleteFile` (fault-injected rename).
- I13.2 W MUST stop at the first gap. Gate: `FileTierStore.WatermarkStopsAtTheFirstGap`; `TierStoreContract.WatermarkCannotJumpGap`.
- I13.3 An empty window MUST be recorded (state Empty) and MUST count toward contiguity. Gate: `FileTierStore.AnEmptyWindowKeepsTheContiguousRunIntact`; `TierStoreContract.EmptyWindowMaintainsContinuity`.
- I13.4 Exempt (salvage) and Failed records MUST NOT advance W. Salvage files MUST remain readable. Gates: `FileTierStore.ExemptRecordsDoNotAdvanceTheWatermark`; `TierStoreContract.ExemptSalvageReadableWithoutAdvancingWatermark, TierStoreContract.FailedWriteNeverAdvancesWatermark`.
- I13.5 A Deleted record supersedes the publication of the same file for reads. A file removed by retention after it was persisted does not lower W. - I13.10 The WAL is truncated at receipt settlement, the same condition as I13.8, never at W alone; a durable story-drop record, written only after the story is tombstoned in the Catalog, settles every WAL record of that story. The WAL exists to survive a Keeper crash until the Grapher has written. Gate: `JournalContract.WalTruncatesOnlyAfterReceiptSettlement`, `JournalContract.WalTruncatesDroppedStoryRecords`.
- I13.11 A destroyed story's data is freed downstream (RFC-C, W10.5, W10.17). The Grapher subscribes to WatchRoutes and acts only on tombstoned entries and on stories W10.17 concludes destroyed at a snapshot_end marker: it first appends and fsyncs a `Tombstoned{story_id}` record in its own manifest log (I13.7); it refuses TransferChunk for the story with FAILED_PRECONDITION, decided from the manifest alone so the refusal survives restart; only then does it send WatermarkReport{dropped=true} to every Keeper; and on a worker (M11.7) it waits on its condition variable until the story has no pending receipts, then erases every Published and Empty-window file through Deleted records (I13.5; Empty added 2026-10-03, DESTROY-FLAKE), repeating until none remain and resuming from the manifest after a restart. The Keeper applies a tombstone from whichever arrives first, the Visor tombstone or a dropped=true report, so a Grapher that is down cannot pin retained chunks. It refuses Append for the story with FAILED_PRECONDITION under the story gate and FetchHot from the dropped set read under the membership shared lock (FetchHot never takes the gate, I4.9); it writes an fsync'd WAL record D{story_id} only once it knows the tombstone itself (a tombstoned route, absence at a snapshot_end marker under W10.17, or GetStory; never a report alone), then frees retained chunks; recovery replays D into the dropped set. A Keeper that freed on a report alone pins the story's WAL segments until reconciliation delivers the tombstone. A TransferChunk FAILED_PRECONDITION is a send failure under I12.3, never a drop signal. A drop never reports DURABLE (I5.6) and destroy stays refused while acquisitions are active (I3.6). Gates: `ArchiveTransferTest.TombstonedStoryRefusesLateChunks`, `ArchiveTransferTest.TombstoneWaitsForInFlightPublish`, `ArchiveTransferTest.RestartResumesDestroyFromManifest`, `ArchiveWatermarkTest.TombstoneProducesDroppedReport`, `TierStoreContract.TombstoneRecordRefusesLatePublish`, `JournalContract.TombstonedStoryRefusesAppend`, `JournalContract.TombstoneFreesRetainedChunks`, `JournalContract.DroppedStorySurvivesRestart`, and the destroy case of the dynamic-mode integration test (`dynamic_failover_integration`).
- I13.12 Background compaction (B3) replaces contiguous small archive files of one Grapher with one output through a single fsync'd `compact_v1` line in that Grapher's own log, so every merged manifest shows either all inputs or the output. The output is written to a temporary, fsync'd, installed by link() then unlink of the temporary, and its directory fsync'd before the line (I13.1); it carries a reserved name that orphan adoption cannot parse. The line nests the output under its own key, so an older parser fails closed, and carries the body's length and CRC32C; a line that does not match them is incomplete and retried at the next poll. Supersession is keyed by file, whichever writer's record names it, and outranks Published, Lost and Failed records of any writer: a superseded input leaves `manifest()`, reads and recovery's Lost marking, and its output takes its place with the same coverage, so W is unchanged and the line records W as a floor. Only the committing thread unlinks superseded inputs, after its own fsync of the line succeeded, and a restarted Grapher only after it fsynced its own log; a peer unlinks them only in a tombstoned story. Any manifest append or fsync failure stops compaction until the Grapher reopens. A reader of a superseded input reads the output restricted to the input's HLC window. Recovery removes an unreferenced own output only when its own inputs cover its window and validate, and rolls back an own output that fails validation while every input is intact. An eraseFile of a superseded input fails FAILED_PRECONDITION so the caller reselects. Gates: `FileTierStore.CompactionCoverageAndEveryEventFieldArePreserved`, `FileTierStore.CompactionCrashBeforeOrAfterOutputLinkNeverAdoptsTheOutput`, `FileTierStore.CompactionCrashAfterSwitchCleansInputsOnlyAfterTheOwnLogFsync`, `FileTierStore.CompactionFailedSwitchFsyncStopsCompactionAndBothRecoveryImagesAreSafe`, `FileTierStore.CompactionCleanupBelongsToTheCommittingWriterUntilATombstone`, `FileTierStore.PeerRecoveryDuringCompactionCleanupWritesNoLost`, `FileTierStore.CompactionReaderThatPlannedBeforeTheSwitchReadsIdenticalEvents`, `FileTierStore.CompactionDoesNotChangeWatermarkAcrossRestartRetentionOrOutputLoss`, `ManifestLog.AnIncompleteSwitchLineIsRetriedAtTheNextPoll`, `ArchiveTransferTest.DestroyWaitsForCompactionCleanup`.
- I13.13 Migration (RFC-I 3.3 with the round-2 corrections). A Grapher moves a file to a slower tier only through one fsync'd `migrate_v1` line in its own manifest log, so every merged manifest shows the file at exactly one effective location (I13.14). It moves only files it owns: the effective record belongs to its manifest_writer and the file name encodes it. A file is eligible when its effective record is Published or Empty, its window ends at or below W, a validated mark covers it (I13.17), no switch that is not rolled back supersedes it, it is not a compaction output whose inputs still await cleanup, it holds no claim, no in-flight publish claims its window, and its story is not tombstoned. Every background job that moves, rewrites or unlinks an archive file claims it first under the store mutex, and a file holds at most one claim. The destination is written to a temporary named `.migrate-<hex writer>.<token>`, fsync'd, installed by link() then unlink of the temporary, its directory fsync'd, and verified by reading it back from the tier and comparing length and CRC32C with the source. Every slow-tier operation is relative to the directory descriptor of the tier's availability epoch (I13.15), and nothing ever creates a tier root or an ancestor of it. The line is appended only under the store mutex, after a re-check that every eligibility condition still holds, that the attempt's claim is current, and that the attempt's descriptor is still the epoch's; otherwise the attempt removes what it wrote and appends nothing. An attempt abandoned on a hung tier never commits; when its thread returns it removes only its own temporary and a destination it created. Only the committing thread unlinks the source, after its own fsync of the line succeeded; a restarted Grapher only after it fsynced its own log and re-verified the destination. Outside a tombstoned story a Grapher sweeps, moves and unlinks only names that encode its own manifest_writer; the tombstoned-story sweep is the only cross-writer unlink. Any manifest append or fsync failure stops migration until the Grapher reopens and keeps both copies. Migration never changes a record's state, window, event count or W. After a pass that moved a file the Grapher writes its manifest snapshot to `<tier>/manifest-replica/<writer>.snap` on every slow tier. migrate_enabled is false by default: a deployment whose archive root has a Player or Grapher that cannot read `migrate_v1` MUST keep it false, and it requires a running scrubber (scrub_interval_s above zero). Gates: `FileTierStore.MigrationCrashAtEveryStepLeavesOneEffectiveCopy`, `FileTierStore.MigrationCommitRechecksUnderTheStoreMutex`, `FileTierStore.CompactionNeverTakesAMigratedOrMigratingInput`, `FileTierStore.PeerSweepNeverRemovesAnotherWritersInFlightDestination`, `ManifestLog.ForeignMigrateLineFailsTheRefreshClosed`, `GrapherTierInterleavings.MigrationThroughAReplacedRootNeverCommits`, `GrapherTiers.WorkerMigratesAndReadsIdenticalEvents`, `GrapherTiers.AnIdlePassRewritesNeitherTheReplicaNorTheStatusFile`, ctest `grapher.manifest_restart_migrated`.
- I13.14 Effective location (RFC-I 3.4). A file's effective location is the slowest tier, by rank, named by any `migrate_v1` line for that file, else `local`. It does not depend on the order in which a reader applies log and snapshot lines, and a file never moves to a faster tier. Two lines naming one file at one rank with different tiers or uuids fail the refresh closed. Every open, read, validation, duplicate comparison and unlink of an archive file resolves this location first. A reader that does not find a file where it resolved it re-syncs the manifest and follows the file's compaction successor or its new location once before it reports a failure. An erase unlinks the file at its effective location and at every faster tier where a stale copy may remain, and ENOENT counts as success at each location separately, only after the tier's marker re-read correctly through the operation's descriptor. Gates: `ColdReplay.MigratedArchiveAndReaderPlannedBeforeMigrationReturnIdenticalEvents`, `GrapherTierInterleavings.EraseThroughAReplacedRootStaysPending`, `GrapherTiers.DestroyRequeuesUnavailableTierAndCompletesAfterRecovery`. Not yet built: `ManifestLog.MultiHopLocationIsOrderIndependentAcrossSnapshotCompaction`, `PublishDuplicateOfAMigratedWindowSettles`.
- I13.15 Unavailable is not lost (RFC-I 3.5). Each tier root holds `.chronolog-tier.json`, written only by an explicit tier-add (`chronolog tier add`, and `chronolog create` for `local`), never by a boot, a probe or a migration. It carries the deployment id, the tier's name, rank and kind, a random 128-bit tier_uuid, and the file system identity seen at tier-add. A tier is available only while its marker, read through a directory descriptor of the root opened by a probe, names the expected deployment, tier, rank and uuid and the root's f_type equals the recorded one. An availability epoch owns that one descriptor: it starts with the probe that opened it and ends when a probe or an operation fails or times out, never because a later probe of a healthy root ran. A root without its marker is unavailable, never empty. A file on an unavailable tier is unreadable (I6.14) and never recorded LOST; ESTALE and EIO mark the tier unavailable and never count as missing. The Player never records LOST, and a Grapher never records LOST for another writer's slow-tier file. Every slow-tier operation runs on that tier's executor and is awaited for at most tier_io_timeout_ms; a full queue fails at once with UNAVAILABLE; nothing at Open, destroy, compaction or shutdown waits on a slow tier. A store configured with a deployment id refuses to open a `local` root whose marker is absent, names another deployment, or is not rank 0. A destroyed story's migrated files get their Deleted records whether or not their tier is available; their unlinks stay pending, the destroy worker requeues the story behind the others, and the tier status file reports pending tier deletions per story. Gates: `FileTierStore.EmptyMountPointIsUnavailableNeverLost`, `FileTierStore.AProbeOfAnAvailableTierKeepsItsEpoch`, `GrapherTiers.UnavailableDestinationKeepsTheLocalFile`, `GrapherTierFaults.Permissions`, `GrapherTierFaults.RootRenamed`, `GrapherTierFaults.ReaddedUuidRefused`, `GrapherTierFaults.ExecutorHang` (also run against `/mnt/nfs/chronolog-sprint/tiers` on dragon by `src/chrono-grapher/tests/tier_nfs_proof.sh`), `ReplayContract.UnreadableArchiveFileIsSourceFailed`. Not yet built: a slow-tier LOST verdict (the scrubber only reports a slow-tier file it cannot validate), `AtMostOneProbePerTier`, `AbandonedWorkersAreCapped`, `HungTierDoesNotBlockOpenDestroyCompactionOrShutdown`.
- I13.16 Capacity (RFC-I 3.7; contract part signed off 2026-10-03). Each tier has budget_bytes and min_free_fraction (the tighter applies) and a high and a low watermark. Usage above high, or a file older than migrate_after_s, starts migration, oldest window first, to the next tier that is available and below its own high watermark, until usage is below low; migrate_after_s MUST exceed compact_min_age_secs plus compact_scan_interval_secs, so compaction gets a pass over every run before its files move. `local` keeps hard_stop_reserve_bytes free: below it, publish of a new window and compaction output are refused with RESOURCE_EXHAUSTED, while a duplicate transfer still settles, and manifest appends, manifest compaction, migration, tombstones, destroy and scrub continue inside the reserve. The Keeper refuses new appends per item with RESOURCE_EXHAUSTED and rejection CAPACITY (I5.1, W10.1) while its retained unsettled chunk bytes exceed admission_cap_mb or the free bytes of its WAL file system fall below wal_reserve_bytes, and admits again below admission_resume_mb with the reserve restored. The refusal is decided once per request after the dedupe lookup, applies only to items that would create a new event, and consumes no sequence. No acknowledged event is lost to capacity. Gates: `ClientContract.CapacityRefusalIsRejectedAndTheSameAppendSucceedsLater` (landed with CAP-1); `JournalContract.CapacityRefusalIsDefiniteAndKeepsDuplicateResults` for the RAM and WAL journals, `KeeperRetention.AdmissionCapRefusesNewAppendsAndKeepsRetainedChunks`, `WalJournal.WalReserveRefusesBeforeTheWalFails` (Keeper cap, CAP-2); `ArchiveTransferTest.HardStopRefusesNewWindowsAsASendFailure`, `ArchiveTransferTest.HardStopStillSettlesADuplicateTransfer`, `ArchiveTransferTest.DestroyFreesSpaceAtTheHardStop` (`local` reserve, TIER-4a).
- I13.17 Bounded recovery (RFC-I 3.8 with the round-2 corrections; PI sign-off 2026-10-03). Every own line that makes a file effective (a Published or Empty record, a compact_v1 output, an adopted orphan) carries `seq`, a number strictly greater than every seq its writer ever assigned; Open starts above both the own log's highest seq and the writer's validated mark. A record without seq counts as seq 0 and is covered by any mark of its writer. A Grapher's scrubber validates every own effective Published file on `local` (on slow tiers too when scrub_slow_tiers is set) at scrub_io_bytes_per_sec, repeating every scrub_interval_s. A pass that started when the highest durable own seq was N, and validated every own effective Published file on `local` with seq at most N, replaces `manifest/<writer>.validated` with {writer, through: N} by temporary, fsync, rename and directory fsync. A file the pass skipped because it was claimed, superseded, Deleted or moved since the pass planned it does not hold the mark back; the next pass validates it where it then is. Open validates every effective Published record on `local` whose seq exceeds its writer's mark, where a writer without a mark covers nothing, so a store without marks recovers exactly as before this rule. Whatever the marks, Open validates before any cleanup the own effective records inside the window of every unreferenced own compaction output and every own committed switch output whose inputs remain. Open never validates a file on a slow tier, and it re-resolves a peer's record to its effective location before it records LOST or rolls back. LOST is recorded by Open or by the scrubber, never by a read. The scrubber records LOST, or rolls back an own switch output, only under the store mutex after a manifest re-sync and re-resolution, and a rollback first withdraws its inputs from pending unlinks; an input already claimed for unlink turns the rollback into a LOST. An unlink claim is granted only if, under the store mutex, the file is still pending unlink and still Deleted or still superseded by a switch that is not rolled back. A read of a missing or corrupt file is SOURCE_FAILED whether or not LOST was recorded (I6.14). Gates: `FileTierStore.OpenValidatesOnlyRecordsAboveTheValidatedMark`, `FileTierStore.ValidatedMarkSurvivesManifestCompaction`, `FileTierStore.RecordsPublishedDuringAScrubAreNotCovered`, `FileTierStore.SeqIsNeverReusedAfterATornTail`, `FileTierStore.OpenValidatesInputsOfAnUnreferencedOutputBeforeRemovingIt`, `FileTierStore.OpenValidatesACommittedOutputBeforeUnlinkingItsInputs`, `FileTierStore.ScrubberMarksMissingAndCorruptWindowsLostWithoutLoweringWatermark`, `FileTierStore.ScrubberRollbackWithdrawsPendingInputUnlinks`, `FileTierStore.RollbackBetweenPendingCopyAndUnlinkKeepsTheInputs`, `FileTierStore.ScrubberDuringMigrationOrCompactionCleanupWritesNoLost`, `FileTierStore.PeerOpenDuringMigrationWritesNoLost`, `FileTierStore.FileCorruptedAfterItsMarkIsFoundByTheScrubberAndFailsARead`, `ArchiveService.TheScrubWorkerWritesTheValidatedMark`.

## 14. Security boundary

Core (this repository) provides no TLS, no authentication, no authorization and no data replication: an event lives on one Keeper and one Grapher archive. Catalog metadata replication is distinct and arrives in M8 through NuRaft (section 9). Core assumes a trusted network segment.

- S14.1 The gateway, a separate deployable, does authentication, namespace ACLs at chronicle granularity, redaction of `payload` and of `gen_ai.tool.call.arguments` before append, and an audit log of every Catalog mutation. The log is immutable; nothing in core can scrub a secret after append.
- S14.2 Core MUST NOT grow an auth field in `chronolog.v1`. Identity for audit is carried by the gateway in a request header (name TBD) that core forwards into `attributes` unchanged.
- S14.3 Internal services (`chronolog.internal.v1`) MUST bind only to the cluster interface listed in configuration and MUST refuse to start on 0.0.0.0 unless `--insecure-bind-all` is set. Gate: `tests/integration/bind_guard_test.sh` (ctest `bind_guard_integration`).
- S14.4 The SDKs talk to the gateway or directly to core; they MUST NOT embed credentials.
- S14.5 Core MUST NOT log payload bytes at any level. Gate: CI grep of `src/` for `envelope.payload` inside logging macros.

## 16. Agent operating rules

- A16.3 A contract or proto change needs: an RFC drafted as markdown in the orchestrator's scratch directory outside git, review by two reviewer agents (Codex GPT-6.1 Sol and Fable 5.1 unless the orchestrator names others), and the QA sign-off of the PI, Anthony Kougkas (PI decision 2026-10-02). - A16.4 Agent reports go to the orchestrator's scratch directory outside git. Never a report, plan, summary, evidence, results or audit file in any git tree. Print only the path in the pane.
- A16.5 No human-time estimates anywhere. Progress is gated by tests.
- A16.6 No sudo. No Spack. No network installs outside vcpkg's binary cache.
- A16.7 Ports happen in place inside `src/chrono-*/`, `client/cpp/` (including `client/cpp/context/`), `client/python/`, `client/typescript/` and each separately owned `plugins/<name>/`. - A16.9 Agents MUST NOT write the construction "[noun] - [parenthetical clause]" with a dash as a clause separator anywhere.
- A16.10 Walking-skeleton order governs service ports: Visor Catalog, then Keeper Journal, then compose. The domain-class order underneath is: common domain and client Clock/identity, player pure split and merge, common TierStore and manifest with grapher, keeper Journal and WAL, visor, player service, client/cpp, client/python.
- A16.11 An agent that finds a rule in this file wrong reports it in its report file with the reason and proceeds as written. It does not deviate.
- A16.12 Measurements are recorded in the slice merge or issue that introduces the claim, naming hardware, build type and commit. No evidence or results directories in git. ## 18. Non-goals

- Semantic memory, embeddings, retrieval or any query beyond time range and tail.
- Latency or throughput claims of any kind without a measurement recorded in the slice merge or issue that makes the claim, naming hardware, build type and commit.
- Cryptographic or tamper-evident receipts. A ChunkReceipt is a counter and a transfer checksum (CRC32C by default), not a proof against a malicious Grapher.
- TLS, authentication, authorization, or replication in core (section 14).
- Dynamic ownership changes before M8 (section 4).
- ML-based clock bounds in v1 (section 8).
- Preserving the legacy client protocol, Thallium wire format, or Spack packaging.
- Multi-Keeper write replication for one writer (I7.5). A Route may list several Keepers for partitioning, never for redundancy, in v1.
