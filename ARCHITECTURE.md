# ChronoLog Architecture Specification

This file specifies ChronoLog 4.0: its data model, its contracts, its failure behaviour and the tests that enforce them. Normative words MUST, MUST NOT and SHOULD are used in the RFC 2119 sense. Every invariant names the test that enforces it. Every number cites a file path or commit, or is marked TBD.

Contract headers referenced below are the ones in `include/chronolog/` and the two proto files in `proto/`. Where this document and a header comment disagree, the header is wrong until an RFC says otherwise, and the change that notices MUST fix the header.

## 1. Authority and change process

1. This file is the specification of ChronoLog and the sole authority for its behaviour. Where code, a header or proto comment, a document under `docs/` or a commit message disagrees with it, this file wins and the change that notices fixes the other.
2. Sections 3 through 10 and section 15 are the contract. A change to them is a contract change: it MUST go through an RFC, review by two reviewers, and the PI's QA sign-off before merge (A16.3). The durable record of an RFC is the diff to this file plus the merge commit message.
3. A change to sections 11 through 14 or 16 through 18 is an editorial change. One reviewer suffices.
4. An unresolved point is written as a line starting `OPEN:` with both options and a pick. The change that resolves it replaces the line with the rule and cites the merge; in sections 3 through 10 and 15 that change is a contract change. There are none at present.
5. No line MAY state a measurement without a path or commit. A claim without a source is marked TBD and is not an invariant.
6. This file lives at the repository root and is the only normative architecture document. `docs/architecture.md` is a map of it for new engineers and carries no rules of its own. Design notes, RFC drafts, reports and plans stay outside the repository.
7. Test names in this document are normative. Renaming a test named here is a contract change.
8. Reading an invariant id: I = data and behaviour invariant (sections 3 through 9, 12, 13), W = wire rule (section 10), M = module rule (section 11), S = security rule (section 14), A = engineering rule (section 16). Commit messages cite these ids (A16.8). A retired id is never reused.
9. ChronoLog 4.0 is a rewrite of the legacy ChronoLog code base; section 17 records what it removed and where the legacy semantics went.

## 2. Glossary

- **Chronicle**: a namespace of stories. **Story**: one append-only log identified by `story_id`.
- **story_id**: uint64 assigned by Catalog. Never derived from names. Legacy derived it as CityHash64(chronicle+story), which collides on ("a","bc") versus ("ab","c") (`src/chrono-common/include/ArchiveManifest.h`, origin/archive-file-manifest). That derivation is forbidden.
- **writer_id**: uint64 assigned by Catalog at acquire. **incarnation**: uint64 persisted per writer identity, strictly increasing on every re-acquire. **sequence**: uint64 per (writer_id, incarnation), starts at 1, gapless.
- **EventId**: (story_id, writer_id, incarnation, sequence). The identity of an event. Equality of EventId is equality of events. `include/chronolog/types.h`.
- **HLC**: hybrid logical clock {int64 physical_ns; uint32 logical}. Keeper-assigned on accept.
- **causal_floor**: the maximum HLC a client has observed from any append result or read. Sent on every append item.
- **physical time**: the writer's CLOCK_REALTIME reading in ns, with an optional uncertainty bound and a clock status.
- **Durability**: ACCEPTED (Keeper RAM) or DURABLE (fsync'd Keeper WAL). Only DURABLE is an ack. UNSPECIFIED in a request means DURABLE and is never an achieved level.
- **Visor**: the process hosting Catalog and Cluster. **Keeper**: ingestion and WAL, hosts Journal. **Grapher**: tiering and archive, hosts TierStore publish. **Player**: hosts Replay.
- **Epoch**: per-story ownership version. A Route is valid for exactly one epoch.
- **Route**: {epoch, keepers, grapher, player} for a story. **KeeperRef**: {process_id, endpoint}, the one Keeper identity used by Route.keepers and Acquisition.assigned_keeper; internal subscriptions use process_id alone.
- **Pending-fsync HLC**: per writer, the HLCs assigned to DURABLE events whose fsync has not completed. Read only under that writer's lock.
- **Chunk**: a half-open HLC window [start, end) of one story's events, the unit of Keeper to Grapher transfer and of archive publication. Identified by a string `chunk_id` unique per Keeper.
- **Revision**: a monotonically increasing number on every AcquisitionUpdate, a persisted Catalog counter in SQLite that is never reused across Visor restarts. Keepers report `applied_revision` in Heartbeat. **fenced**: the per-item bool a Release returns, true iff the assigned Keeper applied the release revision within the fence timeout.
- **Receipt**: a Grapher-assigned number for one delivered chunk, scoped to a Grapher instance string. Delivery is not persistence.
- **W (persisted watermark)**: per-story end of the longest contiguous run of persisted windows from the story's earliest recorded window. Monotonic within a live story generation; a tombstone ends the generation.
- **E**: the Keeper's eviction boundary. Invariant E <= W.
- **Salvage chunk**: a chunk written outside the contiguous timeline. Watermark-exempt. Readable, never advances W.
- **Manifest**: the archive's append-only record of published files, one log and one snapshot per Grapher. `ManifestRecord.manifest_writer` names the Grapher instance that owns a log; it is distinct from the event `writer_id`.
- **Frontier (sealed, exclusive)**: for writer w assigned to Keeper k, an HLC F with the sealed-prefix property: every event of w with hlc < F is visible to reads and no event of w with hlc < F will ever be ingested. That property is the whole definition. With mixed durability a pending DURABLE event caps F below ACCEPTED events that are already visible. All writers on one Keeper share that Keeper's sealed frontier.
- **Completion**: the trailing message of a Replay.Read stream stating complete, frontier and laggards.
- **Gateway**: the out-of-core process that does authn, ACLs, redaction and audit. Not part of this repository's core.
- **Contract**: one of the six pure-virtual C++ interfaces in `include/chronolog/`.

## 3. Data model and the three time fields

Every event carries exactly three time-related fields. None substitutes for another.

| Field | Who assigns | Type | Use |
| --- | --- | --- | --- |
| physical | writer, at creation | TimeReading{physical_ns int64, uncertainty_ns optional uint64, status} | Range queries on wall time, auditing, OTel alignment |
| hlc | Keeper, on accept | Hlc{physical_ns int64, logical uint32} | Total order and causality |
| identity | Catalog (ids) and writer (sequence) | EventId | Deduplication, per-writer order, retry |

Every stored and streamed Event carries `durability`, the achieved level (ACCEPTED or DURABLE), so readers can apply I6.8. Envelope fields, all optional: `content_type` string; `payload` bytes, max size configurable, default 1 MiB, enforced at the Keeper; `trace_id` bytes(16) and `span_id` bytes(8) carrying W3C trace context; `attributes` map<string,string> for OTel GenAI keys (gen_ai.agent.id, gen_ai.conversation.id, gen_ai.tool.call.id, gen_ai.operation.name), MCP request ids, and A2A task_id, context_id, message_id; `kind` string, an open set naming what the event is (for example observation, action, result, message, decision, artifact, metric); `actor` string naming who produced it (an agent, a human or a program); `links`, each {`type` string, target EventId, optional target hlc}, with an open set of types (for example caused-by, replies-to, derived-from, supersedes), within the limits of I3.9. Key names follow the OTel GenAI semantic conventions (gen-ai-agent-spans), the A2A specification proto and the newest dated MCP schema, never the 2024-11-05 one.

Invariants:
- I3.1 An event MUST carry a complete EventId (all four fields non-zero) before the Keeper accepts it. story_id and epoch come from the request, writer_id, incarnation and sequence from the item (W10.13). Gate: `JournalContract.RejectsIncompleteEventId`.
- I3.2 A payload above the configured maximum MUST be rejected per item with INVALID_ARGUMENT in the item status, never truncated. A trace_id not exactly 16 bytes or a span_id not exactly 8 bytes, when present, MUST be rejected the same way. Gate: `JournalContract.PayloadAndTraceContextValidation`.
- I3.3 The Keeper MUST NOT modify physical time. It MUST assign hlc. Gate: `JournalContract.EnvelopeAndPhysicalReadingRoundTrip`.
- I3.4 Story and chronicle names map to ids in Catalog only. No component MAY compute an id from a name. Gate: `MetadataStoreContract.AssignedIdsDoNotAliasConcatenatedNames`.
- I3.5 Tombstones are identity tombstones: a destroyed story_id never returns and Catalog keeps its tombstone forever; the name may be reused by a new story with a new story_id. Gate: `MetadataStoreContract.StoryTombstonePermanence`.
- I3.6 Destroying a chronicle tombstones every story in it. Destroy of a story or chronicle MUST materialize its authority-selected due acquisitions before checking active rows and MUST refuse with FAILED_PRECONDITION while any acquisition remains active. In static mode it MUST additionally refuse while any EXPIRED or SUPERSEDED termination, including relevant historical incarnations, lacks applied_revision at least its original release revision from the owning process's currently registered instance. Registration alone is not fence proof; a replacement instance proves it after applying the WatchAcquisitions snapshot through that revision. Materialized expiry commits even if destroy is refused; no partial chronicle tombstone is allowed. Gates: MetadataStoreContract.ChronicleTombstonePermanence, DestroyRefusesActiveAcquisitions, DestroyMaterializesLeaderDueSet, DestroyRefusalCommitsMaterializedExpiry, StaticDestroyRequiresConfirmedExpiryFence and StaticDestroyRequiresConfirmedSupersessionFence.
- I3.7 Release fences the incarnation: once (writer_id, incarnation) is released, the Keeper MUST reject every later append carrying it with FAILED_PRECONDITION, and a release carrying an older incarnation MUST NOT release a newer one. Gate: `MetadataStoreContract.OldReleaseCannotReleaseNewIncarnation`, `JournalContract.ReleasedIncarnationCannotAppend`.
- I3.8 Every acquisition has a finite liveness-only lease. Omitted duration uses acquisition_lease_default_ns=300000000000; supplied positive duration clamps to the configured min/max. Invalid duration, empty preference, zero expected prior, invalid request id or checked arithmetic overflow MUST fail before mutation. Expiry apply checks the current unreleased tuple; terminal cause and original global release revision are idempotent and renewal MUST NOT revive a terminal acquisition. Acquire request ids have at least 128 random bits, are process-local retry ids of at most 128 UTF-8 bytes, and MUST NOT enter client checkpoints. Matching current-live retry preserves the grant and deadline; changed inputs refuse INVALID_ARGUMENT. Plain Acquire refuses HELD; conditional plain Acquire requires the exact terminal prior; takeover with expected prior is CAS, and a mismatch returns PRIOR_MISMATCH/current incarnation without mutation. Restart uses a fresh-id prior CAS. Same-id terminal retry identifies the matched incarnation and original cause, or PRIOR_MISMATCH/current when a successor exists. Same-term authority lapses and service gaps preserve remaining time rather than granting a fresh duration. Gates: `MetadataStoreContract.EveryAcquisitionHasAFiniteLease`, `LeaseRequestUsesDefaultAndClamps`, `RetriedAcquireAfterLostReplyReturnsTheSameGrant`, `SameIdTerminalRetryReportsCauseAndMatchedIncarnation`; enforcement gates, all in `MetadataStoreContract`: `ExpiryCommitChecksCurrentIncarnationAndUnreleased`, `ExpiredReleaseRetryReturnsOriginalRevision`, `SelectedExpiryCannotAcknowledgeRenewal`, `RenewalBeforeExpirySelectionPreventsExpiry`, `RenewalAtDeadlineSelectsExpiry`, `RequestIdRejectsChangedInputsWithoutMutation`, `UnexpiredLeaseRefusesSupersessionWithoutTakeover`, `ConditionalAcquireRequiresCurrentTerminalIncarnation`, `CompareAndSwapTakeoverRequiresCurrentPriorIncarnation`, `PriorMismatchReportsCurrentIncarnation`, `ConditionalRecoveryCannotTakeOverANewerHolder`, `ExplicitTakeoverRecordsSuperseded`, `SameIdRetryPreservesTupleWhenExpiryCommitsBeforeSample`, `RestartRetainsDurationAndTerminalCause`, `StaticSuspendOrRestartExcludesDowntime`.
- I3.9 `kind`, `actor` and `links` travel in the envelope, are stored and streamed with the event unchanged, and the Keeper gives them no meaning. They are optional, and a request that sets none behaves as before. An actor does not replace the writer: sequence, dedupe and incarnation fencing stay per writer_id (I5.4, I5.5, I3.7), and an actor is a claim by the writer, not an authenticated identity (S14.6). The Keeper validates them per item as I3.2 does, rejecting with INVALID_ARGUMENT in the item status and never truncating: `kind` at most 64 bytes, `actor` at most 256 bytes, a link `type` at most 64 bytes, and at most 16 links per event. A link `type` MUST be non-empty and its target EventId complete (all four fields non-zero, as I3.1), else the item is INVALID_ARGUMENT. A `kind` or a link `type` beginning with `chronolog.` is reserved to core: the Keeper MUST reject it per item with INVALID_ARGUMENT until this document defines it. Attribute keys are not reserved, because plugins already write `chronolog.*` keys. A link carries its target EventId and optionally the target's hlc. kind, actor, attributes and links are the indexed fields: they, and only they, may appear in a predicate (I6.17). Indexed means selectable by a predicate evaluated over the range being read; it does not mean a secondary index over values (section 18). Gates: `JournalContract.EnvelopeKindActorLinksRoundTrip`, `JournalContract.EnvelopeFieldLimitsRejectPerItem`, `JournalContract.ReservedKindAndLinkTypeAreRejected`, `TierStoreContract.EnvelopeKindActorLinksSurviveTheArchive`, `WalJournal.PreChangeSegmentReplaysWithKindActorAndLinksEmpty` (a segment written before the fields existed replays with them empty).
- I3.10 A link is a plain reference. Acceptance never depends on its target: the Keeper does not look the target up and does not require that it exists, is visible, lives in the same story or has the hlc the link names, and an item whose links point at events that never exist is accepted and stored like any other. Gate: `JournalContract.LinkTargetNeedNotExist (to build)`.
- I3.11 Names and paths. A chronicle name MUST NOT contain `/`. A story name MAY contain `/` and MUST NOT begin or end with one or contain an empty segment (`//`). No segment of a chronicle or story name MAY begin with `@`: such segments are reserved to core (phase 3 places branches under them). createChronicle and createStory refuse a name that breaks these rules with INVALID_ARGUMENT in the ItemStatus (W10.3). The rules apply at creation; an object created before them keeps its name and stays readable by id. The path of a story is `<chronicle name>/<story name>`, and with these rules a path names at most one live story. A prefix is one or more whole segments without a leading or trailing `/`; an empty or malformed prefix is INVALID_ARGUMENT. A prefix never matches a story with a segment beginning with `@` unless the prefix itself names that segment. Gates: `MetadataStoreContract.NameRulesMakeStoryPathsUnique (to build)`, `MetadataStoreContract.ReservedSegmentsAreRefused (to build)`.

## 4. Ownership epochs

Every story has one owning Route per epoch. Every AppendItem carries (story_id via EventId, epoch).

- I4.1 `Membership::validateEpoch(story_id, epoch)` MUST reject a stale epoch. A stale epoch is never a gRPC error: Append returns gRPC OK, the affected items carry FAILED_PRECONDITION in their ItemStatus plus `current_route`, and because a batch is single-story (W10.13) a stale request-level epoch rejects every item and the AppendResponse also carries a top-level `current_route`. No trailing-metadata encoding. Gate: `MembershipContract.StaleEpochRejection`; `JournalContract.StaleEpochReturnsCurrentRoute`.
- I4.2 Epochs MUST strictly increase per story. `MetadataStore::compareAndSetEpoch` is the only mutator and MUST reject a desired epoch that is not greater than the current one. Gate: `MetadataStoreContract.EpochCompareAndSet`.
- I4.3 In static membership mode (`membership_mode: static`, the default) epochs are static: every story is epoch 1 and routes are fixed from configuration. Dynamic mode changes epochs only under I4.7 to I4.15. Implementations MUST still carry and validate the field, so a client is correct in either mode. Gate: `MembershipContract.StaticEpochIsOneAndValidated`.
- I4.4 A client receiving a FAILED_PRECONDITION item MUST adopt the returned Route and retry with the same EventIds. Retries are idempotent (section 5). Gate: `ClientContract.ClientRetriesOnStaleEpochWithSameEventIds` in `client/cpp/tests/`.
- I4.5 Cluster.WatchRoutes MUST send a full snapshot on subscribe and on reconnect. A Keeper MUST NOT serve a story before it has a Route for it. Gate: `MembershipContract.UnknownStoryCannotValidate`.

- I4.6 A Route change MUST NOT invalidate an in-flight Keeper to Grapher chunk stream; the stream completes under the old epoch. Chunks are immutable once sealed and the receipt protocol tolerates resends. Gate: `ArchiveTransferTest.StreamCompletesAcrossEpochChange`.

Dynamic mode (RFC-B). All of the following hold only when `membership_mode: dynamic`; static deployments are unchanged. Defaults, fixed in the Catalog policy at creation (`src/visor/dynamic/MembershipState.cpp`): ceiling_ahead 5000 ms, physical_ahead 2000 ms, B_L (acceptance_budget) 3 s, B_H (hlc_budget) 30 s.
- I4.7 Ceilings. Every Keeper instance holds a ceiling pair committed in the Catalog, C (an Hlc) and CP (physical ns). It MUST NOT assign an hlc >= C, report a sealed frontier above C, or report a physical frontier above CP - A (I8.9). Cluster.ExtendCeiling grants only to the current registered instance of a process, only when the request's applied_route_revision is at or above that process's fence revision (the revision of the latest route change of any story whose old or new Route lists it), and monotonically per process across instances: C = max(wanted_hlc + ceiling_ahead, previous C), CP = max(realtime + B_L + physical_ahead, previous CP). A refusal for the revision condition returns the RouteUpdates the Keeper is missing, read at the leader. An append that would reach C releases the story gate, its writer lock and the clock core, waits for an extension or a route application for at most append_ceiling_wait_ms, re-enters from validation, and fails UNAVAILABLE on timeout. Register by a new instance revokes every earlier instance of that process and returns the floor pair (max C, max CP); if the new instance did not recover the earlier instance's WAL, the same command commits an epoch change for every story the earlier instance served with it as a predecessor. Gates: `JournalContract.NoAssignmentAtOrAboveCeiling`, `JournalContract.CeilingWaitDoesNotBlockRouteApplication`.
- I4.8 Transition budget. No raise of a Keeper's acceptance clock L (I8.8) puts it more than B_L ahead of its CLOCK_REALTIME, and no observed floor puts its HLC more than B_H ahead of it. A transition that needs more installs the new Route but defers admission at the new epoch for that story until realtime catches up, answering UNAVAILABLE meanwhile. Gate: `JournalContract.TransitionsCannotRatchetTheAcceptanceClock`.
- I4.9 Epoch change and admission gate. Route changes caused by one trigger (heartbeat silence for keeper_failure_timeout_ms, which affects availability only; or the operator's DrainKeeper, JoinKeeper, AbandonKeeper) are one CatalogCommand under one revision. For each story X it carries epoch e + 1 (compareAndSetEpoch stays the only epoch mutator, I4.2), the new Route, the ordering cut H_X = max over every instance of every old-Route Keeper of the C ever granted to it, each predecessor's own cut, and the story's physical floor PF_X(e + 1) = max(PF_X(e), min over every old-Route process of the latest CP granted to its latest registered instance); it sets the fence revision of every Keeper listed in the old or new Route. Each Keeper keeps a writer-preferring per-story gate held shared by every append from epoch and assignment validation through hlc assignment and pending or visible registration; lock order is gate, membership, shard, writer, clock core, and FetchHot, Heartbeat, the sealer and the WAL committer never take it. Applying a route update takes the gate exclusive, installs the Route and cuts, schedules observeFloor(H_X) when RouteUpdate.observe_floor is set for this Keeper (it is new to the Route or inherits remapped writers), schedules the raise of L to PF_X when it is new to the Route, releases the gate, and reports the revision applied only after every story in the command passed its exclusive section; admission at e + 1 opens when the scheduled steps are done under I4.8 and the ceiling exceeds H_X. Survivors never raise L. Gates: `JournalContract.ReassignedWriterObservesOldFrontier`, `JournalContract.RouteChangeWaitsOutValidatedAdmissions (TSAN)`, `JournalContract.NewMemberAcceptanceClockCoversTheStoryPhysicalFloor`.
- I4.10 Unlisted Keeper. A Keeper MUST reject per item with FAILED_PRECONDITION and current_route every append for a story whose applied Route does not list its process_id, checked under the gate with validateEpoch. Gate: `JournalContract.UnlistedKeeperRejectsAppend`.
- I4.11 Ordering and reassignment. Every hlc an old-Route instance can still assign for X is below its committed C, hence below H_X; every new-epoch assignment of a remapped writer is above H_X. Only writers of removed Keepers are remapped, by writer_id over the new Route's Keepers, stable per (writer_id, epoch) (I7.5); a remapped writer re-acquires (incarnation + 1), and unacked DURABLE items of the old incarnation are reported as outcome unknown, never acked and never silently resent. Gate: `ClientContract.ClientWhoseKeeperWasRemovedReportsOutcomeUnknownAndReacquires` (`client/cpp/tests/`, ctest `sdk.ClientContract.*`).
- I4.12 Retired seals. A Keeper answering FetchHot for a story at an epoch it no longer owns reports sealed frontier min(F, own cut) and physical frontier min(P, own CP - A); a current owner's trailer carries its applied epoch. Gate: `ArchiveTransferTest.RetiredOwnerSealIsCutAtTheHandoff`.
- I4.13 Predecessors. RouteState for a story carries predecessors {KeeperRef, instance, owned epoch, own cut C_k, own CP_k} for every removed Keeper instance and every revoked instance whose WAL was not recovered. FetchHotRequest carries expect_instance and expect_epoch; a Keeper answers a predecessor request only when both match, and the trailer echoes its instance. A Read whose range starts below a predecessor's own cut includes it as a source on [start, min(end, own cut)); its physical span is (-inf, max(C_k.physical, CP_k) + S). A predecessor that does not answer, or whose seal is below that bound, makes the Read SOURCE_FAILED or LAGGING_WRITERS. Gates: `ReplayContract.UndrainedPredecessorIsASource`, `ReplayContract.DeadPredecessorIsSourceFailed`, `ReplayContract.ReplacementInstanceCannotAnswerForItsPredecessor`.
- I4.14 Drain. Once its sealed frontier reaches its own cut, a retired instance ships an Empty chunk for any eventless part of [chain_end, own cut), and an instance that never held an event for the story is drained at once. It reports drained for exactly (story, instance, owned epoch) when its eviction floor reaches its own cut (I13.8); the leader removes only that entry and in the same command raises RouteState.archived_below to the cut, and the Player reads the archive over [start, max(B, archived_below)). Gates: `ReplayContract.DrainedPredecessorHistoryComesFromTheArchive`, `MembershipContract.StaleDrainReportDoesNotRemoveANewerPredecessor`, `JournalContract.RetiredKeeperDrainsWithAnAlreadyEvictedFinalChunk`, `JournalContract.WriterlessRetiredStoryDrainsAtItsOwnCut`.
- I4.15 Abandonment. Heartbeat carries per (instance, story) settlement proofs (coverage_start, settled_through), committed in batches and never above the truth. AbandonKeeper first removes the process from every Route, then replaces each predecessor entry of each of its instances with the abandoned range [settled_through of that same instance's proof, own cut) when the proof covers the instance's first event, else [Hlc{0,0}, own cut). A Keeper that was never granted a ceiling (a cluster switched from static mode) can only be abandoned as total loss: [Hlc{0,0}, +inf) on both axes, with no ordering claim for its writers. Every Read intersecting an abandoned range is complete=false with SOURCE_FAILED. The Catalog refuses any other epoch change for a story while a Keeper of its current Route has never been granted a ceiling. Gate: `MembershipContract.AbandonedRangeUsesOnlyTheSameInstanceProof`. A Tail delivers no event across an abandoned range: I6.13 caps its frontier at the range start and terminates SOURCE_FAILED when the frontier reaches that range, with complete=false. Gate: `ReplayContract.TailStopsAtAnAbandonedRange`.

## 5. Ack semantics

`enum Durability { DURABILITY_UNSPECIFIED = 0; ACCEPTED = 1; DURABLE = 2; }` in `proto/chronolog/v1/chronolog.proto`. UNSPECIFIED means DURABLE in a request and MUST never appear as an achieved success level. Default DURABLE.

- ACCEPTED: the event is in Keeper RAM and ordered. It is lost on Keeper crash.
- DURABLE: the event is fsync'd in the Keeper WAL with group commit. It survives Keeper crash.
- Only DURABLE is called an ack in any documentation, log line, metric or SDK name.

Invariants:
- I5.1 A server that cannot provide the requested level MUST reject that item with UNIMPLEMENTED (level not built) or UNAVAILABLE (level built but failing) in the ItemStatus and `achieved_durability = DURABILITY_UNSPECIFIED`. It MUST NOT return ACCEPTED when DURABLE was requested. Status codes are fixed by this file and asserted exactly by headers and contract tests: unbuilt durability UNIMPLEMENTED, built but failing UNAVAILABLE, sequence gap FAILED_PRECONDITION with the expected sequence, payload or trace-context violation INVALID_ARGUMENT, stale epoch or released incarnation FAILED_PRECONDITION, physical reading outside the acceptance window OUT_OF_RANGE (I8.9; the rejection consumes the sequence), capacity refusal RESOURCE_EXHAUSTED with rejection CAPACITY (I13.16; decided once per request after the dedupe lookup, applied only to items that would create a new event, the sequence not consumed; amended 2026-10-03, PI A16.3 sign-off). Gate: `JournalContract.NoSilentDurabilityDowngrade`.
- I5.2 A Journal without a WAL (the RAM Journal) MUST fail every DURABLE append per I5.1 with UNIMPLEMENTED; its clients MUST request ACCEPTED explicitly. Gate: `JournalContract.AcceptedIsExplicitRamReceipt` instantiated for the RAM Journal.
- I5.3 AppendResult per item MUST carry status, achieved durability, assigned hlc, EventId. Gate: `JournalContract.AppendResultCarriesAllFourFields`.
- I5.4 A duplicate EventId MUST return the original result (same hlc, achieved durability equal or higher) and MUST NOT store a second copy. Gate: `JournalContract.IdempotentRetryReturnsOriginalResult` (same id and hlc, achieved durability not lower, one stored copy); `WalJournal.AcceptedThenDurableUpgradeSurvivesCrashWithOutOfOrderSequences` (a DURABLE retry of an ACCEPTED event achieves the higher level and keeps it across a crash).
- I5.5 A gap in sequence for (writer_id, incarnation) MUST be rejected per item with FAILED_PRECONDITION and the expected next sequence in the item message. Later items of the same writer in that batch MUST also be rejected. Gate: `JournalContract.GaplessSequenceRejection`.
- I5.6 DURABLE MUST mean fsync returned success, not write() returned. An fsync failure MUST fail every item in the group with UNAVAILABLE and MUST NOT report DURABLE for any of them. Gate: `JournalContract.FsyncFailureFailsTheGroup` (fault-injected file sink). Crash gate: `tests/integration/keeper_wal/keeper_wal_restart_test.sh` (ctest `keeper.wal_restart`).
- I5.7 Legacy RAM retention (KeeperChunkRetentionStore) cannot implement DURABLE and MUST NOT be labelled as such.
- I5.8 AppendStream cancellation MUST NOT roll back accepted items. Gate: `JournalAdapterTest.CancelledStreamKeepsAcceptedItems`.
- I5.9 A batch MUST be processed in item order per writer; an item's result position equals its request position. Gate: `JournalContract.PerItemFailureDoesNotEraseSuccessfulBatchItems`.

- I5.10 The WAL commits groups adaptively: as soon as the previous fsync returns, the committer writes and fsyncs every record queued at that moment, up to group_commit_max_bytes. The knob group_commit_window_us (default 0, at most 10000) holds a group open until the window has passed since its first record or the byte bound is reached; 0 is adaptive commit. I5.6 holds in both modes. Measured with tools/bench/run.sh custom at 6bbe4575 on dragon (two NVMe disks, dev build): a nonzero window cost 10 to 46% of throughput for one writer at batch 1 and gained at most 2.6% at 64 writers with batch 64, so the default stays 0. Gates: `JournalContract.FsyncFailureFailsTheGroup` instantiated for window 0 and 1000 us, `WalJournal.WindowedGroupReportsDurableOnlyAfterSyncReturns`. PI QA sign-off 2026-10-03.

## 6. Completeness semantics

`Replay.Read(story, [start, end))` on hlc or physical time returns EventBatch messages and ends with exactly one Completion: `complete bool`, `frontier hlc`, `repeated laggards {writer_id, incarnation, frontier}`. Then EOF.

Completion also carries `IncompleteReason reason` with values LAGGING_WRITERS, PHYSICAL_AXIS_UNBOUNDED, SOURCE_FAILED, TRUNCATED. A Read sets it whenever `complete=false`, and when several apply it reports the first of SOURCE_FAILED, TRUNCATED, PHYSICAL_AXIS_UNBOUNDED, LAGGING_WRITERS (`src/player/replay/CompletionPolicy.cpp`). A Tail that ends without a failure, for example by cancel, carries complete=false and reason UNSPECIFIED, because a Tail makes no claim (I6.5).

Definition: the read is complete iff every Keeper in the story's Route answered and its sealed frontier F_k >= end, on the HLC axis. Equality is sufficient because the frontier is exclusive. The registered-writer view from WatchAcquisitions is used only to name laggards (writers assigned to a Keeper that failed or lags); a stale acquisition view therefore cannot produce a false complete. The Keeper obtains F by ticking its HLC (future assignments are > F) under the rules in I6.11; for DURABLE data F is capped at the minimum pending-fsync HLC. Idle registered writers share their Keeper's frontier and do not block completeness. A writer is registered from acquire until release or incarnation supersession. This definition is the HLC axis. An HLC frontier does not bound a writer's future backdated CLOCK_REALTIME stamps, so a physical-axis Read has its own rule, I6.10, which rests on the acceptance policy that bounds backdating (I8.8 to I8.12).

Invariants:
- I6.1 An HLC Read with some registered writer's sealed frontier below end MUST set `complete=false`, reason LAGGING_WRITERS, and list that writer in laggards. A frontier equal to end is sufficient. Laggards are the writers whose Keeper did not answer or whose sealed frontier is below end. Gate: `ReplayContract.CompletionNamesLaggardsAndEqualityIsSufficient`, `ReplayContract.CompleteWhenEveryKeeperSealReachesEnd`, `ReplayContract.IdleRegisteredWriterDoesNotBlockCompleteness`, `ReplayContract.UnknownWriterCoveredByItsKeeperSeal`.

- I6.3 A Keeper that fails to answer MUST make the reply incomplete with reason SOURCE_FAILED; a truncated answer MUST make it incomplete with reason TRUNCATED. Component gates: `ColdReplay.AKeeperThatDidNotAnswerWidensTheArchiveReadAndMarksTheReplyIncomplete`, `ColdReplay.ATruncatedAnswerMarksTheReplyIncompleteWithoutWideningTheRead`. Contract gate: `ReplayContract.FailedSourcePreventsCompleteness`, `ReplayContract.TruncatedSourcePreventsCompleteness`.
- I6.4 Events MUST be deduplicated by EventId across hot and archive sources. Component gates: `ReplayMerge.EventFromTheArchiveAndAKeeperIsReturnedOnce`, `ReplayMerge.EventsDifferingOnlyInWriterIdAreDifferentEvents`, `ReplayMerge.EventsDifferingOnlyInIncarnationAreDifferentEvents`. Contract gate: `ReplayContract.TotalOrderAndEventIdentityDeduplication`.
- I6.5 `Replay.Tail` MUST NOT claim completeness. Its Completion on orderly termination MUST have `complete=false`. Gate: `ReplayContract.TailNeverClaimsCompleteness`.
- I6.6 `Journal::frontier(story)` MUST return the Keeper's sealed frontier for every writer registered on that Keeper, including writers with zero events, and that value MUST satisfy the sealed-prefix property and nothing more; in particular it MUST NOT exceed the minimum pending-fsync HLC. When nothing is pending it exceeds every assignment. Gate: `JournalContract.HalfOpenRangeAndFrontierIncludesRegisteredWriter`, `JournalContract.SealedFrontierExceedsEveryAssignmentWhenNothingPending`, `JournalContract.DurableInvisibleUntilFsyncAndSealDoesNotPassPendingHlc`, `JournalContract.IdleRegisteredWriterDoesNotBlockCompleteness`.
- I6.7 A Read on a tombstoned story MUST fail whole-request with FAILED_PRECONDITION. A Read admitted before the tombstone that reaches an archive file removed by I13.11 MUST end complete=false with SOURCE_FAILED, never a partial result presented as complete. Gate: `ReplayContract.ReadOnTombstonedStoryFails` (first sentence); `ColdReplay.AFileRemovedByAStoryDestroyEndsSourceFailed` and `ColdReplay.ATailOverAFileRemovedByAStoryDestroyEndsSourceFailed` (second sentence).
- I6.8 `complete=true` MUST imply that every event in the range that any writer will ever produce is in the stream. A later Read of the same range MUST return the same event set for DURABLE events; ACCEPTED events may vanish on Keeper crash and the invariant says so. On the physical axis, completeness is relative to the writers' reported intervals (I8.9). Visibility: an ACCEPTED event is visible once accepted, a DURABLE event only after its fsync. Gate: `ReplayContract.CompleteReadIsStableForDurableEvents` (two Reads of one source in process; its only instantiation reopens a fake, so it proves repeatability, not crash stability); ctest `keeper.wal_restart` steps `stable-before` and `stable-after` (a complete Read through the Player before a Keeper SIGKILL and the same Read after the restart and the resend to the archive hold the same DURABLE ids, HLCs and payloads).
- I6.9 Tail resumes exclusively after `position` (hlc, EventId); the event at `position` MUST NOT be re-sent. A Position with no id is I6.23. Gate: `ReplayContract.TailResumesExclusivelyAfterPosition`.
- I6.10 Physical-axis Read (RFC-A). Selection: every event whose interval [lo, hi] (I8.9) intersects [s, e): lo < e and hi >= s (an unbounded event: s <= p < e). For a story whose physical_policy flag is true (I8.12) the sources are read on the HLC window [s - S - D, e + A + D) (saturating) and filtered by interval; for a story whose flag is false the sources' whole HLC domain is scanned and the Read is never complete. The interval test runs at the source (Keeper FetchHot with the physical range; the archive reader after decoding), and read_max_events counts only matches. A Read whose matches exceed the bound returns TRUNCATED with no claim; the SDKs split the physical range in halves recursively, read each half as an independent Read, deduplicate by EventId and report the aggregate complete iff every leaf is complete. A Read is complete iff the story's flag is true, every Route Keeper answered with the Route epoch and reported a physical frontier P_k >= e, no source failed or was truncated, no LOST window lies in the archive range, no selected event is unbounded, and no abandoned range or undrained predecessor span (I4.13) intersects [s, e) unless every such predecessor answered with its own P >= e. A selected unbounded event, or a story whose flag is false, gives PHYSICAL_AXIS_UNBOUNDED (meaning: an event in range has no finite clock bound); P_k < e gives LAGGING_WRITERS. Gates: `ReplayContract.PhysicalReadCompleteWhenEveryPhysicalFrontierPassesEnd`, `ReplayContract.PhysicalRangeHonorsUncertainty`, `ReplayContract.UnboundedEventMakesPhysicalReadIncomplete`, `ReplayContract.StoryWithoutPolicyIsNeverPhysicallyComplete`, `replay_adapter.PhysicalReadAboveTheLimitIsTruncatedWithoutClaim` (`src/player/tests/`).
- I6.11 Frontier ordering rules, all MUST. (a) Archive.FetchHot ticks F before it scans events, never after, so every event with hlc < F accepted during the scan is in the reply. (b) HLC assignment and insertion are atomic under the writer's lock, and the frontier tick happens before any per-writer lock is taken for the scan. (c) Completeness is decided over every Keeper in the Route; the Player maps registered writers to `assigned_keeper` from WatchAcquisitions only to name laggards, and a Keeper that did not answer makes the read SOURCE_FAILED with its writers listed. (d) In dynamic mode an epoch change carries the ordering cut H_X of I4.9 (the maximum ceiling ever granted to the previous epoch's Keepers, which bounds every hlc they can assign); every Keeper that is new to the Route or inherits remapped writers MUST observeFloor(H_X) before admitting at the new epoch, and survivors that inherit no writer need not. A writer's new incarnation is never admitted on a different Keeper until its old incarnation is fenced on the old Keeper. Under static epochs the persisted Catalog assigned_keeper is shared across incarnations, so both incarnations land on one Keeper and I7.4 rejects late old-incarnation appends. (e) Pending-fsync state is tracked per writer and registered in the same writer-lock critical section as HLC assignment. The scan ticks h_t first, then for each writer takes that writer's lock, scans its visible events and reads that writer's minimum pending-fsync HLC while still holding the lock. F = min(h_t, min over writers of those per-writer minima). Two conditions make this sound and are part of the rule: fsync completion makes an event visible and clears its pending entry under the same writer lock, so a scan never observes an event that is neither visible nor pending; and writer state is created under the story lock before the writer's first HLC assignment, and the scan iterates the writer set as it is after the tick, so every writer assigned before the tick is scanned. A global pending set sampled outside the writer locks is unsound whether sampled before the scan (an event assigned before the tick but registered after the sample) or after it (an fsync completing after the scan drops an unreturned event from the cap). (f) FetchHotTrailer carries the Keeper's current epoch; the Player MUST treat a trailer epoch different from its Route epoch as SOURCE_FAILED. Gates: `ArchiveTransferTest.FetchHotTicksFrontierBeforeScan`, `ArchiveTransferTest.FrontierTickOrderedBeforeInsert (TSAN)`, `ReplayContract.UnknownWriterCoveredByItsKeeperSeal`, `JournalContract.PendingFsyncRegisteredWithAssignment (TSAN)`, `JournalContract.FsyncCompletionFlipsVisibilityUnderWriterLock (TSAN)`, `JournalContract.WriterCreatedBeforeFirstAssignmentIsScanned`, `JournalContract.ReassignedWriterObservesOldFrontier`, `ReplayContract.TrailerEpochMismatchIsSourceFailed`, `AcquisitionWatcherTest.NewOwnerAdmittedOnlyAfterOldOwnerFenced`.
- I6.12 Truncated HLC Reads. A TRUNCATED HLC Read's frontier c MUST be at or below: every Route Keeper's reported sealed frontier; for every applicable predecessor whose seal is below its own cut, that seal; the end of what the Player returned; and for every source whose answer was truncated, the hlc of the last event that source returned. No LOST window may lie below c, and the Player then cuts c down to an archive record start. Every source's contribution is exclusive at c, so [start, c) is complete on its own and a continuation from c inclusive has no gap or duplicate. Gate: `ReplayContract.TruncatedReadFrontierIsACompletePrefix`.
- I6.13 Tail delivery frontier (RFC-D). Let position be the exclusive resume position and initialize `T0 = position.hlc`. T never decreases. Every required source contributes only coverage proved under its expected epoch and instance, following I6.11 and I6.12. Retained coverage is final within its instance. An instance change discards that source's buffered state and makes the current round non-advancing; refetch from T. Compute T_min as the minimum covered bound of every Route Keeper and every still-constraining predecessor. Cap it at the start of each abandoned range above T that it would cross (I4.15). If a required source has neither an eligible answer nor retained coverage, this round moves nothing. A round with no source proves no advancement. Deliver every merged hot-buffer and archive event with `T <= hlc < T_min` and `ReplayLess(position, event)`, exactly once per Tail RPC in ReplayLess order; then set `T := max(T, T_min)`. Events sharing an HLC below T_min are ordered by `(writer_id, incarnation, sequence)`; all events at `hlc == T_min` wait. Archive events obey the same bound regardless of eviction floors. Across reconnects I6.9 governs exclusive resumption from the client's last received event. If T lies in or reaches an abandoned range, end with complete=false, frontier T and reason SOURCE_FAILED after delivering any eligible prefix already queued. Any Keeper FAILED_PRECONDITION, without message matching, or a recorded archive tombstone is evidence for Catalog confirmation. Only a Catalog FAILED_PRECONDITION ends the Tail with FAILED_PRECONDITION, taking precedence over archive-tombstone SOURCE_FAILED termination, including a tombstone first discovered by the archive refresh. Previously queued eligible events may be returned before confirmation. Without confirmation, a refusing or down Keeper stalls delivery; an archive tombstone, LOST window or archive-read failure retains the existing SOURCE_FAILED behavior. A failure of the Route source for the round ends the Tail with that status; the client resumes under I6.9. A Tail never claims completeness (I6.5). Gap-free continuation across Keeper instances requires that no source's F fall below T, as provided by the WAL's frontier reservation (section 12). I6.8 permits ACCEPTED events to vanish on crash. A Keeper without a WAL does not satisfy section 12's restart rule; for it the gap-free promise holds only above T. This rule does not promise recovery of ACCEPTED data or delivery of new events assigned below T after a RAM-only restart. Gates: every `ReplayContract.Tail*` case, the Tail cases of `replay_adapter`, `replay_adapter_small_budget` and `ColdReplay`, and the `RealKeeperTail` cases, as listed in section 15.
- I6.14 Unreadable archive files (RFC-I 3.10; PI sign-off 2026-10-03). A Read whose range overlaps an effective Published archive record, as resolved from the manifest when the Read planned it and after the re-resolution of I13.12 and I13.14, whose file cannot be read at its effective location (tier unavailable, file missing, undecodable, checksum mismatch, object-store error, or no answer within the read deadline: archive_read_timeout_ms, 30000 by default, for a file on `local`, and tier_io_timeout_ms for a file on a slow tier) MUST end complete=false with reason SOURCE_FAILED, never TRUNCATED (I6.12), and MUST NOT return events of that range while claiming completeness. A file that a Deleted record retires, or whose compaction successor reads, is not a failure. A Tail delivers no event at or above the start of such a file and ends SOURCE_FAILED as I6.13 states. Gate: `ReplayContract.UnreadableArchiveFileIsSourceFailed`, with cases missing, undecodable, checksum mismatch, unavailable tier, hang on a slow tier, hang on `local`, physical axis, Tail, a file retired by a Deleted record, and a file read from its compaction successor.

Prefix, predicate and wait rules. The SDKs and docs call a story a scope; this document and the wire say chronicle and story, and the contract has no scope type. Every event lives in exactly one story, the physical home of its history. The path of a story is `<chronicle name>/<story name>`, and a story name may itself contain `/`, as in `lab/proj/task-17/planner`. A prefix matches whole path segments only: `lab/proj` matches `lab/proj/a` and never `lab/project`. The invariants below add Reads and Tails over a prefix of story paths, predicates, newest-first order, lookup by EventId and await. Each leaves I6.1 to I6.14 unchanged for a request that names one story and sets none of the new fields. Redaction of individual events is specified separately (phase 1b, its own review) and is not part of these invariants.

- I6.15 Prefix Read and Tail. A Read or Tail may name a prefix of story paths instead of a story. A Read returns the merged history of every story whose path equals the prefix or lies below it by whole path segments, resolved through the Catalog only (I3.4, I9.3). The stream is ordered by (hlc, story_id, writer_id, incarnation, sequence), the order of I7.7, and is deduplicated by EventId (I6.4). A prefix Read through e is complete iff the story set under the prefix was read at one Catalog revision R, every story in it is complete through e on the Read's axis (I6.1, I6.10), and every Keeper that any story under the prefix can route to has a sealed frontier at or above e (the physical frontier of I8.10 on the physical axis). Static mode meets the last condition by checking every configured Keeper, because every Route lists all of them; in dynamic mode the creation floor and the confirming read of I6.16 close the set after R. The Completion names R. A story tombstoned at R is excluded from the set, and repeatability (I6.8) holds per revision, so a destroyed child never fails the reads above it. A story of the set that is destroyed while the Read runs ends the Read complete=false with SOURCE_FAILED (I6.7), never a partial result presented as complete; the client's next Read resolves a later R. A prefix that matches no story is not an error: the Read returns no event and its Completion names R with complete=false and reason LAGGING_WRITERS, because no Keeper proved a frontier for it; it makes no claim. A prefix that resolves to more than prefix_max_scopes stories (default 1024, section 13) fails the whole request with RESOURCE_EXHAUSTED (W10.3); a prefix Read never returns a subset of its stories. Incomplete reasons follow I6.3, and a TRUNCATED prefix Read's frontier c is the minimum of its stories' frontiers under I6.12, and the stream holds no event of any story at or above c. A prefix Tail resolves its story set once at R and fixes it for the life of the stream. I6.13 applies with the sources of every story in the set taken together (one T, the minimum over all of them), delivery is in the order of I7.7, and I6.9 resumes exclusively after `position` in that order, and the Tail MUST opt in to progress (I6.21) or the request is INVALID_ARGUMENT; its first message is a progress message that names R. A story destroyed during the Tail leaves the set without ending the stream, and picking up stories created after R is the client's re-subscribe in phase 1. Gates: `replay_adapter.PrefixReadIsCompleteOnlyAtOneCatalogRevision (to build)`, `replay_adapter.PrefixOverTheStoryCapIsResourceExhausted (to build)`, `replay_adapter.PrefixTailFixesItsStorySetAtR (to build)`, `replay_adapter.PrefixReadExcludesAStoryTombstonedAtR (to build)`, `replay_adapter.EmptyPrefixMakesNoClaim (to build)`.
- I6.16 Story creation floor, dynamic mode. In dynamic membership mode (I4.3) the createStory command computes inside apply and records, in the same commit, the creation floor pair CF = (CF_C, CF_P): the maximum C and the maximum CP over every ceiling pair ever granted to any Keeper instance of the deployment (I4.7). The Catalog MUST refuse createStory with FAILED_PRECONDITION while any registered Keeper process has never been granted a ceiling, as I4.15 refuses an epoch change. The story's first RouteUpdate carries CF_C as its ordering cut and CF_P as its physical floor PF_X, and lists every Keeper of the Route in observe_floor. Before a Keeper admits the story's first append it MUST observeFloor(CF_C) and raise its acceptance clock L to CF_P, both under the transition budget of I4.8 and answering UNAVAILABLE meanwhile, exactly as a Keeper new to a Route does in I4.9; admission opens when its own ceiling exceeds CF_C. Hence every hlc of the story is above CF_C and every accepted interval has lo at or above CF_P - A (I8.9). The Player completes the rule: after it has received the last frontier of a prefix Read it MUST read the Catalog again, linearizably, and confirm that no story under the prefix was created after R. If one was, it resolves the set again and repeats the Read, at most prefix_resolve_retries times (default 3, section 13), and then answers complete=false with reason LAGGING_WRITERS. Soundness: every frontier the Read used was reported before the confirming read and is bounded by a ceiling granted before it (F <= C and P <= CP - A, I4.7), and a story created after the confirming read has CF at or above every such ceiling, so its events are above e on the HLC axis and are refused below P on the physical axis; a story created before the confirming read is in the set. Static mode needs neither the floor nor the confirming read, because every Route lists every configured Keeper and each of them answered. Gates: `MembershipContract.NewStoryRouteCarriesTheCreationFloor (to build)`, `MembershipContract.CreateStoryRefusedWhileAKeeperHasNoCeiling (to build)`, `MembershipContract.CreationFloorIsComputedAtApplyNotProposal (to build)` (a ceiling granted between proposal and apply is covered by the floor), `JournalContract.NewStoryObservesTheCreationFloorBeforeItsFirstAppend (to build)`, `replay_adapter.PrefixReadReResolvesWhenAStoryIsCreatedDuringIt (to build)`; ctest `visor.dynamic_prefix_claim (to build)` (real processes: a prefix Read complete through e on each axis returns the same events after a Keeper joins and a story is created under the prefix on it).
- I6.17 Predicates. Read and Tail accept a predicate over the indexed fields of I3.9. A predicate is a conjunction of equality terms: `kind` in a set of values, `actor` in a set of values, an attribute key equal to a value, an EventId equal to a value, or a link given by its target EventId and optionally its type; the term matches on the target EventId and ignores the hlc a link carries. An event matches when it satisfies every term, and a set inside one term is satisfied by any of its members. A predicate holds at most 256 values in total, counting every set member and every term. An attribute term MUST have a non-empty key, a link term a complete target EventId, and an EventId term complete ids (all four fields non-zero); a predicate that breaks a rule fails the whole request with INVALID_ARGUMENT. There is no disjunction across terms, no pattern match and no predicate on the payload or its content type. Filters only remove events: a predicate never changes the range, the order, the sources consulted or the frontier, so every Completion rule above holds unchanged for the matching events, and `max_events` counts matches, as I6.10 already does. A predicate is evaluated at the source by scanning the range (Archive.FetchHot and the archive reader, as the physical filter of I6.10 is); a per-chunk index may speed that scan and is never part of the contract. A predicate is data and no user code runs in the storage path. Gates: `ReplayContract.PredicatesOnlyRemoveEvents (to build)`, `replay_adapter.MalformedOrOversizedPredicateIsInvalidArgument (to build)`.
- I6.18 Newest-first Read. A Read may ask for order newest-first. It is HLC axis only; on the physical axis it is INVALID_ARGUMENT. `max_events` bounds it as it bounds any Read (W10.1 soft target; zero means read_max_events). With an open end the Player sets e to the minimum sealed frontier of the sources, read before the scan, and the Completion returns it. With a given end, e is that end, and a source whose sealed frontier is below it makes the Read incomplete with LAGGING_WRITERS exactly as I6.1 does. The Read returns the matching events of [start, e) in descending order (`ReplayLess`, or I7.7 for a prefix), and the sources scan descending (FetchHotRequest `order`, section 10). When every matching event of [start, e) was returned the Read is complete under the rules of an oldest-first Read. When `max_events` cut it, the Read ends complete=false with reason TRUNCATED and the Completion carries c and e, with `frontier` equal to e; a continuation reads [start, c), never from `frontier`: c is at or above the hlc of the oldest event the Player returned and, for every source whose answer was truncated, the hlc of the oldest event that source returned; every event with hlc at or above c is in the stream and none below it, so [c, e) is complete on its own in the sense of I6.8 and a continuation over [start, c) has no gap or duplicate. No LOST window, unreadable file (I6.14) or abandoned range (I4.15) may lie in [c, e); when one does, or a source failed, the reason is SOURCE_FAILED and there is no claim. Gates: `ReplayContract.NewestFirstTruncatedSuffixIsComplete (to build)`, `replay_adapter.NewestFirstIsHlcAxisOnly (to build)`.
- I6.19 Lookup by EventId. There is no Get RPC. A lookup that has the hlc, held by the caller or carried by a link, is a point read: a Read of the half-open range that holds exactly that hlc, restricted to that EventId, A caller that has the hlc, its own or one a link carries, reads the half-open range that holds exactly that hlc with the EventId as the selector; Await does the same internally (I6.20). A lookup without an hlc is an Await with a zero wait. An event that is not visible (I6.8) is not an error; the lookup returns the answer of I6.20. Gate: `replay_adapter.LookupByEventIdIsAPointReadOrAZeroWaitAwait (to build)`.
- I6.20 Await. `Await(ref, bound)` takes an EventId, its hlc when the caller has one, and a wait bound. It returns as soon as the event is visible or answer (3), (4) or (5) holds, and otherwise at its bound with answer (2). The bound is the request's `wait_bound_ns`, capped at await_max_wait_ms (300000 by default, section 13) and at the request deadline when the caller set one; a negative bound is INVALID_ARGUMENT; at the cap the Await returns the current certificate and the client re-arms, and a zero bound returns the first answer at once. The answers are (1) visible, with the event; (2) absent, complete through F, meaning the event is not visible and cannot have an hlc below F; (3) sequence consumed without an event, meaning the Keeper recorded a rejection that consumed the sequence (I8.9) and the event never exists; (4) will never exist, meaning the writer's incarnation is fenced (I3.7) without having accepted that sequence; (5) unknown, meaning no certificate is available and the event may exist. The Player serves Await. For a ref with an hlc it first performs the point read of I6.19: a hit is (1). A miss while the read's frontier F is at or below that hlc keeps waiting. A miss with F above that hlc proves only that the event is not at that hlc, so the Player continues as for a ref without an hlc; a failed source is (5). For a ref without an hlc, (story, writer_id, incarnation, sequence), the Player asks every Keeper of the story's Route and every predecessor entry (I4.13) over the internal Archive.WriterStatus call (section 10), and uses the one answer with known=true; I7.5 and I6.11(d) make it at most one. The answer comes from the writer checkpoint of I6.22: the sequence at or above next_sequence with the incarnation live is (2) through that Keeper's sealed frontier F, and the Await keeps waiting; at or above next_sequence with the incarnation released, expired or superseded is (4); inside the dedupe window is the recorded result: a recorded rejection that consumed the sequence is (3), and a recorded hlc h leads to the point read at h, where a hit is (1), a miss with F at or below h keeps waiting (the event is pending), and a miss with F above h is (5) (an ACCEPTED event lost in a crash, I6.8); below the dedupe window is (5), because the event may exist and the caller needs its hlc. When no Keeper answers known=true, or a Keeper that could have held the incarnation did not answer or was abandoned (I4.15), the answer is (5), never (2); an incarnation not yet acquired is therefore (5). A waiting Await holds one of the Player's max_streams slots (M11.4) and one past the cap fails RESOURCE_EXHAUSTED. An Await in a tombstoned story fails whole-request with FAILED_PRECONDITION as I6.7 says. Gate: `replay_adapter.AwaitAnswersWithACertificate (to build)`, with one case per answer and per row of the table above.

- I6.21 Tail progress, opt-in. A Tail request carries a progress flag; the SDKs always set it and a prefix Tail requires it (I6.15). A Tail that opted in receives a progress message carrying a Position with hlc T and no id whenever its delivery frontier T (I6.13) advances and nothing matched, at most once per round, so a subscriber whose predicate matches seldom still advances its resume position instead of rescanning from its last match. A progress message claims that every matching event with hlc below T has been delivered. It is not a Completion, and a Tail still never claims completeness (I6.5). A Tail that did not opt in receives only batches and the final Completion, as before. Gate: `ReplayContract.TailProgressIsOptInAndAdvancesTheResumePosition (to build)`.
- I6.22 Writer checkpoint retention (RFC-T round 3, 2026-10-04; it resolves the OPEN on checkpoint retention). The Keeper MUST keep the checkpoint head of every (writer_id, incarnation) it served, that is next_sequence, last_hlc, released and the termination cause, for the life of the story: across release, eviction of the writer's events and Keeper restart, and dropped only with the story (W10.5). It MUST keep the per-sequence result, the hlc or the recorded rejection (I8.9), for the last dedupe_window sequences of each writer (65536 by default, section 13). A head is a few dozen bytes, so the state is bounded by acquisitions, not by events. The Keeper answers Archive.WriterStatus (section 10) from this state, and I6.20 reads no other. Gates: `JournalContract.WriterCheckpointHeadSurvivesReleaseAndEviction (to build)`; ctest `keeper.wal_restart` step `checkpoint-after (to build)`, which after a SIGKILL restart finds the heads and windows of the writers acquired before it answering as they did.
- I6.23 Resume from a Position with no id. A Tail whose `from` Position has an hlc T and an id that is absent or all zero resumes at every event with hlc at or above T, an event at exactly T included. With no id there is no event at the position to exclude, so I6.9 does not apply. The resume is sound because I6.13 delivers every event below T before it moves T, so every delivered event has hlc below T and none at or above it has been delivered: a resume from a progress message (I6.21) misses and repeats none. Gate: `ReplayContract.TailResumesAtEveryEventFromAnIdlessPosition (to build)`.

## 7. Ordering

Total order for replay: (hlc, writer_id, incarnation, sequence), lexicographic. Implemented once as `ReplayLess` in `include/chronolog/types.h`. Per-writer order is sequence order and is never violated.

- I7.1 Replay output MUST be sorted by the total order within one stream. Gate: `ReplayContract.TotalOrderAndEventIdentityDeduplication`.
- I7.2 For a fixed (writer_id, incarnation), hlc MUST be non-decreasing in sequence. The Keeper enforces this at accept because it assigns hlc in arrival order and rejects gaps. Gate: `JournalContract.PerWriterOrderSurvivesBackwardPhysicalStep`.
- I7.3 Read-then-write causality: if client A observes event X (hlc h) and then appends Y with causal_floor >= h, then hlc(Y) > h. Gate: `JournalContract.KeeperAssignsHlcAboveCausalFloor`.
- I7.4 A new incarnation of a writer MUST sort after every event of its previous incarnation. The Keeper MUST reject an append whose incarnation is below the highest it has seen for that writer. The only exception is a writer of a story abandoned as total loss under I4.15. Gate: `JournalContract.OlderIncarnationIsRejected`.
- I7.5 Two Keepers serving one story (a Route lists several keepers for partitioning) MUST NOT both assign hlc for the same writer. Writer to Keeper affinity is `Acquisition.assigned_keeper`, stable per (writer_id, epoch); a Keeper MUST reject an append from a writer not assigned to it with FAILED_PRECONDITION and current_route. Gate: `MetadataStoreContract.AssignedKeeperStableWithinWriterEpoch`, `JournalContract.UnassignedKeeperRejectsWriter`. Preferred Keeper is a first-assignment hint resolved against the committed Route. HONORED uses an eligible initial hint, NOT_IN_ROUTE discloses a stale hint, and RETAINED discloses existing affinity precedence. - I7.6 Legacy timestamp ordering guard kept by the client Clock: `ClientClock.StrictlyIncreasesEvenWhenRawStepsBackward` in `client/cpp/tests/clock_test.cpp` (origin/visor-clock-exchange).
- I7.7 Prefix order. A stream that merges more than one story (I6.15) is ordered by (hlc, story_id, writer_id, incarnation, sequence), lexicographic, implemented beside `ReplayLess` in `include/chronolog/types.h`. `ReplayLess` is defined within one story and does not compare story_id, and writer_id alone does not separate two stories, so two events of different stories with equal hlc and writer_id would otherwise be unordered. ## 8. Clock contract

`Clock::now() -> TimeReading{physical_ns, uncertainty_ns optional, status}` with status Synced, Unsynced or Unavailable (`include/chronolog/clock.h`).

- v1 bound: read with ntp_adjtime(2) in read-only mode (modes = 0, unprivileged). maxerror is in microseconds; bound_ns = maxerror x 1000, which already includes the kernel's drift growth between disciplining updates. Synced iff the call succeeds, STA_UNSYNC is clear and bound_ns <= cap (default 1 s); then uncertainty_ns = bound_ns; otherwise Unsynced with no bound; a failing call is Unavailable. Services use `src/common/clock/KernelClock`; client/cpp carries its own twin (section 11).
- Unsynced and Unavailable MUST carry no finite bound: `uncertainty_ns` is absent. An absent bound means unknown, never zero.
- `Clock::tick() -> Hlc` for a local event, `Clock::observe(Hlc) -> Hlc` merges a remote HLC with the standard HLC rule, `Clock::uncertainty()` returns the last bound.
- No ML in v1. A learned predictor MUST NOT shrink the bound until residual coverage is validated.
- `chronolog.internal.v1` Cluster.ReadClock returns the Visor's monotonic authority tick for a Cristian round-trip estimate (offset = authority_tick_ns + RTT/2 - t1). That tick is kept separate from CLOCK_REALTIME and from the chrony bound. RTT uncertainty MUST NEVER replace physical uncertainty, and ReadClock MUST NOT be used by the Keeper to assign hlc. It is not in `chronolog.v1`; it can be promoted later additively. Writers without chrony report Unsynced physical time.
- Legacy Cristian exchange with the Visor (`client/cpp/include/ChronoClock.h`, origin/visor-clock-exchange) reported uncertainty = RTT/2. That exchange is replaced by the chrony-backed Clock; the monotonic clamp and the injected TimeSource test seam are kept (`ChronoClock`, `client/cpp/include/chronolog/client/clock.h`).

Invariants:
- I8.1 HLC MUST strictly increase per Keeper even when physical time steps backward or the source becomes Unavailable. Gate: `ClockContract.HlcMonotonicUnderBackwardPhysicalStep`, `ClockContract.UnavailableSourceKeepsHlcAdvancing`.
- I8.2 `observe(h)` MUST return an Hlc > h and > the last tick. Gate: `ClockContract.ObservePreservesReadThenWriteCausality`.
- I8.3 A Synced reading MUST have a finite bound; an Unsynced or Unavailable reading MUST NOT. Gate: `ClockContract.UnsyncedAndUnavailableHaveNoFiniteBound`.
- I8.4 The HLC logical counter MUST reset to 0 when physical advances and MUST increment otherwise. Gate: `ClockContract.StandardHlcLogicalTick`.
- I8.5 The Keeper MUST assign hlc = max(local physical, last assigned, client causal_floor) with tick. Gate: `JournalContract.KeeperAssignsHlcAboveCausalFloor`.
- I8.6 A causal_floor far in the future MUST NOT be accepted blindly. The Keeper MUST reject an item whose causal_floor.physical_ns exceeds local physical by more than the Catalog policy's skew limit S (60000000000 ns by default, section 13) with INVALID_ARGUMENT. Gate: `JournalContract.AbsurdCausalFloorIsRejected`.
- End-to-end gate: `tests/integration/visor/clock_skew_harness.sh` (origin/visor-clock-exchange), asserting that the absolute error of the measured offset is at most the reported uncertainty plus 2 ms slack (`kSlackNs = 2'000'000` in `tests/integration/visor/clock_skew_probe.cpp:31`; the harness runs as ctest `visor.clock_skew`).

- I8.7 `Hlc.physical_ns` is CLOCK_REALTIME on the Keeper. HLC tolerates steps by construction (I8.1) and this keeps hlc comparable to the writer's physical field. Gate: `ClockContract.HlcMonotonicUnderBackwardPhysicalStep`.

Physical acceptance policy (RFC-A). The policy constants A (acceptance window, default 15 s), S (the causal floor skew limit of I8.6, default 60 s), D = S + reserve_ahead (default 61 s), the uncertainty cap (default 1 s) and a policy version are fixed when the Catalog is created; Register returns them and a process configured differently refuses to start (`MembershipContract.MismatchedPolicyRefusesRegistration`). Per event: p = physical_ns; u = uncertainty_ns when Synced and u <= cap, else the event is unbounded and u = 0; lo = p - u; hi = p + u, computed with overflow checks (an unrepresentable interval is INVALID_ARGUMENT, `JournalContract.UnrepresentableIntervalIsInvalidArgument`).
- I8.8 Acceptance clock. L lives inside the Keeper's HLC core: L = max(CLOCK_REALTIME, previous L), raised only by I4.8. `Clock::assignChecked(floor, interval)` runs in one critical section of the core: compute the candidate hlc from max(L, floor, last), including any logical overflow carry; if candidate.physical - L > D raise L to candidate.physical - D; test I8.9 against that final L; commit the candidate only if the item passes; return the hlc with that L. The Keeper calls it under the writer lock and holds the lock until the event is registered pending or visible. Hence L <= hlc.physical <= L + D for every accepted event. On restart L = max(CLOCK_REALTIME, restart hlc.physical - reserve_ahead, R + A), R the highest physical frontier ever reported (persisted beside the HLC reservation). Gates: `ClockContract.AssignCheckedIsAtomicWithTheFinalAcceptanceClock (TSAN)`, `JournalContract.PhysicalCheckOrderedBeforeInsert (TSAN)`, `JournalContract.HlcLeadOverAcceptanceClockIsBounded`.
- I8.9 Acceptance rules. The Keeper MUST reject an item with lo < L - A or hi > L + S with per-item OUT_OF_RANGE, achieved UNSPECIFIED. The rejection consumes the sequence: nothing is stored, the rejection is recorded in the dedupe window and in the persisted writer checkpoint, next_sequence advances, and a retry of that EventId returns the same OUT_OF_RANGE before and after a restart. Gates: `JournalContract.BackdatedReadingIsOutOfRange`, `JournalContract.FutureReadingIsOutOfRange`, `JournalContract.OutOfRangeConsumesSequenceAndRetriesIdempotently`.
- I8.10 Physical frontier. `Journal::physicalFrontier(story)` reads L first, then takes each writer lock over the writer set as it is after that read: P = min(L - A, min lo over pending events that are not yet visible); an ACCEPTED event being upgraded to DURABLE stays visible and does not cap P. The Keeper reports max(last reported P, computed P), persists it beside the HLC reservation, never reports it above that reservation or above CP - A (I4.7), and carries it in FetchHotTrailer.physical_frontier_ns, computed before the event scan. Gates: `JournalContract.PhysicalFrontierBoundsLaterAcceptance`, `JournalContract.PhysicalFrontierSurvivesRestart`, `JournalContract.DurabilityUpgradeDoesNotLowerPhysicalFrontier`.
- I8.11 Every physical completeness claim on a story is protected across Keeper changes: survivors' own P bounds earlier claims, and a Keeper new to the Route raises L to the story's physical floor PF_X (I4.9) before admitting. Gate for the new-member clause: `JournalContract.NewMemberAcceptanceClockCoversTheStoryPhysicalFloor`. Gate for the survivor clause: ctest `visor.dynamic_physical_claim` (real processes: a physical Read complete through P stays complete with the same events after a Keeper is SIGKILLed and a Keeper new to the Route joins, and both Route Keepers answer OUT_OF_RANGE for an event below P). It rests on I8.10's `JournalContract.PhysicalFrontierBoundsLaterAcceptance`.
- I8.12 Policy coverage per story. The Catalog keeps a per-story physical_policy flag, true at creation iff every Keeper of the story's first Route registered with the current policy version, and cleared permanently when a Keeper without it serves the story or an archive chunk without the policy marker (ChunkIdentity.physical_policy) touches it. A Keeper's new WAL writes the policy record first; a WAL without it registers its Keeper as without policy. Gate: `MembershipContract.PolicyDowngradeEmitsARevisionedDelta`, `player.ReplayContract.ArchiveWithoutPolicyMarkerMakesPhysicalReadIncomplete`; ctest `keeper.policy_marker` (real stack: a Keeper whose WAL holds Q0 serves a story, its chunk reaches the archive, and a physical Read of the archived event returns it with PHYSICAL_AXIS_UNBOUNDED and never complete while the HLC Read is complete; the same stack on a fresh WAL completes the physical Read).

## 9. The six interfaces

All live in `include/chronolog/`, are pure virtual, return `absl::Status` or `absl::StatusOr<T>`, and contain no gRPC or protobuf types. Shared value types live in `types.h`: EventId, Hlc, TimeReading, Durability, Route, Epoch, Envelope, Event, AppendItem, AppendResult, Range, Frontier, Completion, Chunk, ManifestRecord, ChunkReceipt, WatermarkReport, ReplayBatch. Thread-safety stated here and in the header comments is normative.

**Clock** (`clock.h`): now() -> StatusOr<TimeReading>, tick() -> Hlc, observe(Hlc) -> Hlc, uncertainty() -> StatusOr<optional<uint64>>, assignChecked(floor, interval) -> {hlc, L} or OUT_OF_RANGE or WOULD_EXCEED_CEILING (I8.8, I4.7), observeFloor(Hlc), which raises the HLC without assigning an event and is never ceiling-gated (I4.9), acceptanceClock() -> L and raiseAcceptanceClock(floor) (I8.8, I4.8). tick() and observe() are infallible: loss of the physical source sets status Unavailable on now() and HLC continues from last assigned plus logical ticks. All methods MUST be safe to call concurrently from any thread; tick and observe serialize on one atomic or mutex; now() MUST NOT block on I/O, so the chrony refresh runs on a background thread owned by the implementation. Invariants I8.1 through I8.4. Suite: `ClockContract`.

**MetadataStore** (`metadata_store.h`): createChronicle, getChronicle, listChronicles, destroyChronicle, createStory, getStory, listStories, listStoriesByPrefix, destroyStory, acquire(story, writer_identity[, AcquireOptions]) -> Acquisition{story_id, writer_id, incarnation, route, assigned_keeper, lease, keeper_preference}, renewAcquisitions(tuples) -> per-tuple results, release -> ReleaseResult, compareAndSetEpoch. `assigned_keeper` is a KeeperRef{process_id, endpoint}, the single Keeper for this writer in the current epoch, stable per (writer_id, epoch); AcquireResponse carries no epoch field of its own, route.epoch is the only epoch in that response; it enforces I7.5 while Route still lists every keeper. All methods thread-safe and linearizable per key. Persistence is SQLite (vcpkg sqlite3) in WAL journal mode with synchronous=FULL; acquire and incarnation bumps MUST commit before the RPC returns. In dynamic mode the Catalog replicates the same operations through NuRaft behind the same contract (RFC-B): the SQLite database is the state machine, each mutation is one CatalogCommand applied as one transaction with every id and revision assigned inside apply, snapshots are SQLite online backups, the leader serves mutations and linearizable reads only under a valid NuRaft leadership lease, followers forward unary calls, and any replica serves the watch streams from its applied state; subscribers reject a snapshot or delta whose revision or per-story epoch regresses. I9.1: the Raft log store MUST fsync before append returns. Gate: `MetadataStoreContract.RevisionSurvivesLeaderChange` (replicas restarted in process, so it proves the state is reloaded from disk, not that it was fsync'd); `RaftStorageTest.DurableStateJournalIsWalAndSynchronousIsFull` (the Raft store's own connection runs journal_mode=WAL and synchronous=FULL, which is what makes each commit an fsync); ctest `visor.restart` (real processes: SIGKILL of the leader mid-workload, then SIGKILL of all three replicas; the Catalog revision never goes back and an acquisition committed just before the kill survives with a higher incarnation). Invariants I3.4 through I3.6, I4.2, I9.2, I9.3, plus `MetadataStoreContract.PersistedIncarnationStrictlyIncreases`, `MetadataStoreContract.StoryTombstonePermanence`, `MetadataStoreContract.AssignedKeeperStableWithinWriterEpoch`. Suite: `MetadataStoreContract`.

Finite acquisition grants, process-local request-id dedupe, explicit takeover/CAS and typed native AcquireRefusal details follow RFC-G (PI sign-off 2026-10-02 21:25). New grants/incarnations and terminal transitions are durable; ordered per-entry RenewAcquisitions updates only qualified-authority memory and writes no SQLite row, Raft entry, revision or feed delta. SQLite remains Raft's applied state machine. CLOCK_MONOTONIC deadlines use a separate map mutex, never held across store I/O, fsync, proposal/network waits or acquisition of the store mutex. Post-commit applied-transition observation installs live deadlines and removes terminal entries even after a lost RPC reply. A new term/fresh step-up or static restart rebuilds now+T; same-term qualification lapses and service-tick gaps pause remaining time, charging overlap once before due checks. Every sweep performs bounded progressing missing-row reconciliation; current unreleased missing tuples initialize now+T on Renew/retry/evidence, while existing due/pending entries never reset. Authority qualification is an atomic timestamped state with the applied index published at apply and peer ages sampled without the store mutex; stale samples cannot end a newer lapse. Step-up captures the applied index under the store mutex while the observer buffers transitions. Reconciliation drops durable terminal tuples; ExpireAcquisitions apply returns per-tuple outcomes, including no-ops, to clear pending marks. A partial index on acquisitions WHERE released=0 bounds scans. The completed service tick shares map serialization with Renew, evidence and sweep; a separate monitor cannot report progress for a stalled worker. Configuration MUST require 0 < acquisition_lease_min_ns <= acquisition_lease_default_ns <= acquisition_lease_max_ns and acquisition_lease_min_ns > ns(max(raft.election_upper_ms, heartbeat_timeout_ms) + release_fence_timeout_ms + lease_safety_margin_ms), with checked conversion and a service-tick gap allowance below lease_min. SDK CLOCK_BOOTTIME horizons are scheduling advice only. Client acquire is single-flight per process-owned request id: concurrent use waits or refuses, delivered ids refuse FAILED_PRECONDITION, and an identical logical acquire reuses its own unresolved id only after the prior call returned without a grant. At most one Writer per tuple exists per Client.

I9.2 Chronicle and story properties. createChronicle and createStory accept optional properties: `tier_policy` (a string), `retention_ns` (an int64 in nanoseconds, W10.9; zero or unset means no value, negative is INVALID_ARGUMENT) and `granularity` (one of ns, us, ms, s). The Catalog stores them with the chronicle or story row and returns them from getChronicle, listChronicles, getStory and listStories. They are set at creation and immutable: phase 1 defines no way to change them. They are inert: no component reads them to change tiering, retention, read-side slot bucketing or any other behavior until phase 5, and inheritance down a path is computed then, not stored now. They survive restart, Raft snapshots and leader change as the rest of the row does, and an object created without them reads back with them unset. Gate: `MetadataStoreContract.ChronicleAndStoryPropertiesAreStoredAndInert (to build)`.

I9.3 List by prefix. listStoriesByPrefix(prefix, limit) with limit from 1 to 65536, else INVALID_ARGUMENT, returns every story whose path (`<chronicle name>/<story name>`) equals the prefix or lies below it by whole path segments, in one linearizable read, with the Catalog revision R at which that read was taken (the global counter of W10.14). A tombstoned story (I3.5) is not in the result. When more than `limit` stories match it says so and returns none of them, so the Player enforces prefix_max_scopes (I6.15) without reading an unbounded set. A story with a reserved segment (I3.11) is in the result only when the prefix names that segment. Gate: `MetadataStoreContract.ListByPrefixIsOneRevisionAndSegmentExact (to build)`.

**Membership** (`membership.h`): route(story_id) -> Route, routeState(story_id) -> RouteState {Route, ordering cut, physical floor, predecessors, archived_below, abandoned ranges} (I4.9 to I4.15), validateEpoch(story_id, epoch), registerProcess(Process{id, instance, endpoint, role}), heartbeat(id, instance, applied_revision). route() returns a snapshot copy taken under a bounded shared-lock section; validateEpoch() takes at most a shared lock; registration may take an exclusive lock. Invariants I4.1, I4.3, I4.5, I7.5, plus `MembershipContract.RegisterHeartbeatAndRestartFencing`. Suite: `MembershipContract`.

**Journal** (`journal.h`): append(AppendBatch{story_id, epoch, items}, durability) -> vector<AppendResult> (single-story batches, W10.13); read(story, range) -> vector<Event>; frontier(story) -> vector<Frontier>; keeperFrontier(story) -> Hlc, the Keeper-level seal even when no writer is registered, which FetchHotTrailer carries as `sealed_frontier`; physicalFrontier(story) -> int64 (I8.10); writerStatus(story, writer_id, incarnation, sequence) -> the writer checkpoint head, the recorded result for the sequence when it lies inside the dedupe window, and the sealed frontier, which the Keeper serves to the Player as Archive.WriterStatus (I6.22). append() MUST be callable concurrently for different stories; for one writer, acceptance and hlc assignment MUST be atomic. read() holds each writer lock only for that writer's scan slice and never across the whole story. Invariants I3.1 through I3.3, I3.9, I3.10, I5.1 through I5.9, I6.6, I6.22, I7.2 through I7.4, I8.5, I8.6, I13.8. Suite: `JournalContract`.

**TierStore** (`tier_store.h`): publish(Chunk) -> ManifestRecord; read(story, range); manifest(story) -> vector<ManifestRecord>; contiguousWatermark(story) -> Hlc. publish() MUST be thread-safe across stories and across concurrent streams of one story (legacy `ArchiveManifest::append` is mutex-serialized for this reason). Visibility is API visibility: a reader sees a chunk only through its manifest record, never by scanning files; publish() is atomic to readers in that sense. read() MUST be safe concurrently with publish(). Invariants I13.1 through I13.7, I12.2 through I12.4. Suite: `TierStoreContract`.

**Replay** (`replay.h`): read(story, range) and tail(story, position) each return a `ReplayStream` with next() -> optional<ReplayBatch> (nullopt is EOF) and cancel(). A stream has exactly one consumer; distinct streams are independent; cancel() is thread-safe, idempotent and unblocks a pending next(); destroying a stream cancels and joins owned work. The implementation MUST NOT invoke the consumer under any internal lock. Invariants I6.1 through I6.5, I6.7 through I6.10, I6.13, I6.15 through I6.21, I7.1. In phase 1 read gains the prefix, predicate and order forms, tail gains the prefix, predicate and progress forms, and the interface gains await, which also serves lookup by EventId. Suite: `ReplayContract`.

A Tail (I6.13) maintains a buffer and covered bound for each Route Keeper and applicable predecessor, keyed by process id and predecessor owned epoch, with the Keeper instance attached. Fetch from max(T, covered); a new source starts at T. A source's covered bound is its sealed frontier, capped at its own cut for a predecessor and the last returned event HLC when truncated (I6.12). An empty truncated answer adds no coverage. A predecessor is unconstraining only when its covered bound reaches its own cut. Buffer limits cut coverage at the first omitted event, keeping only the prefix strictly below that HLC, except that an empty source buffer always admits its first event and the archive always admits its first equal-HLC group, so the payload budget (tail_max_bytes, section 13) is soft by one payload or one tie group per share, with one warning per source per Tail. Full buffers suspend replacement calls until delivery frees room; retained coverage is reused only in the matching epoch and required predecessor instance. Any share shrink, including a joining predecessor or a newly configured archive, may discard buffered payload and reset the fetch start to T without decreasing T. At most one Catalog confirmation occurs per round, and an unchanged refusal set after a live Catalog answer needs no new confirmation; identity and instance changes supply new evidence.

Every suite MUST be declared with `GTEST_ALLOW_UNINSTANTIATED_PARAMETERIZED_TEST`, so a build that omits an implementation stays green. Every implementation of a contract MUST instantiate its suite. A suite instantiation is a `INSTANTIATE_TEST_SUITE_P` in the component's own test directory, never inside `tests/contract/`.

## 10. Wire API rules

Public package `chronolog.v1`, file `proto/chronolog/v1/chronolog.proto`, services Catalog (chronicle and story create, get, list and destroy, Acquire, RenewAcquisitions, Release, CompareAndSetEpoch), Journal (Append unary, AppendStream bidi), Replay (Read, Tail server streams; Await unary, W10.20). Catalog commits the release, then waits up to `release_fence_timeout_ms` for the assigned Keeper's Heartbeat `applied_revision` to reach the release's revision. fenced=false means the release is committed but the Keeper had not confirmed; appends that Keeper accepted before fencing stay valid and sort before any newer incarnation. No claim of linearizable release is made. Release is idempotent by (story_id, writer_id, incarnation): a retry after a lost response returns the committed revision and the current fenced state, which is also how a client polls fence state. Gate: `MetadataStoreContract.ReleaseReportsFenceState`, `CatalogAdapterTest.DroppedReleaseRetryReturnsCommittedState`, adapter `CatalogAdapterTest.ReleaseWaitsForAppliedRevision`. Polling an EXPIRED or SUPERSEDED tuple returns its original revision/current fence state without overwriting its cause. Sweeper commits and returns without this bounded fence wait. Neither a persisted confirmation command nor a metric proves fencing.
- W10.13 Append batches are single-story. AppendRequest carries story_id, epoch, durability, batch_id and items; an item carries writer_id, incarnation, sequence, physical, causal_floor and envelope; a result carries the full EventId. A batch mixing stories is impossible by construction and the top-level current_route is unambiguous. Gate: `JournalContract.PerItemFailureDoesNotEraseSuccessfulBatchItems` on the new shape.
- W10.14 AcquisitionUpdate and ReleaseResponse carry `revision`, a persisted Catalog counter never reused across Visor restarts, and the proto comments say so; HeartbeatRequest carries `applied_revision`. There is one global Catalog revision counter. A Keeper's applied_revision is the highest R such that every update relevant to that Keeper with revision <= R is applied; irrelevant revisions are skipped implicitly, and applied_revision is scoped to the reporting process instance. WatchAcquisitions on subscribe or reconnect sends a full snapshot of the acquisitions assigned to that Keeper as of revision R, then deltas above R; a (re)started Keeper applies the snapshot, restoring every fence, before admitting any append. Gates (acquisition adapters): `AcquisitionWatcherTest.RevisionGapsAreSkipped`, `AcquisitionWatcherTest.RestartRestoresFencesBeforeAdmission`, `AcquisitionWatcherTest.AppliedRevisionIsMonotonic`. AcquisitionUpdate.termination_cause=8 preserves the original cause. A replacement instance proves a fence only after applying the snapshot through its revision; obsolete-instance reports cannot prove it. Snapshot absence need not restore a precise diagnostic cause; Catalog Renew classifies it.
- W10.15 CLOCK_STATUS_UNSPECIFIED on the wire maps to Unavailable in every adapter, never to Synced; the proto comment states it. Gate: `JournalAdapterTest.UnspecifiedClockStatusIsUnavailable` (Keeper), `EventConvert.UnspecifiedClockStatusIsUnavailable` (Player), `ProtoChunkCodec.UnspecifiedClockStatusIsUnavailable` (archive codec), `ClientEventConvert.UnspecifiedClockStatusIsUnavailable` (C++ SDK), `GrapherClockAudit.AnonymousUnsyncedOrSteppedReplyIsInconclusive` (the Grapher's reading of a Visor reply).
- W10.16 `chronolog.v1.Story` carries `Route route = 6`, filled by GetStory and ListStories with the story's current Route (none for a tombstoned story); Story.route.epoch equals Story.epoch in the same response. It is a snapshot: a client MUST still adopt current_route from any FAILED_PRECONDITION item (I4.4). Gate: `catalog_adapter.GetStoryCarriesCurrentRoute` (`src/visor/tests/`).
- W10.17 Story destroy propagation (RFC-C). `RouteUpdate` and `WatchRoutesResponse` carry `bool tombstoned = 11`: the story was destroyed at this revision and no route follows. The destroyStory or destroyChronicle transaction takes one fresh acquisition revision and inserts, per destroyed story, a tombstoned RouteUpdate into membership_history, in static and dynamic mode alike; WatchRoutes delivers history rows in both modes. Full snapshots never carry tombstones (I3.5 keeps them forever). Membership commands skip tombstoned stories: no epoch change, predecessor, drained or abandonment entry is written for one, a DrainKeeper or AbandonKeeper still commits for the Keeper's live stories, and a destroy and a route change for one story are separate commands. Subscribers apply the epoch-regression rule only to updates with tombstoned=false; a tombstoned update is applied whatever its revision, before the epoch and revision guards, never lowers the applied revision, and after it every later RouteUpdate for that story_id is ignored. `WatchRoutesResponse` carries `bool snapshot_end = 12`: exactly one message with it set follows the snapshot entries and precedes every delta, with revision R, story_id 0 and no route. A Keeper, Grapher or Player reconciles only at that marker. A story it holds data for, learned from a route at a revision at or below R and absent from the snapshot, is treated as a received tombstone with no lookup: every story live at R is in the snapshot and story ids are never reused (I3.5). A story known only above R, or only from an acquisition, an append or a FetchHot, keeps the bounded Catalog.GetStory lookup, resolved on a worker before any story gate. A snapshot whose R is below the subscriber's applied revision concludes nothing, and a stream that ends before its marker reconciles nothing. Reconciliation never gates serving. A Keeper acknowledges R at the marker and each later revision after applying it, and reports it as Heartbeat applied_route_revision (PI QA sign-off 2026-10-03). Gates: `MembershipContract.DestroyEmitsTombstoneDelta`, `MembershipContract.NoRouteChangeAfterTombstone`, `RouteWatcherTest.TombstoneUpdateIsAppliedWithoutARoute`, `cluster_adapter.WatchRoutesEmptySnapshotHasOnlyTheMarker`, `DynamicClusterBeforeFirstStoryTest.WatchRoutesEmptySnapshotEndsBeforeFirstDelta`, `RouteWatcherTest.SlowSnapshotNeverLooksUpOrReconcilesBeforeItsMarker`, `RouteWatcherTest.StoryCreatedAfterTheSnapshotKeepsItsAppendsAtTheMarker`, `RouteWatcherTest.AcknowledgesTheSnapshotAtItsMarkerAndEachDeltaAfterIt`.
- W10.18 AcquireRequest adds optional lease_duration_ns=3, optional preferred_keeper_process_id=4, takeover=5, optional expected_prior_incarnation=6 and acquire_request_id=7. AcquireResponse keeps field 6 unused and adds AcquisitionLease lease=8, optional keeper_preference=9, refusal_reason=10, HELD remaining_ns=11, optional current_incarnation=12 and optional termination_cause=13; existing fields 2/3/4 identify a matched terminal tuple. - W10.19 Event stream message size (PI sign-off 2026-10-03). ## 12. Failure model

Each failure names the behaviour and the gate. "Lost" below means lost from the system; ACCEPTED data is by definition lost on Keeper crash. The ids I12.1 to I12.5 have no entry of their own: each labels the rule of the paragraph in this section that carries it in parentheses. I12.6 is retired; I6.10 replaced it.

**Fault-tolerance model.** Core does not replicate events. An event is durable once its Keeper's WAL fsync returns (I5.6). The Keeper keeps it until the Grapher's receipt settles it in the archive (I12.3, I12.4, I13.10). The archive lives on a file system the deployment chooses, and a shared or replicated one gives archive durability. In dynamic mode the Catalog is replicated by Raft (I9.1). A lost Keeper disk loses that Keeper's events that are not yet settled, and reads over them end SOURCE_FAILED and never claim completeness (I4.15, I6.14). Event replication across Keepers is not provided; deployments that need it put the WAL on replicated storage.

**Keeper crash.** ACCEPTED events are lost. DURABLE events are recovered from the WAL on restart and resent to the Grapher. Retained chunks whose receipt was not settled are resent. Gate: `tests/integration/keeper_wal/keeper_wal_restart_test.sh` (ctest `keeper.wal_restart`); `JournalContract.DurableAckSurvivesCrash` (I12.1). A restarted Keeper MUST resume HLC assignment above every frontier it has ever reported: the WAL persists a reserved HLC high watermark and the Keeper never reports a frontier beyond the persisted reservation (gate: `JournalContract.RestartResumesAboveReportedFrontier`). A Read spanning the crash reports laggards until writers resume. Writers MUST re-acquire; the new incarnation sorts after the old one (I7.4). A Tail spanning a crash retains its frontier and discards the restarted source's buffer. Gap-free continuation under I6.13 requires WAL reservation preventing frontier regression; a Keeper without a WAL does not meet this restart rule, and I6.8 separately permits ACCEPTED loss. Writers that must re-acquire after the crash use `takeover=true, expected_prior_incarnation=their own prior incarnation`, with one logical request id reused through retries. A matching current live row can be atomically superseded; an intervening holder refuses PRIOR_MISMATCH. This explicit self-recovery avoids HELD for a full lease without weakening I7.4, WAL reservation or assignment/fence/floor rules. A restart with no prior-incarnation checkpoint follows the Writer crash policy. A generic not-registered rejection alone is not proof of Keeper crash or EXPIRED; classify through Catalog as section 6 specifies. The successor accepts future operations, with prior uncertain operations requiring explicit reconciliation. The smoke and WAL restart gates check exact ids and HLCs, actual fsync receipts and post-restart frontier ordering.

**Grapher crash.** Receipts are scoped to a Grapher instance; a new instance has a new `grapher_instance` and new numbering. A Keeper MUST NOT settle a pending receipt with a report from another instance (I12.2). Component gates: `KeeperRetention.RestartedGrapherSettlesAResentChunkBelowTheKnownWatermark`, `KeeperRetention.DelayedReportFromTheSameGrapherDoesNotUndoANewerOne`. W is recovered from the per-Grapher manifest logs (`FileTierStore::contiguousWatermark` over the merged `ManifestLog` index, `src/common/tier/`). Contract gates: `TierStoreContract.ManifestRestoresContiguousWatermark`, `JournalContract.ReceiptFromAnotherGrapherInstanceIsNotSettled`.

**Interrupted chunk stream.** A stream that ends without an OK ChunkReceipt MUST be treated as not delivered; the Keeper MUST mark the chunk send-failed and keep it readable and resendable (I12.3). Component gate: `KeeperRetention.MarkSendFailedKeepsChunkReadableAndResendable`. Contract gate: `ArchiveTransferTest.PartialStreamYieldsNoReceipt`. A receipt whose byte count differs from what was sent MUST be treated as a failed send.

**Receipt without persistence.** A covering W alone MUST NOT settle a pending receipt (I12.4). Component gates: `KeeperRetention.ChunkAckedUnderACoveringWatermarkWaitsForItsReceipt`, `ArchiveWatermarkTest.ReceiptStaysPendingUntilTheChunkIsWritten`, `ArchiveWatermarkTest.WatchReflectsPublishAndDroppedStory`, `ArchiveTransferTest.AFailedPublishReturnsNoReceiptHoldsTheWatermarkAndNeverReusesTheNumber`. Contract gate: `JournalContract.CoveringWatermarkAloneDoesNotSettleReceipt`.

**Keeper shutdown.** The Keeper MUST hand unshipped chunks to extraction while it still runs, resend chunks with no receipt, and wait up to `shutdown_confirm_timeout_secs` (default 150, `src/keeper/KeeperConfig.h`) for the Grapher to confirm (I12.5). Gates: `KeeperRetention.ShutdownWaitEndsWhenTheGrapherConfirmsEveryChunk`, `KeeperRetention.ShutdownWaitSendsAgainAChunkTheGrapherNeverWrote`, `KeeperRetention.ShutdownWaitGivesUpAtTheTimeout`, `KeeperRetention.ShutdownSendsAgainAChunkWhoseSendFails`.

**NFS and shared file systems.** Measured by Kun Feng on ares-comp-[03-08], NFSv3, `acregmax=120` (commits 152dd5a8, 56571da5 on origin/archive-file-manifest):

| Assumption | Result | Measurement |
| --- | --- | --- |
| concurrent O_APPEND from several clients is atomic | FAIL | 66.1% record loss, 6 nodes synthetic; 3.2% in a live 2-Grapher run; 0% with 6 processes on 1 node |
| stat() reflects recent writes promptly | FAIL | 120.14 s detection lag against a 1 s poll |
| compaction is detectable | PASS | via mtime, late never lost |
| link() fails rather than clobbers | PASS | EEXIST |
| readdir sees new files | PASS | no persistent UNRECORDED |

Consequences, all normative: no two processes MAY ever append to one file on a shared file system (per-Grapher manifests, section 13). A poller MUST open() a file before deciding whether it changed; stat() on the path is not a change detector. After the fix the publish-to-visible latency measured median 0.19 s, max 1.00 s at a 1000 ms poll (commit 56571da5). Gates: `ManifestLog.EachWriterAppendsToItsOwnLog`, `TierStoreContract.IndependentWriterLogsMergeWithoutSharedAppend`, `FileTierStore.ReadersMergeNewWriterLogsAndDeduplicateInReplayOrder`, `ManifestLog.CompactionLeavesOtherWritersLogsAlone`, `ManifestLog.ATornFinalLineIsDiscardedAndEarlierRecordsSurvive`; `tests/integration/keeper_wal/manifest_restart_test.sh` (ctest `grapher.manifest_restart`). A Player that starts before any manifest exists MUST adopt one that appears later without restart (third bug in commit 56571da5; gate: `ColdReplay.ReadOnlyViewMergesEveryWriterAndNeverScansDataFiles`, which covers a manifest log created after startup). The archive scanner MUST exclude manifest artifacts: Open's orphan scan reads only numeric story directories and adopts only names that parse as chunk files, so nothing under `manifest/` is ever adopted (`src/common/tier/FileTierStore.cpp`).

**Clock loss.** When the Clock source becomes Unavailable the Keeper MUST keep assigning HLC from last-assigned plus logical ticks. Writer physical readings pass through unchanged. Physical-axis reads follow I6.10: an event's interval uses its bound when Synced, and a selected event without a finite bound makes the Read incomplete with PHYSICAL_AXIS_UNBOUNDED (I12.6, replaced by I6.10). Gates: `ReplayContract.PhysicalRangeHonorsUncertainty`, `ClockContract.UnavailableSourceKeepsHlcAdvancing`.

**Visor crash.** Catalog state is in SQLite with WAL journal mode and synchronous=FULL, so every acknowledged acquire and incarnation bump survives (section 9). In static mode Routes are fixed from configuration, so Keepers continue serving; acquire and release are unavailable until restart, and appends under a valid epoch continue. In dynamic mode the same operations replicate through NuRaft and a Visor crash fails over to a new leader; a new leader waits a full keeper_failure_timeout_ms before declaring any Keeper failed. Gate: `tests/integration/visor/visor_restart_test.sh` (ctest `visor.restart`).

**Keeper failover (dynamic mode).** A Keeper that stops renewing its ceiling stops admitting within ceiling_ahead_ms (I4.7). When the leader removes it from its stories' Routes (I4.9), the successor admits only above the ordering cut, Reads below the removed Keeper's own cut need it as a predecessor source until it returns and drains (I4.13, I4.14), and an operator who declares it lost uses AbandonKeeper, whose ranges stay SOURCE_FAILED forever (I4.15). Gates: the dynamic-mode integration test, ctest `visor.dynamic_failover` (`tests/integration/dynamic/`, listed in section 15).

**Player crash.** Stateless. A client's ReplayStream ends with a non-OK status; the client re-issues Read or Tail from its last position (I6.9). Gate: `ClientContract.ClientResumesTailAfterStreamError` in `client/cpp/tests/`.

**Writer crash.** A restarted writer without a prior incarnation waits for committed expiry before ordinary Acquire, or uses a deliberate unconditional takeover. An RFC-F launcher holding its host-local slot lock and checkpointed prior incarnation may use `takeover=true, expected_prior_incarnation=N`; only the current row N, live or terminal, can advance. Mismatch returns PRIOR_MISMATCH/current incarnation and cannot fence a newer holder. Within one process each logical Acquire retains its at-least-128-bit random request id across a lost reply; a checkpoint or restart never restores it and always creates a fresh id for prior CAS. An unknown newer PRIOR_MISMATCH requires explicit takeover; retry of the current live grant returns the same incarnation rather than HELD. A new successful grant strictly increases incarnation, while an idempotent retry does not. I3.7/I7.4 still reject late old-incarnation appends after the Keeper has seen the release/new incarnation; before the fence they remain valid and sort before the successor. Unacked DURABLE requests remain UNKNOWN and never become fabricated acknowledgments or silent resends. Gates: `JournalContract.ReleasedIncarnationCannotAppend`, `JournalContract.OlderIncarnationIsRejected`, and the request-id and CAS recovery cases `MetadataStoreContract.RetriedAcquireAfterLostReplyReturnsTheSameGrant`, `RequestIdRejectsChangedInputsWithoutMutation`, `CompareAndSwapTakeoverRequiresCurrentPriorIncarnation`, `PriorMismatchReportsCurrentIncarnation`, `ConditionalRecoveryCannotTakeOverANewerHolder`.

**Release fencing lag.** Between Catalog's commit of a release and the Keeper applying that revision, the old incarnation can still append at its Keeper. Those events are valid and sort before the next incarnation because the next incarnation is assigned the same Keeper in the same epoch (I7.5). Release reports `fenced=false` when the Keeper did not confirm within the timeout (W10.12). A Visor restart MUST NOT reuse a revision; the counter is a persisted SQLite row. The Keeper heartbeats immediately after applying the fence (W10.6). Gate: `MetadataStoreContract.ReleaseReportsFenceState`, `MetadataStoreContract.RevisionSurvivesRestart`.

**Partial manifest line.** A torn final line MUST be discarded and earlier records kept (`ReadTail` keeps only complete newline-terminated lines and retries an incomplete one at the next poll, `src/common/tier/ManifestLog.cpp`). Gate: `ManifestLog.ATornFinalLineIsDiscardedAndEarlierRecordsSurvive`, `TierStoreContract.TornManifestRecordIsIgnored`.

| Failure | Behavior and residual |
| --- | --- |
| Writer dies without Release | No new admission or explicit renewal; a continuously qualified Catalog eventually commits EXPIRED. New term/restart can add T; same-term lapses preserve remaining time with downtime excluded. Static destroy waits for fence proof. |
| Writer cannot reach Catalog, reaches Keeper | Keeper-carried new admission renews if Keeper reaches Catalog. RPC failure/local horizon never stops SDK dispatch. |
| Busy Writer reaches Catalog; Keeper cannot | All-Writer scheduler explicitly renews on lead schedule even during continuous append. Keeper evidence is supplementary; its failed delivery cannot alone expire this Writer. |

Dynamic residual bounds concern new admission under existing ceilings, not fsync latency or lease safety. Static fence proof can delay destroy indefinitely until the owning process is restored. Timeout never supplies that proof.

## 13. Tiering

Tiers are ordered per deployment and get slower (RFC-I 3.1): Keeper RAM (hot, serves Tail and recent Read, bounded by retention_cap_mb); the Keeper WAL (DURABLE); `local`, the Grapher's archive_root wherever it lives, where every chunk is published; then zero or more slow tiers of kind `posix` (NFS, PFS, a second disk; `s3` is deferred). Manifest logs, snapshots and validated marks stay with `local` (I13.7); a manifest never lives on a migration target. Every Grapher and every Player that reads an archive has a tier table in its own config: an ordered list of {name, kind, root, rank} with `local` at rank 0, where a root is a path on that host. Manifest lines name a tier, its rank and its uuid, never a host path. A posix slow tier MUST honor fsync and make link and unlink durable on reply, which on NFS means a `sync` export. The Grapher is the only writer to the archive; Players are readers. Chunk windows are half-open on the HLC axis (`Chunk{start, end}` in `types.h`).

- I13.1 Files MUST be published (written to a temporary name, fsync'd, installed by link() under the final name then unlink of the temporary, then the containing directory fsync'd) before their manifest record is appended or durability is confirmed, so the manifest never names a partial or unlinked file and never overwrites an existing one. A crash between the two loses the trailing record, which only under-reports W. Source: `FileTierStore::publish`, `src/common/tier/FileTierStore.cpp`. The Grapher subscribes to WatchRoutes and acts only on tombstoned entries and on stories W10.17 concludes destroyed at a snapshot_end marker: it first appends and fsyncs a `Tombstoned{story_id}` record in its own manifest log (I13.7); it refuses TransferChunk for the story with FAILED_PRECONDITION, decided from the manifest alone so the refusal survives restart; only then does it send WatermarkReport{dropped=true} to every Keeper; and on a worker (M11.7) it waits on its condition variable until the story has no pending receipts, then erases every Published and Empty-window file through Deleted records (I13.5), repeating until none remain and resuming from the manifest after a restart. - I13.12 Background compaction replaces contiguous small archive files of one Grapher with one output through a single fsync'd `compact_v1` line in that Grapher's own log, so every merged manifest shows either all inputs or the output. Any manifest append or fsync failure stops compaction until the Grapher reopens. A reader of a superseded input reads the output restricted to the input's HLC window. Recovery removes an unreferenced own output only when its own inputs cover its window and validate, and rolls back an own output that fails validation while every input is intact. - I13.13 Migration (RFC-I 3.3). A Grapher moves a file to a slower tier only through one fsync'd `migrate_v1` line in its own manifest log, so every merged manifest shows the file at exactly one effective location (I13.14). It moves only files it owns: the effective record belongs to its manifest_writer and the file name encodes it. A file is eligible when its effective record is Published or Empty, its window ends at or below W, a validated mark covers it (I13.17), no switch that is not rolled back supersedes it, it is not a compaction output whose inputs still await cleanup, it holds no claim, no in-flight publish claims its window, and its story is not tombstoned. Every background job that moves, rewrites or unlinks an archive file claims it first under the store mutex, and a file holds at most one claim. The destination is written to a temporary named `.migrate-<hex writer>.<token>`, fsync'd, installed by link() then unlink of the temporary, its directory fsync'd, and verified by reading it back from the tier and comparing length and CRC32C with the source. Every slow-tier operation is relative to the directory descriptor of the tier's availability epoch (I13.15), and nothing ever creates a tier root or an ancestor of it. The line is appended only under the store mutex, after a re-check that every eligibility condition still holds, that the attempt's claim is current, and that the attempt's descriptor is still the epoch's; otherwise the attempt removes what it wrote and appends nothing. An attempt abandoned on a hung tier never commits; when its thread returns it removes only its own temporary and a destination it created. Only the committing thread unlinks the source, after its own fsync of the line succeeded; a restarted Grapher only after it fsynced its own log and re-verified the destination. Outside a tombstoned story a Grapher sweeps, moves and unlinks only names that encode its own manifest_writer; the tombstoned-story sweep is the only cross-writer unlink. Any manifest append or fsync failure stops migration until the Grapher reopens and keeps both copies. Migration never changes a record's state, window, event count or W. After a pass that moved a file the Grapher writes its manifest snapshot to `<tier>/manifest-replica/<writer>.snap` on every slow tier. migrate_enabled is false by default: a deployment whose archive root has a Player or Grapher that cannot read `migrate_v1` MUST keep it false, and it requires a running scrubber (scrub_interval_s above zero). Gates: `FileTierStore.MigrationCrashAtEveryStepLeavesOneEffectiveCopy`, `FileTierStore.MigrationCommitRechecksUnderTheStoreMutex`, `FileTierStore.CompactionNeverTakesAMigratedOrMigratingInput`, `FileTierStore.PeerSweepNeverRemovesAnotherWritersInFlightDestination`, `ManifestLog.ForeignMigrateLineFailsTheRefreshClosed`, `GrapherTierInterleavings.MigrationThroughAReplacedRootNeverCommits`, `GrapherTiers.WorkerMigratesAndReadsIdenticalEvents`, `GrapherTiers.AnIdlePassRewritesNeitherTheReplicaNorTheStatusFile`, ctest `grapher.manifest_restart_migrated`.
- I13.14 Effective location (RFC-I 3.4). A file's effective location is the slowest tier, by rank, named by any `migrate_v1` line for that file, else `local`. It does not depend on the order in which a reader applies log and snapshot lines, and a file never moves to a faster tier. Two lines naming one file at one rank with different tiers or uuids fail the refresh closed. Every open, read, validation, duplicate comparison and unlink of an archive file resolves this location first. A reader that does not find a file where it resolved it re-syncs the manifest and follows the file's compaction successor or its new location once before it reports a failure. An erase unlinks the file at its effective location and at every faster tier where a stale copy may remain, and ENOENT counts as success at each location separately, only after the tier's marker re-read correctly through the operation's descriptor. Gates: `ColdReplay.MigratedArchiveAndReaderPlannedBeforeMigrationReturnIdenticalEvents`, `GrapherTierInterleavings.EraseThroughAReplacedRootStaysPending`, `GrapherTiers.DestroyRequeuesUnavailableTierAndCompletesAfterRecovery`. A Keeper resending a window whose holder migrated is compared against the holder at its effective location; while that tier is unavailable the transfer is UNAVAILABLE and writes nothing, so its receipt settles when the tier returns. Gates: `ManifestLog.MultiHopLocationIsOrderIndependentAcrossSnapshotCompaction`, `FileTierStore.PublishDuplicateOfAMigratedWindowSettles`.
- I13.15 Unavailable is not lost (RFC-I 3.5). Each tier root holds `.chronolog-tier.json`, written only by an explicit tier-add (`chronolog tier add`, and `chronolog create` for `local`), never by a boot, a probe or a migration. It carries the deployment id, the tier's name, rank and kind, a random 128-bit tier_uuid, and the file system identity seen at tier-add. A tier is available only while its marker, read through a directory descriptor of the root opened by a probe, names the expected deployment, tier, rank and uuid and the root's f_type equals the recorded one. An availability epoch owns that one descriptor: it starts with the probe that opened it and ends when a probe or an operation fails or times out, never because a later probe of a healthy root ran. A root without its marker is unavailable, never empty. A file on an unavailable tier is unreadable (I6.14) and never recorded LOST; ESTALE and EIO mark the tier unavailable and never count as missing. The Player never records LOST, and a Grapher never records LOST for another writer's slow-tier file. The owning Grapher's scrubber (scrub_slow_tiers) records LOST for a slow-tier file only when the file is missing (ENOENT) or fails its length, checksum or decode through openat on the epoch's descriptor, the marker then re-reads correctly through the same descriptor, a manifest re-sync still resolves the file to that tier as effective, and the same verdict repeats in a later pass at least tier_probe_interval_ms after the first, under a probe that started after the first verdict and verified the root; a pass that reads the file intact, or any failure that is not such a miss, withdraws the pending verdict. Every slow-tier operation runs on that tier's executor and is awaited for at most tier_io_timeout_ms; a full queue fails at once with UNAVAILABLE; nothing at Open, destroy, compaction or shutdown waits on a slow tier. A store configured with a deployment id refuses to open a `local` root whose marker is absent, names another deployment, or is not rank 0. The tier status file (tier_status_file) is rewritten when its content changes and at least every tier_status_heartbeat_ms, carries written_at_unix_ms and heartbeat_ms so a reader can tell a stale file, and carries the last scrub pass (enabled, validated, skipped, lost, rolled_back, slow_failed, through, finished_at_unix_ms, error); an idle pass rewrites neither the status file nor a manifest replica before the heartbeat is due. - I13.16 Capacity (RFC-I 3.7; contract part signed off 2026-10-03). Each tier has budget_bytes and min_free_fraction (the tighter applies) and a high and a low watermark. - I13.17 Bounded recovery (RFC-I 3.8; PI sign-off 2026-10-03). Every own line that makes a file effective (a Published or Empty record, a compact_v1 output, an adopted orphan) carries `seq`, a number strictly greater than every seq its writer ever assigned; Open starts above both the own log's highest seq and the writer's validated mark. A record without seq counts as seq 0 and is covered by any mark of its writer. A Grapher's scrubber validates every own effective Published file on `local` (on slow tiers too when scrub_slow_tiers is set) at scrub_io_bytes_per_sec, repeating every scrub_interval_s. A pass that started when the highest durable own seq was N, and validated every own effective Published file on `local` with seq at most N, replaces `manifest/<writer>.validated` with {writer, through: N} by temporary, fsync, rename and directory fsync. A file the pass skipped because it was claimed, superseded, Deleted or moved since the pass planned it does not hold the mark back; the next pass validates it where it then is. Open validates every effective Published record on `local` whose seq exceeds its writer's mark, where a writer without a mark covers nothing, so a store without marks recovers exactly as before this rule. Whatever the marks, Open validates before any cleanup the own effective records inside the window of every unreferenced own compaction output and every own committed switch output whose inputs remain. Open never validates a file on a slow tier, and it re-resolves a peer's record to its effective location before it records LOST or rolls back. LOST is recorded by Open or by the scrubber, never by a read. The scrubber records LOST, or rolls back an own switch output, only under the store mutex after a manifest re-sync and re-resolution, and a rollback first withdraws its inputs from pending unlinks; an input already claimed for unlink turns the rollback into a LOST. An unlink claim is granted only if, under the store mutex, the file is still pending unlink and is one of: still Deleted, still superseded by a switch that is not rolled back, a file of a tombstoned story (I13.11), or the output of a rolled-back switch (I13.12). A read of a missing or corrupt file is SOURCE_FAILED whether or not LOST was recorded (I6.14). ## 14. Security boundary

Core (this repository) provides no TLS, no authentication and no authorization, and it does not replicate events (section 12, Fault-tolerance model). Core assumes a trusted network segment.

- S14.1 The gateway, a separate deployable, does authentication, namespace ACLs at chronicle granularity, redaction of `payload` and of `gen_ai.tool.call.arguments` before append, and an audit log of every Catalog mutation. The log is immutable; nothing in core can scrub a secret after append.
- S14.2 Core MUST NOT grow an auth field in `chronolog.v1`. Identity for audit is carried by the gateway in a request header (name TBD) that core forwards into `attributes` unchanged.
- S14.3 Internal services (`chronolog.internal.v1`) MUST bind only to the cluster interface listed in configuration and MUST refuse to start on 0.0.0.0 unless `--insecure-bind-all` is set. Gate: `tests/integration/bind_guard_test.sh` (ctest `integration.bind_guard`).
- S14.4 The SDKs talk to the gateway or directly to core; they MUST NOT embed credentials.
- S14.5 Core MUST NOT log payload bytes at any level. Gate: ctest `contract.ContractLogs.NoPayloadInLogs` (`tests/contract/log_payload_guard_test.sh`) scans every absl logging and CHECK statement under `src/`, comments and string literals removed, for a payload identifier.
- S14.6 The envelope `actor` (I3.9) is a claim by the writer. Core neither verifies it nor derives an access decision from it; an identity that must be trusted comes from the gateway (S14.1, S14.2).

## 17. Relation to legacy ChronoLog

ChronoLog 4.0 is a rewrite. It removed Mochi, Thallium, Margo, Argobots, RDMA and Spack from the build (M11.4 keeps them out) and kept the legacy semantics that protect data. Legacy ingestion, chunking and RAM retention became the Keeper's Journal, which added the fsync'd WAL behind DURABLE (sections 5 and 13). Legacy extraction, HDF5 chunk writing, the archive manifest, receipts and watermark reports became the TierStore in `src/common/tier/` and the Grapher, with chunk transfer on Archive.TransferChunk (W10.4), watermark reports on Archive.WatchWatermarks and `dropped=true` in place of the UINT64_MAX sentinel (W10.5). Legacy Visor chronicle, story, acquisition and registration state became the Catalog and Cluster behind the MetadataStore and Membership contracts, persisted in SQLite (section 9). The legacy Cristian clock exchange became the chrony-backed Clock, keeping the client's monotonic clamp and test seam (section 8). The legacy Player's range split, merge and archive reader became the Replay contract in `src/player/` (section 6). The legacy client protocol and Thallium wire format gave way to `chronolog.v1` over gRPC (section 10), and chunk windows moved from steady_clock nanoseconds to the HLC axis (section 13). Every legacy test was re-homed on a 4.0 test or dropped with a reason named in the commit that deleted it (da0a6275 Keeper, f3d26493 common, 1613e3a7 Grapher, c8f72499 Player, d55b5840 client, 8b60c648 Visor); legacy retirement completed with b4705f68. Of the legacy guard tests only `tests/integration/visor/clock_skew_harness.sh` survives, and it runs on 4.0 as ctest `visor.clock_skew`.

## 18. Non-goals

- Semantic memory, embeddings, retrieval, or any query beyond time range, tail, the equality predicates of I6.17 (kind, actor, attributes, links) and link lookup by EventId and await (I6.19, I6.20). The PI lifted this non-goal for those two on 2026-10-04. Value indexing in the Keeper (a secondary index over attribute values or payload), predicates on the payload, disjunction and pattern match across terms, and anything semantic remain non-goals.
- Latency or throughput claims of any kind without a measurement recorded in the merge or issue that makes the claim, naming hardware, build type and commit.
- Cryptographic or tamper-evident receipts. A ChunkReceipt is a counter and a transfer checksum (CRC32C by default), not a proof against a malicious Grapher.
- TLS, authentication or authorization in core (section 14), and event replication across Keepers (section 12, Fault-tolerance model).
- Ownership changes in static membership mode; only dynamic mode changes epochs (I4.3).
- ML-based clock bounds in v1 (section 8).
- Preserving the legacy client protocol, Thallium wire format, or Spack packaging.
- Multi-Keeper write replication for one writer (I7.5). A Route may list several Keepers for partitioning, never for redundancy, in v1.
